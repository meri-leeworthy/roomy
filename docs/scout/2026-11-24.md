## Proposals (ranked)

### 1. Retry a send once on a fresh connection when the pooled socket was already closed

- Evidence: `discord-bridge`, 24 h to 07:01Z: **88**
  `Discord→Roomy send failed; queued for re-offer` records, **every one** whose
  `error` is undici's *"The socket connection was closed unexpectedly"* —
  against **1** the previous day. 88 re-offers then landed and **22 failed
  again**. The same string appears **385** times in the bridge's 24 h: 248 as
  `Connection error for <space>` (`live-roomy`), 110 in `send-retry`, 25 in
  `profile`, 2 in `reactions`. **328 of the 385 land within 30 s of one of the
  1,773 sync socket closes**, so one transport event takes out both the WS and
  the pooled HTTP path. The send path is a single attempt by design —
  `send-retry.ts:67-78`, whose comment justifies it against "the dominant
  failure is already a 20s XRPC timeout", a different class from a
  connection-reuse error that returns before a byte of response. On failure the
  entry waits `SWEEP_BASE_MS` 30 s, doubling to a 30-minute cap
  (`send-retry.ts:44-45`), so the Discord message lands up to ~30 min late.
- Why now: this is the user-visible half of the flap. A Discord message that a
  user typed is not lost, it is silently delayed by up to half an hour, 88 times
  a day on the bad days and ~0 on the quiet ones.
- Scope sketch: in `sendEventOrQueue`, classify the failure before queueing —
  an error marked `code: "UND_ERR_SOCKET"` (or the "socket connection was closed
  unexpectedly" text undici produces) is a stale-pooled-socket reuse, so
  re-attempt the send exactly once on a new connection and only queue if that
  attempt fails too. Count both outcomes (absorbed / queued). Do not change the
  queue schema, the backoff, or the single-attempt rule for timeouts.
- Acceptance: 24 h after deploy, no `Discord→Roomy send failed; queued for
  re-offer` whose `error` is a closed pooled socket, and a test that a first
  attempt failing on a reused socket succeeds on the second without touching the
  queue.
- Suggested priority: P2.
- Not already tracked because: TASK-479/`#622` count ingest *skips*;
  TASK-487/`#635` is bridge liveness over shard/subscription state; `#528` logs
  the reconnect. Nothing classifies a stale-socket error or retries it, and the
  "attempt once" decision in `send-retry.ts` was made against timeouts.

  heartbeat closes with code `4000` and reason `heartbeat-timeout`

  drop an idle socket on its own. The heartbeat is not the visible cause.
