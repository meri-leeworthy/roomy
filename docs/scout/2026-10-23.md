### 1. Every appserver restart takes production down for about two minutes, because the boot sweep walks 4,442 space DBs while the server is already answering traffic

- **Evidence.** Three restarts landed inside three hours last night, and each produced the same signature. The last one: `appserver ready (DID: did:web:api.roomy.space, port: 8080)` at **01:33:54Z** on build `080b95dd` (`packages/appserver/src/index.ts:79`), then **161** `Error: Request timed out: query` lines between **01:34:26Z and 01:35:30Z** (54 in the 01:34 minute, 107 in 01:35), every one on that build. `roomy_db_timeouts_total{type="query"}` reads **233** and is flat at 233 on every scrape from 01:37Z onward — the whole day's timeout budget was spent in that window; `{type="checkSpaceSchema"}` is 2 and `{type="health"}` 4, likewise boot-only. The burst is not confined to one route: `space.getMetadata` 11 lines, `admin.getSpaceMembership` 10, sync `topic access check failed` 101 (one per room per bridged space), `sendEvents` 4 — i.e. live traffic, not a background job.
  **The work is the boot sweep.** `reMaterializeFromLocalEvents` is deliberately fire-and-forget (`src/index.ts:68-79`, the comment says *"the server is already accepting requests"*), and it then walks **every** stream sequentially: `checkSpaceSchema`, `hasPendingSpaceMigrations`, `backfillEntitySpace`, `PRAGMA optimize` per stream (`src/streams/reMaterialize.ts:245-300`). The two startup lines bracket the walk: ready at **01:33:54**, `re-materializing 15 streams from local events DB (4427 already up to date)` at **01:38:26** — 4,442 streams in 4 min 32 s, in the same DB pool that serves requests. One space's schema check timed out twice inside that window (`schema check timed out for did:plc:223vz7mgtjzrcbnzlh5qvjhs (attempt 1/4)` 01:34:45, `(attempt 2/4)` 01:35:20).
  **The client-visible half is worse than the error lines.** Across the three restart windows Cloudflare returns **502 `origin_bad_gateway`** for `space.roomy.auth.getConnectionTicket`: the bridge logs **9** of them, at `22:25:40`–`22:25:46`, `23:42:06`–`23:42:21` and `01:34:05`–`01:34:08` — the last pair inside the sweep window, the first two in the gap before the process answers at all. Each is a bridged space that cannot open its sync socket until it retries. The bridge's capacity gate fails in the same windows: **46** `capacity: getSpaceMembership failed … keeping previous decision` lines in 24 h, **33 of them in the 23:00 hour and 13 in the 01:00 hour**, i.e. all of them in the two restart hours.
- **Why now.** This is the first appserver restart since 2026-10-15 (the old process had 587,851 s of uptime), so the cost has not been visible in the records; with the current merge cadence — 38 PRs closed in the last 24 h, three appserver deploys — it is now a several-times-a-day event. Every deploy buys two minutes of 502s, 233 DB timeouts, a dropped socket per bridged space and a capacity gate reading stale.
- **Scope sketch.** Two changes, either of which alone shrinks the window; both are in `packages/appserver`. (a) Hold readiness: `log.info("startup", "appserver ready")` and the health response should come after the sweep's first pass, or the process should answer `/health` with a not-ready status until then, so the platform does not route traffic into a pool that is mid-sweep. (b) If fire-and-forget is kept deliberately, bound its *pressure* rather than its concurrency: the per-stream `analyze` and `backfillEntitySpace` are idempotent, cost a round-trip each, and are the bulk of the walk — batch them (one transaction per N streams) or yield between streams so the live pool is never starved.
- **Acceptance.** Deploy a build that has pending stream work; in the five minutes after `appserver ready`, `roomy_db_timeouts_total` shows **no increase** and the appserver logs no `Request timed out: query`; the bridge logs no `getConnectionTicket … 502` and no `capacity: getSpaceMembership failed` for that window. An appserver boot from a caught-up DB is unchanged (the sweep still reports "all N streams already up to date").
- **Suggested priority:** **P2** — no data is lost, but every deploy is a user-visible two-minute outage plus a bridge-wide socket reset, and the fix is a readiness gate or a batched walk.
- **Not already tracked because.** No task, plan or PR names the boot sweep's cost. `TASK-393` is about socket drops as a steady-state phenomenon (267/24 h, unrelated to restarts); `TASK-356` is a worker host's runaway `bun test`. Nothing in the queue mentions boot, readiness or deploy windows.

### 2. The client's persisted cache is 77% single-message entries, so it evicts the rooms it exists to keep — 37,729 entries dropped in a day

- **Evidence.** The client telemetry stream (`service_name="roomy-app-lite"`, 24 h, 649 lines) carries **124** `cache: dropped entries over the persistence budget N dropped: […]` lines in one day, totalling **37,729 evicted entries** (mean 304 per drop, max **450**). The budget is `MAX_PERSISTED_ENTRIES = 200` (`packages/app-lite/src/lib/client.ts:124`), so each drop is a set that had grown to 400–650 while the cap held 200.
  **What is being kept is not what persistence is for.** Each drop names a bounded 5-key sample (`DROPPED_KEY_SAMPLE`, `packages/sdk/src/cache/bound.ts:40`); across the 124 lines that is 620 sampled keys, of which **479 (77%) are `space.roomy.message.getMessage`** — one entry per *message id*. The rest are the entries that make a restore useful: `room.getMessages` 48, `room.getMetadata` 29, `space.getMetadata` 26, `getRoomSummary` 26, and the tail (`getRequests` 5, `getMembers` 4, `getMembershipStatus` 3) — i.e. the room lists and headers are exactly what the per-message flood pushes out.
  **Where the flood comes from.** `createMessageQuery` (`packages/app-lite/src/lib/queries/message.ts:56-96`) is instantiated once per rendered reply context (`MessageContextReply.svelte:16`), keyed per message id (`:81`), and seeded from the room list it already holds (`initialData`, `:88-94`). `isPersistableQuery` (`packages/sdk/src/cache/persister.ts:132-142`) accepts any success-status query with data and a non-zero `gcTime`, so every one of those seeded per-message entries is persisted as a first-class entry — duplicating a message that is already inside the persisted `room.getMessages` page.
  **A second, smaller drain:** **13** `cache: snapshot has a different shape version; discarding` lines, because `persistedShapeVersion(buildId)` (`persister.ts:99-101`) folds the build id into the snapshot version. With three deploys in the window, a snapshot written by one build is discarded by the next.
- **Why now.** The persistence seam exists so a reload restores rooms instead of a cold start ("the rows persistence exists to keep", `client.ts:155-158`), and the budget was chosen deliberately to be deterministic. Today the budget is spent on 77% duplicates, so the feature's benefit is mostly thrown away on the restore path — and the symptom is invisible unless a client's console is read, which is why it has run unremarked.
- **Scope sketch.** Keep the 200-entry budget; stop the duplicates entering it. Add a persistence opt-out honoured by `isPersistableQuery` (a `meta` flag on the query) and set it on `createMessageQuery`, whose data is by construction already in `room.getMessages`; alternatively exclude keys whose data arrived only as `initialData`. Do **not** raise `MAX_PERSISTED_ENTRIES` — the cache already evicts 96% of `getActivityFeed`'s entries server-side, and a bigger client budget would persist more duplicates.
- **Acceptance.** A 24 h telemetry read shows no `dropped entries over the persistence budget` line whose sampled keys are dominated by `getMessage` (and a drop of >200 entries becomes rare rather than hourly); a session that opens 20 rooms, reloads, and finds `getSpaces`/`getMetadata`/`room.getMessages` restored from the snapshot — verified by a component test on the persister's `selectPersistableEntries` with a seeded message query present.
- **Suggested priority:** **P3** — no data loss and no user-visible error; the cost is that the offline/first-paint restore keeps the least useful 200 rows.
- **Not already tracked because.** No task mentions client persistence, the cache seam or `MessageContextReply`. `TASK-19` is auth; CF1 is the *server's* query cache, a different cache with a different eviction story.

### 3. The boot replay reports `succeeded: 15, failed: 0` while applying zero events — and advances the cursor past every event it could not decode

- **Evidence.** The 01:38Z replay on build `080b95dd` names 15 streams and every one of them reports `applied: 0` with a non-zero `materializerErrors` — 1, 1, 1, 3, 5, 7, 7, 10, 17, 20, 22 and so on, **89 in total** — and then the run closes with `progress … "succeeded":15,"failed":0` and `complete "succeeded":15,"failed":0`. A replay that applied nothing is reported as a clean pass.
  **The reason is a decode that yields no `$type`.** The per-event warnings in the same second read `no materializer for event 01KDRHF2VR9KMFFH2E4JDRN63E (kind: undefined) — skipping` — not a retired event kind, an *absent* one. The cause is `event: decode(e.payload) as Event` (`packages/appserver/src/streams/reMaterialize.ts:513`), a raw `@atcute/cbor` decode cast to `Event` with no validation, which `materialize()` (`packages/appserver/src/materialization/materializer.ts:28-37`) then reports as `No materializer found for event kind: undefined`.
  **Nothing retries, and nothing is attributable.** `applyBatch` increments `stats.materializerErrors` and records the failure for a debug-only sink (`applyBatch.ts:171-190`; the reason is logged only under `isDebugEnabled()`), and the chunk's cursor is advanced regardless — *"used to advance the cursor after the chunk is processed (whether it succeeded or failed)"* (`applyBatch.ts:307-310`). So the event is skipped permanently, and the only surviving trace is a per-stream count with no kinds in it.
- **Why now.** The counts are small today (89 events, 15 of 4,442 streams, all legacy ULIDs from 2025-12 and 2026-01), and that is the point: a *current* decode regression would look identical — same `applied: 0`, same green summary, no alert, and the cursor already past it. This is the failure mode the appserver has no observability for, and CF2 says no rule would fire even if it did.
- **Scope sketch.** Separate the two cases that `materialize()` currently collapses: an event whose decoded payload has no `$type` is a **decode failure** and should log with the event id and payload length at `warn` (it may be a legacy encoding, which is fine, but say which), while "no materialiser registered for a *known* kind" stays a skip. Then make the replay summary honest: a stream with `materializerErrors > 0` should not be counted in `succeeded`, and the per-stream line should carry the distinct kinds skipped. Leave the cursor policy alone unless Meri wants un-decodable events to block a stream forever — that is a decision, not a bug.
- **Acceptance.** A unit test replays a stream containing one event whose payload has no `$type` and one with a known-but-unregistered kind, and asserts the run's summary reports a non-zero skip count with both kinds named; a boot that replays only legacy events logs one line per stream naming the kinds, and still boots.
- **Suggested priority:** **P3** — no observed user impact today; it is the reporting and attribution half, and it is the only thing standing between a decode regression and silent permanent data loss.
- **Not already tracked because.** TASK-399 is the record-path migration (a different replay seam); no task or plan mentions re-materialisation, the cursor policy, or decode failures.
