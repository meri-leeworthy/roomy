### 1. The Discord bridge's backfill still drops a failed thread-create forever, and the room's messages are dropped with it

- **Evidence.** `packages/discord-bridge/src/services/backfill.ts:755` and `:1633` call `roomy.sendEvents(spaceDid, events)` directly, inside a `try` whose catch only logs (`:780-784` — `\`Failed to create Roomy thread for ${thread.id} in ${spaceDid}\``). `repo.registerMapping(spaceDid, "thread", threadId, threadUlid)` sits on the next line, so a failed send means the mapping is never written. **`#397` (`dcd62d92`) moved `room-sync.ts`'s four sites onto `sendEventOrQueue` and did not touch this file** — `grep -c sendEventOrQueue packages/discord-bridge/src/services/backfill.ts` → **0**. - **Why now.** The failure is one event in 7 days, and it is total and permanent for the thread it hits: no room, and no backfill of the thread's history either (the `backfillRecentWindow`/`backfillChannel` calls that follow also sit behind the mapping). ### 2. The search backfill re-scans the whole `entity_space` index once a minute, forever, to find a space it has already caught up

- **Evidence.** `packages/appserver/src/search/backfill.ts:557` (`nextCursorSpace`) and `:545` (`hasCursorlessBacklog`) both open with `select distinct space_did from (select distinct space_did from entity_space) s left join search_backfill_cursor c …`, and the loop calls `nextCursorSpace` **every 60 s** (`IDLE_POLL_MS`, `:30`) even when nothing is pending — the steady-state log line is `scope=search-backfill msg=progress spaceDid=did:plc:um4u37yulavnw64jfqgozjkw rows=0 indexed=0 failed=0 backfilled=115` once a minute. - **Acceptance.** On a caught-up corpus, `/health/search` still reports the same fields and the per-cycle query stops appearing in `[db-slow]` (or its p95 drops below the 50 ms threshold) while `sum(count_over_time(… scope="search-backfill" [1h]))` stays at ~60/h. ### 3. The CLI's `--parent` says it creates a thread and sends a reply, and the responder propagates a stored bad target

## Limits of the evidence

- **Proposal 1's mechanism is a source read plus two live log facts, not a staged reproduction.** The `sendEventOrQueue`-free `backfill.ts` is a grep on `3f414b57`; the `Failed to create Roomy thread` line and the 750 drops are exact log reads on the bridge build production runs. What I did **not** do is read the bridge's `failed_sends` store (I have no access to its LevelDB) or observe the thread's messages being lost at ingest. "Permanently" means "until a backfill for that space runs successfully", per the code paths I read.
- **Proposal 2's cost is a sampled estimate, not a whole-stream measurement.** The 6 h figure (818 s over 348 occurrences) comes from a `limit=1000` Loki range query over `scope="db-slow"` filtered to that one SQL string; Loki's `limit` is applied per stream-chunk, so the sample is a sample. The 1,347/24 h count and the per-replica split come from a range query with `limit=5000` and are lower bounds on the true count. I did not run `EXPLAIN QUERY PLAN` against a live DB or measure the query in isolation.
- **Proposal 3's rate is exact; its attribution to the help text is my reading.** The 90 lines, 12 in 24 h and the 41 distinct timestamp×target pairs are log reads; the live 400 is a reproduction I ran this session. The claim that the help text *caused* any particular instance is inference from the two today (both used a room id as its own parent, and the responder's trace in that thread shows the worker reasoning about "is this the room id or the message id").
- **CF8's CI findings are quoted from job logs, not reproduced.** Twenty-odd `Test Appserver` job logs and four Playwright logs were fetched and each test's duration read from the raw output; four `next` runs and fourteen branch runs were compared directly. I ran no `bun test` and no Playwright locally, and I did not open the uploaded traces or `test-failed-1.png`.
