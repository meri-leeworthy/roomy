### 2. The scheduled tick has been posting its own model-429 error text as its answer — the loop has reported nothing real for ~2 days

- **Evidence:** Meri's Forest `#coordination`, last 100 messages. Classified by hand: from **2026-09-16T16:12:14Z to 2026-09-18T06:01:43Z, 19 consecutive messages** (2-hour cadence, no gaps) are a 2,061-char dump of raw `omp` NDJSON, every one of them containing:
  ```
  "stopReason":"error","errorStatus":429,
  "errorMessage":"HTTP 429 from https://ollama.com/api/chat
   you (merileeworthy) have reached your weekly usage limit, upgrade for higher limits:
   https://ollama.com/upgrade or add usage credits: https://ollama.com/settings"
  "duration":~28,500
  ```
  The tick's *prompt* still posts normally (`… SCHEDULED SELF-CHECK — 2026-09-18T06:01:02Z`, 14,620 chars); the tick's *answer* is the error dump. Before 2026-09-16T14:29Z the same slot contained real status reports ("**14:00Z tick — fleet clean, all six audits `ok`**"). The 2026-09-18T04:02:23Z one contains the error **three times**.
- **Two separate defects, and the second is the interesting one.**
  (a) *Operational:* the account backing the fleet's model has been over its weekly usage limit since 2026-09-16 ~16:00Z. Nothing in the fleet can fix that — it needs Meri (upgrade or credits). Every tick since has burned ~28.5s and produced nothing.
  (b) *Code:* the failure is **published as an answer** rather than recorded as a failure. `packages/cli/src/omp.ts:191-196`: when `omp` exits 0 but produced no structured answer, the runner resolves with a **fallback made of the raw output tail** — `const fallback = (outTail.text.trim() || errTail.text.trim() || "").slice(-2000); resolve({ answer: fallback, … })`. `packages/cli/src/respond.ts:412` then sees a non-empty `answer`, so the "empty reply — not posting" guard never fires, and the error text is posted to the channel as the agent's reply. The guard that exists cannot trigger, because the fallback guarantees it doesn't.
- **Why now:** this is the loop's own failure mode, and it is invisible *by construction* — no ALERT token, no failed job, no missing message; the channel looks like it is being answered. It has been doing this every 2 hours for two days. It also silently degraded the fleet's coordination signal at exactly the moment Meri was asking for noise reduction (TASK-142).
- **Scope sketch:** two separable changes. (1) In `omp.ts`, distinguish "no structured answer *and* a non-zero/error terminal event in the stream" from "no structured answer but omp succeeded": on the former, reject so `respond.ts`'s existing per-job catch records `queue.finish(id, "failed", message)` and logs. Keep the raw-tail fallback only for the benign case it was written for. (2) Make that failure visible as a task-loop signal — the runner is the only place that observes it. Do **not** widen scope into retry/backoff policy for the model provider; a 429 here is a hard quota, not a transient.
- **Acceptance:** a unit test that drives `runOmp` with a terminal `errorStatus: 429` stream and asserts it rejects (fails pre-fix, since today it resolves with the raw tail); plus one observed tick after the fix that either posts a real answer or records a `failed` job with the 429 message and posts nothing to the channel.
- **Suggested priority:** **P1** — the coordinator is the thing that coordinates; two days of silent non-function is the highest-leverage defect on this list, and defect (b) is a five-line fix.
- **Not already tracked because:** TASK-145/146 are about socket-dead bridges and dispatch preconditions; TASK-148 is about instructions arriving between ticks. None covers "the tick's own answer is its error". Defect (a) is an account/ops fact nobody has recorded.

### 5. `vite:preloadError` is unhandled — a stale-deploy click dead-ends with no recovery

- **Evidence:** Loki `{service_name="roomy-app-lite"} |~ "dynamically imported module"` = **33 in 7d**, spread across the week (`09-14T23:14`, `09-15T03:17/05:22/07:36/09:06/12:05/18:55/19:06/19:09/19:38`, `09-16T00:34/06:17/13:07/18:22×2/18:37/20:27`, `09-17T02:55×3/14:39/20:37`, `09-18T00:47`), naming a different chunk each time (`nodes/23.B7E6DFpR.js`, `nodes/7.r9-5gS3U.js`, `nodes/4.Bw6MEJ26.js`, …). The app has **no handler for this failure**: a repo-wide grep for `preloadError`, `vite:preload` and `ChunkLoadError` across `packages/app-lite/src` and `packages/design/src` returns nothing, and `error-recovery.ts` explicitly does not cover it (its docstring: "we do NOT auto-reload on generic appserver XRPC errors"). Consequence: the navigation the user clicked simply does not happen, and the only recovery is a manual reload — which is exactly the case the module was written for ("In the installed PWA there is no way to manually reload"). The chunks themselves are served fine now (`https://roomy.space/_app/immutable/nodes/23.B7E6DFpR.js` → HTTP 200), so this is deploy skew, not a missing artefact.
- **Why now:** low volume (33/7d ≈ 5/day) but the failure is total for the affected user at that moment, and Roomy deploys many times a day — the appserver alone restarted 4 times in the last 24h. It is the one SPA failure whose standard remedy (`vite:preloadError` → reload) is a few lines and is already 90% implemented next door in `error-recovery.ts` (debounce, rate-limit, `MAX_RELOADS` budget).
- **Scope sketch:** route `window.addEventListener("vite:preloadError", …)` through the existing `scheduleAutoReload` budget in `error-recovery.ts` so a stale chunk reloads once and cannot loop. Do not add a new reload path — reuse the rate-limited one.
- **Acceptance:** a chunk-load failure after a deploy recovers with one automatic reload instead of a dead click; the `MAX_RELOADS`/`COOLDOWN_MS` limits still bound it.
- **Suggested priority:** **P3** — honest caveat: the evidence is a modest count of client-side errors, not a reproduction; I could not reproduce deploy skew on demand, so scope should be confirmed before implementing.
- **Not already tracked because:** TASK-111 covered `TokenRefreshError` invisibility (auth errors), which is a different class; nothing covers chunk/preload failures.
