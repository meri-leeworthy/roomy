### 2. Every sync reconnect replays the same ~100 events into failed Discord sends, and the error names neither the channel nor the status

- **Evidence.** In the 24 h window the bridge logged **3,035** lines, **217** of them `level=error`, and **164 of those are one signature**: `Event callback failed for did:plc:czuof2keyw33z27xk5264olj idx N: Failed to send request to discord.` They come in exactly two bursts, each immediately after a socket reopen — `Connection closed … code=1006` at **22:00:57** and **06:03:09** (`10-23`), `Connection status … reconnecting`/`open` seconds later, then 80 and 82 failures inside the same second. **The two bursts cover the same index range**: `9254–9356` at 22:00Z and `9254–9359` at 06:03Z, 82 distinct indices, so the reconnect replays a backlog that was already replayed eight hours earlier.
  **What the replay does not dedupe.** Outgoing Roomy→Discord messages are deduped by mapping (`packages/discord-bridge/src/services/roomy-event-router.ts:716`), and the mapping is written **only after a send succeeds** (`:524`). So a message whose send failed is retried on the next replay — which is why the same eight message ids appear in both bursts: `Failed to bridge Roomy message 01M5NCG1WJ3W9JHRCJ80T5NEKG to Discord channel 1446965765797580893` at **22:00:57** and again at **06:03:17**, with six siblings in the same pair. On failure the router logs `err` and rethrows (`:869-875`), the gateway catches it, logs the second line and records the index (`packages/discord-bridge/src/roomy/live-gateway.ts:310-322`), then **advances the cursor anyway** (`:329`), so the only thing that ever retries these is the next reconnect.
  **The error is unattributable.** `Failed to send request to discord.` is discordeno's generic wrap of a failed fetch; the logged `error` object carries a stack and no status, no body, no channel id beyond the message text. There is also one `Failed to create webhook for channel 1446969440746078259` in the same window, twice, which is the other reason a whole channel's sends would fail in a row.
- **Why now.** 76% of the bridge's errors in 24 h are this one loop, in one space, and the messages it touches never reach Discord. Two candidate causes are consistent with the evidence and cannot be told apart from the logs: Discord rate-limiting the burst (80 webhook POSTs inside one second after a replay), or a channel/webhook the bot can no longer write to. The fix differs completely, which is why the first deliverable is the attribution.
- **Scope sketch.** (a) Capture and log the HTTP status plus Discord's JSON body on a failed send; put the channel id and the Roomy message id in the same line rather than in two. (b) Do not re-drive a replay blindly: on a `404`/`403` for a channel or webhook, prune or park the mapping and log one line instead of 82; on a `429`, honour `retry_after` and park the event in the same durable queue `#473` built for the Discord→Roomy direction instead of losing it. (c) Make the replay start from the *persisted* cursor for every new connection, which is what `live-gateway.ts:182-208` intends — the identical index range across two reconnects says the intent is not being met.
- **Acceptance.** A reconnect with a backlog produces at most one log line per distinct failure reason; a forcibly deleted channel produces one pruned-mapping line and no repeated send attempts; and the same index range does not appear in two consecutive reconnects.
- **Suggested priority:** **P2** — messages are silently lost and the retry loop is self-sustaining, but it is confined to one bridged space today.
- **Not already tracked because.** `TASK-393`/`#528` instruments socket drops (why the socket closed, what reconnects recovered), not what a replay does on the far side. `#473` (merged, undeployed) is the Discord→Roomy send budget and re-offer queue. `#497` is message classes, `#503` is unmapped channels. Nothing covers Roomy→Discord failure attribution or replay dedupe.

## Limits of the evidence

- **Proposal 1 is a read of the CI logs, not a repro.** I did not run `bun test --isolate` locally, so I cannot say which worker leaks or whether the two crash points share a cause beyond the panic text. The correlation with RSS is strong in one case (11.96 GB) and absent in the other (5.38 GB), and the "Bun bug, not your code" line is Bun's own claim, not a finding.
- **Proposal 2's mechanism is inferred, not observed.** The log proves the replay (identical index ranges 9254–9356/9254–9359 across two reconnects), the send failures, and that the same eight message ids fail twice; the *cause* of `Failed to send request to discord.` is not in the log at all. Rate limiting, a dead webhook and a permission loss all fit, and the first fix — logging the status — is what would distinguish them. I also read the deployed build's behaviour off the logs while reading the source of `next`, which differ (`#497`'s line format is one visible difference).
- **The 403 rooms' space and caller are unknown.** Tempo carries `roomy.room_id` but the appserver's failure lines carry neither the caller nor the space, so the cluster is counted and located but not attributed. The same is true of the 25-character ULID: one client, unidentified.
- **`db-slow` counts statements, not requests, and its threshold is not stated in the log line.** Per-build rate comparisons are only meaningful within a build's own coverage window (1.3 h for `080b95dd`, 12.3 h for `5a205c0f`, 10.3 h for `be48786a`), which is how they are quoted.
- **CF3's 130 messages are counted, but the class is inferred.** The deployed bridge does not print `messageShape`, so "these are poll/component/Lottie messages that `#497` would render" is an inference from the guard's conditions plus the count, not a measurement.
- **The queue is read from the embedded snapshot**, which is measurably behind reality (three shipped entries, one unexplained mirror root) — anything dispatched or closed after it was pasted is invisible here, and Meri's Forest `#tasks` is not readable from a non-member account.
- **No test suite, build or browser run was executed.** Verification was Loki/Mimir/Tempo HTTP reads, the appserver's health endpoints, the GitHub REST API including two failing job logs, `git` reads on the audited worktree, and arithmetic over the retrieved corpora.
