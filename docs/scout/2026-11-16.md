## Proposals (ranked)

### 1. A Discord message delete took the bridge down for three days, because the cursor write that follows each frame cannot fail safely

- **Evidence:** `discord-bridge` has no log line since
  `2026-11-13T14:56:22.826Z` — 64 h 11 m — and the last one is
  `scope=live-roomy`, `Error processing stream frame for
  did:plc:ivppxz3o6zpkzfypl3mf7636`, `SQLiteError: database is locked`,
  `at setSpaceCursor (/app/dist/index.js:1045:50)`. On `origin/next`:
  `packages/discord-bridge/src/roomy/live-gateway.ts:329` calls
  `this.#repo.setSpaceCursor(spaceDid, data.cursor)` **after** the per-event
  `try/catch` (`:304-322`) that absorbs every other failure in the frame;
  `packages/discord-bridge/src/db/repository.ts:863` is a synchronous
  `INSERT … ON CONFLICT DO UPDATE`; the connection sets
  `PRAGMA journal_mode = WAL` and `PRAGMA busy_timeout = 3000`
  (`repository.ts:193-196`), so the lock outlasted three seconds — the
  `database is locked` at 14:52-14:56 was already being reported by the
  capacity sweep (`getMemberCount failed … Failed to send request to discord`)
  four minutes before the crash. There is no `unhandledRejection`/
  `uncaughtException` handler in the bridge (`index.ts:514-515` installs only
  SIGINT/SIGTERM), so the rejection exits the process.
- **Why now:** this is the root cause of the outage TASK-488 records, and the
  fix that is waiting in review (`#635`) does not touch it. Restarting the dead
  container makes the bridge live; it does not stop the next locked write from
  killing it again, and the events it will replay are the same delete-heavy
  burst that produced the lock.
- **Scope sketch:** make cursor persistence non-fatal. Retry
  `SQLITE_BUSY`/`SQLITE_LOCKED` (bounded, short backoff, log on exhaustion),
  and on exhaustion **skip the write and continue** — the code already
  documents at-least-once delivery (`live-gateway.ts:325-328`), so a skipped
  cursor only re-delivers. Install a fatal-cause handler (the appserver's
  `fatal.ts` is the shape) so any future process-ending error is recorded with
  kind and stack before exit. No schema change, no cursor-semantics change.
- **Acceptance:** a test that makes `setSpaceCursor` throw `SQLITE_BUSY` on the
  first attempt and succeeds on retry — the frame completes, the cursor lands,
  the process is alive; a second test where every retry fails — the frame is
  logged and the process still serves the next frame. Plus a test that an
  installed fatal handler records a rejected frame instead of dying silently.
- **Suggested priority:** P1 (currently the only reason both bridge directions
  are dead, and the merge in review does not address it).
- **Not already tracked because:** the crash cause was recorded in coordination
  on 2026-11-14 and TASK-487/`#635` was dispatched from it — but that task is
  liveness reporting plus a container `HEALTHCHECK`, and TASK-488 is the outage
  record. Neither changes the throw site or makes a failed cursor write
  survivable, and both would be satisfied by a restarted container that dies the
  same way next week.

### 2. A database request that times out kills the appserver, and the 25-hour stall is what makes it time out

> **Status at publication: this was dispatched as TASK-490 at 2026-11-16T07:05Z,
> minutes after this record's queue snapshot was taken.** It is kept here because
> the dispatch record and this entry answer different questions: the entry below
> adds the stall-to-fatal correlation (18 s apart, 9th occurrence) and the
> candidate leak sites, which the task text does not carry. If TASK-490 is
> accepted as written, treat this as its evidence appendix rather than new work.

- **Evidence:** `2026-11-16T03:12:41.123Z`: `[fatal] unhandledRejection:
  exiting 1`, `error.message = "Request timed out: run"`, stack
  `at <anonymous> (/app/packages/appserver/src/db/asyncDatabase.ts:264:18)`,
  `pid 30`, `uptime_seconds 1083633`, `build_id f4413dcf`. Fifteen seconds
  earlier, in the same window: `db-slow` `space-6` 2,020 ms self
  (03:12:23.049Z) and `global` 7,715 ms self (03:12:29.060Z) — the ninth
  instance of the 25-hour stall, 25 h 00 m 00 s after the eighth. The timeout is
  30 s (`asyncDatabase.ts:126`), the rejection is raised at
  `asyncDatabase.ts:262-266`, and `packages/appserver/src/fatal.ts:102-146`
  turns any unhandled rejection into `process.exit(1)` by design
  (`FATAL_EXIT_CODE`, `fatal.ts:42`). `send()` marks its own promise handled
  (`asyncDatabase.ts:283-289`), so the leaked rejection comes from a derived
  chain: the only fire-and-forget chain in the appserver with no rejection
  handler is `packages/appserver/src/sync/handler.ts:1159`
  (`void this.#sendStreamEvents(...).then(...)`), and the six
  `void this.#deliverRoomFrame(...)` / `void this.#sendUnreadFrame(...)` sites
  (`:619`, `:710`, `:726`, `:749`, `:886`, `:902`, `:933`) have the same shape.
  The fatal record names the rejecting statement but **not the caller that
  dropped it**, so it cannot be attributed after the fact from production.
- **Why now:** one unhandled rejection is one process death. The trigger —
  a statement exceeding 30 s during the 25-hour stall — is a recurring
  condition, not an exotic failure: 9 statements exceeded 3 s in the last 24 h
  and 61 in the last 7 days. On 2026-11-11 the same timeout was *handled* (two
  `sendEvents` requests returned 500s); today the same class took the process
  down, and only re-materialisation cost made it a 14-second outage.
- **Scope sketch:** give every fire-and-forget DB chain an explicit owner — a
  `.catch()` that logs the failure with the operation name, starting with
  `sync/handler.ts:1159` and the `#deliver*` sites — and have the DB link
  record the awaiting caller (a `route`/`op` label carried into the timeout
  error) so a fatal names the path, not just `run`. Do not change the fatal
  policy: process death on a genuinely unknown rejection is correct, and the
  platform restart now works.
- **Acceptance:** a test that rejects a `run` on each fire-and-forget path and
  asserts the process stays up and the failure is logged once with its
  operation name; a test that a timed-out request's error names the caller, not
  only the statement type. Reproduce-or-not the crash by forcing a 30 s
  statement on a `#deliverRoomFrame` path (report only if it cannot be forced
  without production load).
- **Suggested priority:** P1 — it is a production process death on a condition
  that already repeats daily-scale, and the instrument that would have named it
  (CF26/`#633`, CF21/`#598`) is not deployed.
- **Not already tracked because:** TASK-462 asks why production stopped in
  November (a platform-level answer), TASK-476/`#617` bounds memory,
  TASK-481/`#625` instruments the stall; none of them is about a timeout
  becoming a fatal exit, and no open PR adds a rejection handler.

## Considered and rejected

- **Raising `busy_timeout` instead of handling the error.** A longer timeout
  only widens the window in which a lock must be held before the process dies;
  the write still throws, and the throw is still outside the frame's
  `try/catch`. Rejected in favour of proposal 1's retry-and-continue.
- **Adding a fatal handler alone to the bridge.** It converts a silent death
  into a logged death plus (with `#635`'s `HEALTHCHECK`) a container restart.
  Useful, already covered by `#635`, and insufficient on its own — the process
  would still drop frames every time a write locked.
- **The 12-hour production outage of 2026-11-03.** TASK-462 owns it and its
  cause is a platform question; today's event adds a fatal record but not an
  answer for November, so it is not a new proposal.
- **An "appserver restarted" alert.** CF2 covers the missing alerting layer;
  today's restart was self-healing in 14 s, so a per-restart alert would page on
  a system that recovered.
- **The client's 57 % 401 rate as a new proposal.** It is CF12/CF17, both with
  open PRs; today's change is magnitude, not class.
- **`Could not resolve handle` (CF31).** Not re-measured this tick; the restart
  truncated the counters before the day's window could be read.
- **Seven `unstable` PRs on Netlify checks (CF18).** The checks build a
  `netlify.toml` whose `ignore = "true"` deliberately skips them; not a code
  signal, and not re-measured today.
- **A task for the search backfill's round-robin.** Measured again and still
