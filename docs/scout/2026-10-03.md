### 1. The OAuth `state` parameter is the return URL — a one-character, guessable CSRF token that also breaks login on strict PDSs

- **Evidence.** User report, Muni Town `#todos`, 2026-10-02T08:33:13Z (FenTiger):

  and 08:42:02Z, the same reporter:

  Source, on the audited ref `1c4247a2`:
  - `packages/app-lite/src/lib/auth.svelte.ts:110-112` — `currentReturnUrl()` returns `location.pathname + location.search + location.hash`.
  - `:378` `const returnUrl = currentReturnUrl();` → `:387` `state: returnUrl` (the `login()` path) and `:451` → `:460` (the Tauri path).
  - `packages/sdk/src/browser/oauth-options.ts` `authorizeRequestOptions` — `if (opts.state) out.state = opts.state;`, i.e. only set values are forwarded, so `/` is passed through and the default is never reached.
  - `/home/exedev/roomy/node_modules/.pnpm/@happyview+oauth-client-browser@1.4.4/.../dist/index.js:96` — `const state = options?.state ?? randomHex(16);`, the fallback that would have been correct.

- **Why now.** It is simultaneously (a) a live security weakness in the CSRF binding of the sign-in flow, self-reported by a user who understood it, and (b) a hard login failure on any PDS that enforces OAuth's state-entropy guidance — which is the *correct* behaviour, so this will keep taking out self-hosted users. - **Scope sketch.** Stop overloading `state`. Revisit `authorizeRequestOptions`'s contract and its test, which currently pin "the caller's `state` is forwarded verbatim" as correct. Remove the now-dead `returnUrl`-through-`state` plumbing on both the `login()` and `loginWithAppPassword()` paths.
- **Acceptance.** A network-level assertion (unit test on `authorizeRequestOptions`, or a Playwright test asserting the `authorize` URL) that the `state` sent to the PDS is ≥8 chars of random data and is not the page path; and a test that a return URL survives the round-trip via `sessionStorage` with the page landing back where it started. - **Why now.** The comment's claim that it self-heals is the part worth doubting. `recordScopeGrant` is what persists the raw granted scope so a returning user's next `signIn()` can request it back without re-prompting (`reconcileScope(stored)`, `scopes.ts`); if the record never lands, the next login reconciles against an *absent* grant and silently falls back to `base` — the same silent-downgrade class as yesterday's proposal 7, and it is the mechanism behind the "you have to log in again and lost my settings" complaints. Eight a day is not noise when the consequence is silent and the failure is a `console.warn` nobody reads.
- **Scope sketch.** Decide the intended behaviour, then encode it: either (a) treat a `Missing required scope` on `recordScopeGrant` as expected for sessions minted before the token existed, and make the *consequence* explicit — a one-time, user-visible "your session predates this permission; sign in again to restore your settings" on the access-settings page rather than a swallowed warn; or (b) if the grant genuinely does self-heal, prove it: a test that a login whose first `recordScopeGrant` fails still ends with the wider tier stored. Do not simply raise the log level.
- **Acceptance.** Either the warn is replaced by a path with an observable user-facing outcome, or a test demonstrates the self-heal the comment claims (fail the first `recordScopeGrant`, assert the granted tier is present after the next login).
- **Suggested priority:** **P2** — thin per-day counts, but a silent, still-firing loss of stored permission state.
