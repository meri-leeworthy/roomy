## Proposals (ranked)

### 1. Two appserver processes publish under one set of metric labels, so every rate, quantile and the documented restart alert is wrong

- **Evidence** (Mimir, sampled at 15 s over ten minutes; live `/metrics` as the
  authority):
  - `roomy_process_boot_timestamp_seconds{env="production"}` alternates between
    **2026-11-03T14:12:10.654** and **2026-11-05T06:27:38.627**.
  - `roomy_process_rss_bytes` alternates **~1.08 GB** / **~404 MB**
    (min_over_time over 1 h: 383 MiB; max: 1,040 MiB).
  - `roomy_db_open_space_dbs` alternates **100** / **1**.
  - `roomy_cache_size` alternates **374** / **9**.
  - `roomy_xrpc_requests_total{endpoint="/xrpc/space.roomy.space.getMetadata",status="200"}`
    alternates **43,907** / **7**.
  - The live endpoint on `api.roomy.space/metrics` reports the first value in
    every pair (43,905 at 07:0xZ, RSS 1,077,219,328, cache hits 13,114), so the
    second process is *not* the one serving the public edge.
  - Consequence, measured: `changes(roomy_process_boot_timestamp_seconds[1h])`
    = **119** — the alert documented at `deploy/alloy/README.md:209` fires every
    hour, permanently. `increase(roomy_cache_hits_total[1h])` = **786,193**
    against 13,114 hits since boot — a **60×** overstatement that no panel can
    survive.
  - Cause: `prometheus.scrape "appserver"` has exactly one target —
    `APPSERVER_METRICS_URL` as a single `host:port`
    (`deploy/alloy/config.alloy:153-157`, `deploy/alloy/README.md:29`) — and
    nothing labels the scrape with the replica that answered. Logs already carry
    Railway replica identity (`deploy/alloy/README.md:248`); metrics do not, so
    two processes collapse into one series set and alternate per scrape.
- **Why now:** every production number the loop has quoted for at least seven
  days is a blend — `min_over_time(roomy_process_rss_bytes[1h])` has read ~400 MB
  every hour since 2026-10-31T07Z, so this is not new today, it is newly
  visible. It silently invalidates the restart alert, the cache-hit-rate panel,
  and any rate-based alert that will ever be written on this service.
- **Scope sketch:** give the scrape a per-replica identity — add a
  `RAILWAY_REPLICA_ID`-derived label to `/metrics` (or a second relabel target
  per replica, or scrape only the serving replica) — then re-derive the two
  documented alerting rules against a series set that has one process in it.
  Update `deploy/alloy/README.md` to say that the target must be a single
  replica.
- **Acceptance:** `count(roomy_process_boot_timestamp_seconds{env="production"})`
  is 1 for a single-replica service; `changes(...[1h])` reads 0 on a healthy
  hour and >0 within one scrape of a real restart; a cache-hit-rate panel and
  `increase(roomy_xrpc_requests_total[1h])` agree with values read from the
  live `/metrics` endpoint within the scrape interval.
- **Suggested priority:** P1
- **Not already tracked because:** TASK-461 measures statement time; TASK-458
  closes the endpoint; neither touches label identity. No queue entry, no PR.

- **Scope sketch:** split `getActivityFeed.select` into per-space query,
  profile hydration, embed hydration, reactions and read-state spans, take a
  staging p50/p95 over a fixed load, and then fix the step that owns the time.
  Do not change the query or the indexes until one of them is named.
- **Acceptance:** a staging trace of a 5-space, 100-item page names the dominant

  the regression signal.
- **Suggested priority:** P2
