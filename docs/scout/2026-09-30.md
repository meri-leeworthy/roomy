### 2. The Discord bridge silently discards ~165 messages a day — any message whose only content is an embed

- **Evidence.** `discord-bridge` logs `Skipping message <id> in did:plc:qzie4v7qwnv3mzaflihrf56f: no content and no attachments` **165 times in the 24 h to 07:0xZ**, against 1, 7, 24, 775, 100, 104, 112, 100, 84 on 09-20…09-28 — i.e. a sustained floor of ~100/day, not a burst. The check is `packages/discord-bridge/src/services/message-ingestion.ts:235`: `if (!message.content && attachments.length === 0) { writeSkipRecord("empty_message", …); continue; }`. The message arrives with `embeds` already emptied at the normalizer — `packages/discord-bridge/src/discord/normalizers.ts:35`, `embeds: [], // services don't use embed content today` — and `grep -rn "\.embeds" packages/discord-bridge/src` outside tests and the fake-data generator returns nothing, so no code reads it. A Discord message whose entire payload is an embed (a pasted link's preview, a bot's card, a Tenor/Giphy result) therefore has empty `content`, no attachments, and is dropped before any Roomy event is created. `writeSkipRecord` no-ops unless `ROOMY_SKIP_LOG` is set, so the only trace is the log line.
- **Why now.** Unlike a rendering defect, this is **permanent, silent message loss on the busiest bridged space** — the same class as TASK-215/TASK-156 (`done`) but upstream of the send. Every affected message is indistinguishable, on the Roomy side, from one that was never posted. The bridge is the only path by which most Discord content reaches Roomy.
- **Scope sketch.** The minimal honest fix is not "render embeds" — it is to stop treating a message with embeds as empty. `normalizeMessage` should carry the embed's `url`/`title`/`description` through (the field already exists in the type — `discord/data.ts:126` declares `embeds?`), `buildAttachments` should emit a link/embed attachment for them, and the emptiness check at `:235` should consider embeds. Whether the resulting Roomy message *renders* a card is TASK-22's question and can follow separately. Add a test with an embed-only message asserting it produces an event.
- **Acceptance.** An embed-only Discord message produces a Roomy message; the `no content and no attachments` count for a channel carrying such traffic goes to 0, or every remaining occurrence is accompanied by a stated reason it is genuinely empty.
- **Suggested priority:** **P2** — silent, permanent, ~100–165/day, on a path nothing else covers.
- **Not already tracked because.** TASK-22 asks for *links with embeds* — it is about how a bridged URL renders on the Roomy side, and it presupposes the message arrives. Nothing in the queue covers the drop. (Recorded in the queue at P2; the discard is a second, distinct entry in the same area.)

## Limits of the evidence

- **Proposal 1's mechanism is not established — only its magnitude, onset and scope.** What is directly measured: per-route p95 for every route in the window (from the shipped histogram, not from log parsing), the flat/lower request rate, the unchanged cache hit rate, the 09-28T21:00Z step, the fact that no deploy or restart occurred at the step, and the fact that the two routes which do not touch the per-space pool are the two that did not degrade. I did **not** observe a request waiting on a specific worker: `roomy_pool_worker_pending` samples every 15 s and reads ~0, and the appserver logs no `spaceId` on the `xrpc` line, so I cannot attribute an individual slow request to a space or a worker. The hash collision (94.2% of writes on one of eight workers, and `#321` fixes exactly that) is a strong candidate and is the reason the proposal names it, but the 10–180× factor across *reads* on workers that are not `space-4` is not explained by it, and I am not claiming it is.
- **The previous scout's claim that the histogram cannot answer a per-route question is wrong, and I have re-derived the numbers from it.** `roomy_xrpc_request_duration_seconds_bucket` carries `endpoint` as the full path plus `method`; grouped `by (endpoint)` it yields exact per-route quantiles. The 09-29 report grouped `by (nsid)`, a label that does not exist. Any conclusion in that report resting on log-derived `duration_ms` counts should be re-read against the histogram, which is what proposals 1 and 4 are for.
- **The previous scout's proposal 2, as written, mis-states its own mechanism.** It says the cursor "has already been advanced" when the send fails. On every ref I checked (`95616896`, `1023f9bd`, `b8ef052c`) `repo.setChannelCursor(…)` at `message-ingestion.ts:314` is *inside* the `try`, after `await roomy.sendEvent(...)` — so a throw skips it. Its conclusion is nonetheless correct, and `#320`'s analysis says why: live ingestion is gateway-push driven and offers each message exactly once, and the cursor is read only by `services/backfill.ts`, so nothing recovers a live drop. The claim was wrong in detail and right in effect; the durability fix is `#320`, open and green.
- **Proposal 1's user-facing numbers come from two different instruments and are not comparable to each other.** The 162 × `>20 s` `sendEvents` count is log-derived (parsed `duration_ms` on the `POST … sendEvents` line); the p95/le tables are histogram-derived. Both are exact for what they measure, but a log line and a bucket are not the same measurement and I have not reconciled them beyond confirming both show the same onset hour.
- **Proposal 2's origin is unidentified.** The XRPC side is unambiguous (111 + 76 over 4 days, 51% of `getSpaceSummary`'s traffic, a matching client-side 404 count). I did not find the stored field the two DIDs come from: `roomy-app-lite` logs the failure but not the referrer, and the two DIDs do not appear in any `getSpaces` response I sampled.
