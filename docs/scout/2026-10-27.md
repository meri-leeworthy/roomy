### 2. A channel that cannot have a webhook is retried once per message, in bursts, and those messages are dropped

- **Evidence.** `discord-bridge`, 24 h: **129** `Failed to create webhook for
  channel <id>` (level=error) across **7** channels — 43 on `1447012668199407776`,
  29 on `1508167369187393638`, 28 on `1446965994643001497`, 17 on
  `1472284471805083678`, plus 12 across three more. **Burst shape:** 7 attempts
  on one channel inside 2026-10-26T14:01:56Z, 6 inside 20:21:09Z, four apiece in
  three other single seconds — the same request repeated concurrently, not
  retried over time. Trajectory by 24 h window ending 07:00Z: **0, 0, 0, 2, 24,
  31, 129**. Each failure is a dropped Roomy→Discord message: the paired line is
  `Failed to bridge Roomy message <id> to Discord channel <id>`, **210** in 24 h.
  The code has neither an in-flight promise nor a negative cache:
  `LiveWebhookManager.ensureWebhook`
  (`packages/discord-bridge/src/discord/live-webhook-manager.ts:22-62`) checks
  the persisted token, then calls `createWebhook` on every invocation and throws;
  the five call sites in `services/roomy-event-router.ts` (`:508`, `:848`,
  `:1116`, `:1201`, `:1480`) each invoke it per event.
- **Why now.** The class is compounding (2 → 129 in four days) and it costs
  messages in bridged spaces, silently — nothing surfaces the drop to the Roomy
  side. The logged cause is `Failed to send request to discord`, a transport
  wrapper that names no Discord status, so even a correct backoff would not say
  *why* a channel refuses. That is a second, cheap fix in the same file.
- **Scope sketch.** In `LiveWebhookManager`: one in-flight promise per channel
  (concurrent callers share it), a per-channel cooldown after a failure so the
  next message does not re-attempt immediately, and a log field carrying the
  Discord status/code where the transport layer surfaces one. Where the failure
  is deterministic (missing permission, channel type that cannot hold a webhook),
  record it durably the way `#503` does for unmappable channel types, so the skip
  is countable rather than a repeated error line.
- **Acceptance.** A unit test that fails pre-fix: two concurrent `ensureWebhook`
  calls for one failing channel produce one `createWebhook` attempt; and a
  channel in cooldown produces zero attempts until the cooldown expires. In
  production, the per-second burst disappears from the log and the daily count
  falls to the number of distinct failing channels.
- **Suggested priority:** **P2**.
- **Not already tracked because.** `#541` (TASK-418) makes a *refused send*
  terminal; `#503` (TASK-385) gives forum/media channels a room. Neither touches
  `ensureWebhook`, and the transport-level failure here is retryable by
  classification, so it would stay pending under `#541` and keep repeating.

### 3. A rendered Web Tile never receives its title or icon, and every render logs `No shuttle for ID undefined`

- **Evidence.** `roomy-app-lite` telemetry: **22** exception lines
  `console.error: No shuttle for ID undefined` in 7 d, **18** of them in the last
  24 h, from two browser sessions, all on three rooms in one space (e.g.
  `https://roomy.space/did:plc:drzgt2m6lmcel62gfbzjeap3/01M45C7NZ535M2S41VMC9Z0K0T`),
  at 22:48–22:53Z on 2026-10-26. Mechanism, from the two sources side by side:
  `TileEmbed.svelte:228` registers its own iframe
  (`const id = m.registerShuttleFrame(ifr, t)`) and addresses the shuttle with
  that local `id`, while the tile object's own `#shuttleId`
  (`@dasl/tile-loader@2.0.0` `src/index.ts:141`) is assigned only by
  `Tile.attachIframe` (`:223-225`), which `TileEmbed` never calls. The
  mothership dispatches `load` on the tile when the shuttle reports ready, and
  the tile's own listener then calls
  `sendToShuttle(this.#shuttleId!, SND_SET_TITLE …)` (`:151`, `:158`) with
  `undefined` — the library logs it (`:101`) and returns, so the shuttle is
  never told the tile's title or icon.
- **Why now.** This is the first production rendering of the tile path (`#543`
  and `#556` are deployed; `#558` widens it to every resolved link), and the
  defect is in the shared render component, so it multiplies with `#558` rather
  than staying at 22 lines. The user-visible half is quiet — a frame titled "Web
  Tile" with no icon — which is exactly the kind of thing that survives a
  release if nobody records it now.
- **Scope sketch.** Give the tile the same identity the embed registers: have
  `TileEmbed` hand its iframe to `t.attachIframe(ifr)` (which registers and
  hooks `load` in one place) instead of calling `registerShuttleFrame` itself,
  and use the tile's shuttle id for the payload delivery; or, if the component
  must own the frame, expose a way to set the tile's shuttle id so the built-in
  title/icon handoff works. Then assert the handoff.
- **Acceptance.** A component test that fails pre-fix: mounting `TileEmbed` with
  a loaded tile and dispatching the mothership's worker-ready event delivers
  `SND_SET_TITLE` with the manifest's name and produces no `No shuttle` line. In
  production, the line disappears from `roomy-app-lite` telemetry.
- **Suggested priority:** **P3**.
- **Not already tracked because.** No open task or PR names `TileEmbed`,
  `attachIframe`, or the shuttle title handoff; `TASK-431` (`#558`) is the
  resolver half and does not touch this component.
