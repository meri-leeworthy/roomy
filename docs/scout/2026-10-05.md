### 1. The OAuth `state` parameter is still the return URL: it re-broke self-hosted sign-in today, and the `#362` report of it was never actioned

- **Evidence.** Two independent user reports, five days apart, both naming the same value. FenTiger, Muni Town `#todos`, 2026-10-02T08:33:13Z:
  > `PAR request failed: 400 {"error":"invalid_state",… "Request parameter 'state' must be at least be 8 characters long…"}` … "its state parameter is set to `/`, which my OAuth server is rejecting"

  and the same reporter again, **2026-10-03T07:50:25Z**, after Meri's "fixed!" at 10-02T09:09Z:
  > "…but not today 🙁 I'm seeing the same thing again: the state parameter in the PAR request is set to `/`."

  Source, on the audited ref `746eb5b0`:
  - `packages/app-lite/src/lib/auth.svelte.ts:110-112` — `currentReturnUrl()` returns `location.pathname + location.search + location.hash`.
  - `:378` `const returnUrl = currentReturnUrl();` → `:387` `state: returnUrl` (the `login()` path); `:451` → `:460` (the Tauri path); `:459` → the scope-expansion path.
  - `packages/sdk/src/browser/oauth-options.ts` `authorizeRequestOptions` — `if (opts.state) out.state = opts.state;`, forwarded from `oauth.ts:740` and `:746` into `client.signIn(handle, …)`. A set value is passed through, so the client library's own `?? randomHex(16)` fallback never runs.
  - `git log -S "state: returnUrl" -- packages/app-lite/src/lib/auth.svelte.ts` → introduced by `32060f13` (2026-09-29); no later commit modifies the line. **Nothing on `next` fixes it.**
  - The test that pins the current behaviour as correct: `packages/sdk/src/browser/oauth-options.test.ts`, "forwards state when set" → `expect(opts).toEqual({ state: "/space/1" })`.
- **Why now.** It is simultaneously a live CSRF weakness (the user diagnosed the attack himself: "since it's very easy for an attacker to guess the state right now") and a hard sign-in failure on any PDS enforcing OAuth's state-entropy guidance — which is correct behaviour and will keep taking out self-hosted users. It also has a **sharper consequence this run than last**: `state` is the transport for the return URL, and `#342`'s Semble personal-collection action is the first feature to run *through* the consent round-trip, so a broken/guessed `state` is now on the path that gates writes to a user's own repo.
- **Scope sketch.** Stop overloading `state`. Keep the return URL in `sessionStorage` (written before `signIn`, read after the callback) and let the OAuth client generate its own 16-byte random `state`; `safeReturnUrl` (`:123-127`) stays as defence-in-depth for whatever comes back, but it must no longer be the *transport*. Remove the now-dead `returnUrl`-through-`state` plumbing on all three paths (`login()`, `requestScopeExpansion()`, `tauriLogin()`). Revisit `authorizeRequestOptions`'s contract and its test, which currently pin "the caller's `state` is forwarded verbatim" as correct.
- **Acceptance.** A network-level assertion (unit test on `authorizeRequestOptions`, or a Playwright test reading the `authorize` URL) that the `state` sent to the PDS is ≥8 chars of random data and is not the page path; and a test that a return URL survives the round-trip via `sessionStorage` with the page landing back where it started. Both must fail on the current code.
- **Suggested priority:** **P1** — an auth-flow security weakness plus a reproducible sign-in failure, user-reported twice.
- **Not already tracked because.** TASK-16 ("Token was not issued to this client") and TASK-19 (intermittent post-login auth errors) are different failures. No open task mentions `state`, CSRF, or the return-URL round-trip. This proposal was first raised in `#362` on 10-03 and is re-raised here because **the PR that carried it is still open, the defect is still on `next`, and it re-broke sign-in for the reporter today.**

### 3. An empty cache store reports itself as corrupt, 68 times in three days — the read path warns on an absent snapshot instead of a damaged one

- **Evidence.** Production `roomy-app-lite` telemetry: **68 × `cache: snapshot is not a valid snapshot object; discarding`** (32 in the last 24 h, all 68 in the last 3 d), a `level=warn` on the client, across Chrome/Firefox/Brave/Safari and both desktop and Android. Against 104 authenticated-session markers in the same window, that is a **double-digit percentage of session starts**.

  The message is emitted for a **fresh install as well as a corrupt store**: `packages/sdk/src/cache/persister.ts:206-210` calls `asSnapshot(raw)` and reports the corruption diagnostic whenever it is `undefined`, and `asSnapshot` returns `undefined` for `raw === undefined` (`:245`) — which is what `indexeddb-persister.ts:105-106` returns for a key that has never been written (`store.get(IDB_KEY)` → `undefined`), and what `localstorage-persister.ts:75-77` returns when `getItem` is `null`.

  **Reproduced locally on `746eb5b0`** (throwaway spec, since deleted; `packages/sdk` vitest):
  ```
  ✓ readSnapshot(undefined) → [] and reports "cache: snapshot is not a valid snapshot object; discarding"
  ✓ createSnapshotPersister({read: async () => undefined}).load() → [] and reports the same message
  ```
  Both pass on the current code — i.e. the diagnostic fires on the empty store by construction, not by corruption.

- **Why now.** The first-run/empty case is the *common* one (new device, cleared storage, logout, a browser that evicted the DB), and it is currently indistinguishable in telemetry from a genuinely unreadable snapshot — which is the one case that would justify demoting a working IndexedDB to `localStorage` (`client.ts`'s `withFallback`) and would be worth chasing. A signal that fires on the benign case is the `backlogStuck` class the previous report retired: it cannot be used to find the real one. The fix is a branch, not an investigation.
- **Scope sketch.** Distinguish absence from malformation in `readSnapshot`: return `[]` silently for an absent value, and keep the diagnostic for a value that is present but not a valid snapshot. Both persisters already return `undefined` for "never written"; nothing else needs to change. Optional and cheap: count the empty-store case under its own name so the corrupt-store rate becomes observable for the first time.
- **Acceptance.** A unit test that `readSnapshot(undefined, …)` reports nothing and returns `[]`, and that a present-but-malformed snapshot still reports. The existing `cache: snapshot has a different shape version` / `older than maxAge` messages show the intended shape.
- **Suggested priority:** **P2** — thin in user impact, but it is a one-branch fix to an observability signal the next run would otherwise have to re-derive, and the underlying state is misreported today.
- **Not already tracked because.** No open task mentions the persistent cache at all; `#343` (the feature) and `#360` are merged, and this is the first report to read the client cache diagnostics.
