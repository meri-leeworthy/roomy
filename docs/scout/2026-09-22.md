### 4. Anything over 100 messages is a hard 400 and there is no way to page deeper — the CLI has an uncapped `--limit` and no cursor

  Server cap: `handlers/space.roomy.room.getMessages.ts:36` `optionalInt(params, "limit", { min: 1, max: 100, default: 50 })`.
  CLI: `cli.ts:219` declares `.option("--limit <n>", "Max messages", "20")` with **no ceiling**, and `messages.ts:215-222` forwards it unclamped (`...(limit !== 20 ? { limit: String(limit) } : {})`). `read --help` lists only `--space`, `--room`, `--limit` — **no cursor option** — and `readMessages` never reads the response's `cursor`, so deep history is unreachable by any route.
  Production cost: `Param limit must be ≤ 100` = **80 lines / 7 d**; `got:` values are 101, 120, 150, 200 (×34), 300 (×12), 400 (×12). 21 fall in the 24 h ending today, 6 of which are my own probes at 07:00–07:18Z; the rest are other callers.
- **Why now.** This is the friction Meri named in `#meta` (2026-09-11T05:00Z: *"Agents don't know how to serve app-lite from their own machine and have to almost figure it out from first principles every time"*). The CLI is the agent fleet's read path; a reader that wants "the last 200 messages" gets a 400 and no pagination path, and the failure mode is indistinguishable from a permissions problem.
- **Scope sketch.** In `packages/cli`: clamp `--limit` to the server's cap (or loop on the returned `cursor` until the requested count is reached), and add `--cursor` so deep history is addressable. Mirror the same in any SDK fetch helper that passes a raw limit through. No server change — `max: 100` is a deliberate bound and should stay.
- **Acceptance.** `read --limit 250` returns 250 messages (via cursor iteration) rather than a 400, and no new `Param limit must be ≤ 100` lines appear for CLI-originated traffic.

### 5. Nothing re-fetches a profile that already has a row, so a name or avatar change never appears in message lists

- **Evidence.** The only paths that write the global `profiles` row are: event materialisation, the `getProfile` handler (a user's own profile page), and `hydrateMissingProfiles`. The last of these fetches **only DIDs that are missing or handle-less**: `profileStore.ts:190-200` builds `notInDb = dids.filter(d => !rows.some(r => r.did === d))` and `handleless = rows.filter(r => !r.handle)`, then hydrates `[...notInDb, ...handleless]` and nothing else. `filterMissing` (`profiles.ts:378-410`) likewise returns a DID only when it has no row at all, or a row whose `handle = 'handle.invalid'` and whose `updated_at` predates a 1 h cooldown. **A DID whose row exists with a stale `avatar` or `displayName` is never re-fetched.**
  Avatar URLs are stored as absolute CDN links (`app-lite/src/lib/utils.ts:36`, `https://cdn.bsky.app/img/feed_fullsize/plain/<did>/<cid>`), pinned to the CID at the time of the fetch.
  This is the defect a maintainer reported in `#todos`, 2026-09-15T16:24:54Z (Zicklag): *"Right now anybody who updates their avatar or profile won't get it updated in Roomy, and the avatar will expire and end up blank. We need to do something like this: [Discord link]"*.
- **Why now.** It is maintainer-confirmed, it is the identity layer of every message list and member list (`selectMessages.ts:175`, `members.ts`, `threadActivity.ts`, `userActiveThreads.ts` all read through `hydrateProfiles`), and it silently contradicts the read-after-write work that shipped for the *profile page* (TASK-118 / #198) — that fix made the page fresh and left every other surface stale.
- **Scope sketch.** The gate is the bug: `profiles.ts:401-406` re-fetches **only** rows whose `handle = 'handle.invalid'` and whose `updated_at` predates `STALE_HANDLE_COOLDOWN_MS`. Extend it to display fields — re-fetch rows older than a TTL regardless of handle state — through the same `getProfilesRoomyFirst` pipeline, so the negative cache and HappyView-first ordering are preserved. The second half is the avatar URL: resolve it at read time (or re-derive it from the profile) rather than pinning the CID at fetch time. Confirm the CDN/expiry behaviour with whoever owns it — I verified the *pinning*, not the expiry.
- **Acceptance.** Changing a display name or avatar on the PDS becomes visible in a message list within the TTL without visiting the profile page, and a row is not re-fetched more than once per TTL.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No open task mentions profile refresh, avatar staleness, or `filterMissing`. TASK-118 (#198) is the read-after-write fix for the single-profile read path and is closed.
- **Honest limit.** I verified that no refresh path exists and that avatar URLs are CID-pinned. I did **not** measure an avatar actually going blank — that half is Zicklag's report, carried as his claim.
