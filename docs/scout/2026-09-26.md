### 1. The room timeline's newest page silently omits every system message — thread-created notices, member-joined notices, and every other `sort_idx`-NULL row

- **Evidence.** User report, Roomy Space `#bugs`, 2026-09-25T14:07:45.885Z — *Zicklag*: *"Regression: it doesn't say "@so-and-so created a thread 'my thread'" anymore in the main channel when a thread is created."* Reported **after** the deployed app-lite build; still live.
  Code: `packages/appserver/src/queries/selectMessages.ts:187` filters `and (cc.entity is not null or forward_e.tail is not null)` and `:194` orders `by e.sort_idx desc limit N`. `entities.sort_idx` is written only by `setMessageSortIdxByTimestamp` / `…ByForward` / `…ByMove` / `…ByReorder`; the first returns immediately for any event that is not `createMessage.v0` (`materialization/sortIdx.ts:22`), so the system messages written by `createRoomLink` (`sdk/src/schema/events/link.ts:44`) and `joinSpace` (`sdk/src/schema/events/space.ts:69`) keep `sort_idx` NULL. SQLite sorts NULL last under `DESC`, so with any page limit those rows are beyond the page and unreachable by paging backward.
  Reproduction (throwaway script, per-space DB seeded from `schema-space.sql`, 80 ordinary messages then a `createRoomLink` last): 85 entities, 5 with NULL `sort_idx`; `selectMessages({kind:"room", limit:50})` → 50 messages, the link's system message **absent**, and still absent after paging with the returned cursor. Same script against `#292`'s head → **present in the first page**.
  Root cause commit: `bd12a85c` (2026-09-02, `#106`) replaced `order by coalesce(e.sort_idx, e.id) desc` with `order by e.sort_idx desc` for index reasons, on the stated assumption that "messages always have sort_idx set by the materializer" — which is true for `createMessage` and false for every system message.
- **Why now.** Two independent user-visible symptoms, one already reported by a user and one not yet: thread creation produces no in-channel notice, and a member joining produces no notice. `joinSpace` writes to the space's *oldest* channel (`space.ts:69` selects `order by entity limit 1`), so joining notices have been invisible since 09-02 as well.
- **Scope sketch.** `#292` is the fix and is already open: it orders and filters on the same key (`coalesce(sort_idx, id)`), adds the tie-break, and adds `idx_entities_room_sort_key (room, coalesce(sort_idx, id), id)` so the expression order still walks an index instead of a temp B-tree. No further code is needed. The work here is **the acceptance criterion**: `#292`'s own test covers "orders by sort_idx, not entity id"; it does not assert that a system message appears in the newest page, which is the thing a user reported.
- **Acceptance.** On a build carrying `#292`, a room containing a `createRoomLink` created after N > limit ordinary messages returns that system message in the first page; and on the deployed app, creating a thread in a channel with more than 50 messages shows the "created [thread]" notice without scrolling.
- **Suggested priority:** **P1** — a user-reported regression, reproduced, with a fix that is one merge away.
- **Not already tracked because.** TASK-218 is the paging bug and its acceptance is about bridged-message paging; the entry never mentions system messages, and nothing connects the user's thread-notice report to it.

### 6. A "no write access" rejection is a dead end in the composer — 69 refusals in 7 days, 96% of them on one room

- **Evidence.** `POST /xrpc/space.roomy.space.sendEvents failed: Caller does not have write access to this room` — **69 lines / 7d** and **38 / 24h**, thrown at `handlers/space.roomy.space.sendEvents.ts:183`. The client reports the same refusal: `XRPC space.roomy.space.sendEvents failed (403)` — **21 / 7d**, **10 / 24h**, of which **19 of 21** are one room, `did:plc:syizsigkwc4lqhmtrcmdfhho/01M2QW5A6Q3QQ8PWP07FZH3KRV`, across Mobile Safari, Firefox, Brave and Chrome, first seen 2026-09-25T09:06Z and newest 2026-09-25T22:05Z.
  Code: `ChatInputShell.svelte:260` renders *"You don't have permission to send messages in this channel."* when `canWrite === false` and the composer when `canWrite === true`; `canWrite` comes from `sidebarRoomInfo?.canWrite ?? roomQuery.data?.canWrite` (`routes/[space]/[room]/+page.svelte:237`). Every query in the app is `staleTime: Infinity` with `refetchOnWindowFocus: false` (`lib/client.ts:26`) — freshness is WS invalidation only — so a `canWrite` that was true when the sidebar loaded stays true until the appserver emits an invalidation for that room.
- **Why now.** A user pressing Send and receiving a bare "Message not sent: …" toast (the `catch` at `ChatInputArea.svelte:409` routes to `toast.error`) learns nothing about the permission change and has no way to recover; the composer keeps offering the action. The concentration on one room over two days makes this a repeated experience, not a race.
- **Scope sketch.** Make the refusal self-correcting at the point it is observed: in `ChatInputArea.handleSend`'s catch, detect the write-access XRPC error by `nsid`/status, invalidate that room's `getMetadata` and space `getMetadata` keys, and surface the same permission notice the composer shows for `canWrite === false` rather than a generic send failure. Do not change the access model.
- **Acceptance.** A send refused with `Caller does not have write access to this room` leaves the composer replaced by the permission notice without a reload; and the 403 count for a room whose grant changed is bounded by one per room per session.
- **Suggested priority:** **P3** — a rare configuration change with a confusing, non-recoverable surface. **Limit:** I can show the refusals, their concentration and the client gate, and the `staleTime: Infinity` + WS-only-invalidation design. I cannot show that the affected users saw an enabled composer — that needs the session state, which is not in the logs. The mechanism is a reading of the code, not a reproduction.
- **Not already tracked because.** No entry names send-path 403s; TASK-19/TASK-16 are different signatures.
