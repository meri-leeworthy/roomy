## Proposals (ranked)

### 1. Bridge capacity enforcement measures the **Roomy** member count and throws away the **Discord guild** count the bridge sends, so a large guild bridged into a small space is never over capacity

- **Evidence.** The bridge sends the guild's own member count on every capacity check: `XrpcMembershipClient.getSpaceMembership(spaceId, memberCount)` calls the NSID with `{ spaceId, memberCount: String(memberCount) }` (`discord-bridge/src/roomy/membership-client.ts:65-74`), and that count comes from Discord (`discord/member-count.ts:35-49` — cached members, else `getGuild(…, {counts: true}).approximateMemberCount`).
  The appserver **ignores the parameter**. `handlers/space.roomy.admin.getSpaceMembership.ts:95-96` reads only `spaceId` and derives its own count:
  ```ts
  const spaceDid = requireString(params, "spaceId");
  const memberCount = await memberCountOf(spaceDid);
  ```
  and `memberCountOf` (`:69-78`) is `select count(*) from edges where head = <spaceDid> and label in ('member','admin')` — the space's **Roomy** members.
  Bridged Discord participants are not Roomy members, which is the point: the bridge writes `did:discord:<snowflake>` authors on messages and profiles (`services/message-ingestion.ts:285`, `services/profile-sync.ts:68`), and nothing in the bridge emits a `joinSpace` or writes a `member` edge (`grep -rn "joinSpace\|'member'" packages/discord-bridge/src` → 0). A `member` edge is written by `space.joinSpace` and by the synthetic `admins` payload (`sdk/src/schema/events/space.ts:53,350`, `synthetic.ts:279-304`), neither of which the bridge produces.
  The contract everywhere else says the population is the guild: the handler's own docstring (*"once the bridged guild's member count exceeds 100"*), the constant's docstring (`BRIDGE_TOKEN_SPEND_THRESHOLD`, *"Guilds above this member count"*), and the owner DM (*"your server has N members … the M member capacity of the bridged space"*, `index.ts:110-111`).
  **Scale:** `admin.getSpaceMembership` is the **busiest route on the process** — **23,300 calls in 24 h** (7 d: 132,528, every one `200`) — ahead of `space.getMetadata` (12,939). That is **6.2×** what the documented design accounts for (13 bridged pairs × one forced check per 300 s ≈ 3,744/day; the only pair count the logs carry is the 13 in the fail-open summary, which names the grant-less subset). The 2-minute buckets show the shape but not the cause: over forty minutes they repeat `0, 26, 26, 104` (one bucket 28) — 2× and 8× the 13 pairs — so the endpoint is called several times per pair per cycle rather than once. The other sixteen `isEnabled` call sites (`message-ingestion.ts:206,480,625`; `room-sync.ts:41,186,569`; `profile-sync.ts:54,130`; `send-retry.ts:119`; `backfill.ts:296,434,521,664,867,1270,1526`) read the 300 s cache and would not multiply it, and the forced callers are only the boot check and the 300 s sweep (`index.ts:239,246`) plus guild member add/remove (`:457,485`). I could not attribute the multiplier from the logs; it is recorded, not claimed. Whatever the multiplier, each call runs a `count(*)` over `edges`: `count(*) as n from edges …` appears **450 times in 30 d** in the slow-query corpus at 100–390 ms in the sample taken — while the same number is already maintained as an aggregate (`queries/spaceStats.ts:46-79`, refreshed per materialised membership chunk at `materialization/applyBatch.ts:505-510`, indexed at `schema-global.sql:253-258`).
- **Why now.** The consequence is silent and permanent, in the billing direction: `spend` is written once and forever — a pending grant is marked spent when the count passes 100 (`:112-116`), and a spent grant can never be re-granted or revoked (`bridgeTokens.test.ts`, "Granting again is refused; revoking is refused"). If the compared number is Roomy membership, then a guild with thousands of Discord members bridging into a space with twelve Roomy members reads `overLimit: false` and pays nothing — and the reverse error is worse, because a space whose Roomy membership passes 100 spends the grant permanently without any guild ever being large. The tests cannot see it: every `bridgeTokens.test.ts` case seeds Roomy `member` edges via `makeMember` and never exercises the request parameter, so the semantics it pins are the ones the bridge does not send.
- **Scope sketch.** First a decision, then a small change. The contract has to say which population "capacity" means, because one branch of it is permanent; then either (a) compare the `memberCount` parameter the bridge already sends (admin-only endpoint, so the value is as trusted as the caller), or (b) keep both on the response — `spaceMemberCount` and `guildMemberCount` — and derive `overLimit` and the spend rule from the guild figure, leaving Roomy membership as dashboard data. Either way, read the maintained `space_stats.member_count` instead of re-counting `edges` on 23,300 calls a day, and add a test that sends `memberCount` in the params so the parameter's role is pinned.
- **Acceptance.** A call with `memberCount=5000` against a space holding 12 member edges returns `overLimit: true` and a `memberCount` that is not 12, and a call with `memberCount=50` against a space holding 150 returns `overLimit: false` with no grant spent. Observable as the handler's response, plus a test that fails before the change.
- **Suggested priority:** **P1** — a commercial rule (Roomy Pro bridge capacity) is evaluated against a number that is not the one it was written for, and one of its outcomes is irreversible. Nothing is corrupt, so it is not P0, and no user report exists because the failure is silent.
- **Not already tracked because.** Nothing in the queue names capacity, bridge tokens, `getSpaceMembership` or `memberCount`. `TASK-22` is link embeds; `TASK-277` is avatars.

The observable check is the rendered section plus the query's response on a seeded space, not a unit test of the filter.

### 3. Bridged Discord messages that carry only a poll, only components, or a Lottie sticker are dropped silently — ~149 a day, flat for a week

- **Evidence.** The ingestion gate drops any message with no content, no attachments and no embeds (`discord-bridge/src/services/message-ingestion.ts:238-247`):
  ```ts
  if (!message.content && attachments.length === 0 && (message.embeds?.length ?? 0) === 0) {
    log.warn(`Skipping message ${messageId} in ${spaceDid}: no content and no attachments`);
    writeSkipRecord("empty_message", message, spaceDid);
    continue;
  }
  ```
  Three message classes produce exactly that shape and have no path into `buildAttachments`:
  - **Sticker formats outside 1, 2 and 4.** `buildAttachments` handles `formatType === 4` (GIF) and `1 | 2` (PNG/APNG) (`:391-404`); Discord's `3` (LOTTIE) falls through and yields no attachment. The existing test pins only 2 and 4 (`services/__tests__/message-ingestion.test.ts`, EC01).
  - **Polls.** The bridge does not request `poll` in its desired properties (`discord/types.ts:12-32`), and `DiscordMessageData` has no such field (`discord/data.ts`), though Discordeno's message carries `poll?: DiscordPoll` (`@discordeno/types` `discord.d.ts:1314`).
  - **Component-only messages** (buttons/selects with no text): `components` is likewise absent from the desired properties, and exists on the Discordeno message (`discord.d.ts:1308`).
  **Measured:** `no content and no attachments` is **149 lines in 24 h** and **149 distinct message ids** (one line per lost message, not duplication); the daily series over eight days is `159, 132, 121, 144, 134, 124, 102, 123, 149` — flat at ~130/day, unchanged by any deploy. 145 of the 24 h lines name one space (`did:plc:qzie4v7qwnv3mzaflihrf56f`), 4 another. - **Why now.** The bridge is the only path these users have into Roomy, and a poll or a sticker-only message is a whole message with no partial failure to notice: the sender sees Discord accept it and the bridge post nothing. The 10-12 record recorded this signature as *"a legitimate skip"* on the assumption that an empty body means an empty message; the three holes above are what make that assumption wrong for part of the class, and the count has not moved in eight days.
- **Scope sketch.** Two small additions to the message pipeline, no change to the gate itself: (a) request `poll` and `components` in `desiredProperties.message` and normalise them into `DiscordMessageData`, then give `buildAttachments` a branch that yields something renderable for each (a poll can land as text — question plus options — and a component-only message as its button labels, which is what a reader needs anyway); (b) a `formatType === 3` branch that emits the sticker as a link attachment (`https://media.discordapp.net/stickers/<id>.json` has no image rendering, so either render a placeholder or attach the sticker's `https://cdn.discordapp.com/stickers/<id>.png` if Discord serves one for Lottie, to be checked). The skip log line should carry the message type and its field sizes so the residual class is distinguishable next time.
- **Acceptance.** A component-only message and a poll-only message each produce a Roomy message with non-empty content; a `formatType: 3` sticker message does not reach the skip log; and after the change the `no content and no attachments` rate falls materially below the current ~130/day floor. Verified on the bridge's own test fixtures plus one live observation of the counter.
- **Suggested priority:** **P3** — real, silent loss in a live channel, but at a bounded rate, in one bridge, for message classes no user has reported yet (the 24 h lines name no complaint).
- **Not already tracked because.** `TASK-22` is *link embeds from URLs* (the opposite direction: a message that does arrive, missing its card). Nothing in the queue or in any open PR names polls, components, sticker formats or the `empty_message` skip reason.

### 4. `the stamp expires and the next request refreshes` fails on a clean `next` checkout, and the race it hits is in the product code, not the test

- **Evidence.** This record's PR is docs-only (`git diff --quiet origin/next HEAD -- packages/` → clean), yet its `Test Appserver` job failed on exactly one assertion:
  ```
  packages/appserver/src/queries/userBlocks.test.ts:372   Expected: 1   Received: 2
  (fail) the refresh trigger > the stamp expires and the next request refreshes
  ```
  Reproduced locally on the **audited ref itself**, with no local edits to either file (`git diff --quiet origin/next -- .../userBlocks.ts .../userBlocks.test.ts` → clean): `bun test --isolate src/queries/userBlocks.test.ts` gave **23 pass / 1 fail on five consecutive runs**, and the single test alone failed 3 times in 5. The failure is line 372, the *second* `expect(calls).toBe(1)` — the "inside the window an authenticated request costs nothing" assertion — so the second `warmBlockSet` refetched inside a 40 ms TTL.
  The mechanism is in the product code. `warmBlockSet` stamps the attempt from `Date.now()` captured when the fetch **completes** (`queries/userBlocks.ts:335`, `const now = Date.now()` inside `replaceBlockRows`, which `fetchAndStore` calls at `:296` only after the fetch returns), and `warmBlockSet` then compares the *next* caller's `Date.now()` against that stamp (`:255-261`). Under `--isolate` the first fetch pays process/DB startup — measured with a throwaway probe on this ref: **`stamp_age_at_completion = 94 ms` against a 40 ms TTL**, versus 4 ms and 11 ms on two later runs. Every call that completes with more latency than the TTL leaves a stamp that is already stale when it lands, so the next call refetches by design. The test sets `BLOCK_CACHE_TTL_MS=40` — a value no caller would use — which is what makes a 94 ms fetch into a failure; production's TTL is 60 s (`:77`), so nothing user-facing is wrong.
  **The test is not new, and it is not always red.** It last changed in `a691477a` (#465, the deployed build); `#451` touched `userBlocks.ts` this morning but not the test. `#62cb7884`'s own `Test Appserver` job is green, and so are the seven other open PRs sampled — so this is run-to-run: the same code passes whenever the first fetch happens to finish inside the 40 ms window.
- **Why now.** It is the only red check on this record, and the next worker whose PR is docs-only or unrelated will hit it and reasonably assume their change caused it. It also hides a real property: `warmBlockSet`'s dedupe window is bounded by *fetch completion* plus TTL, so a slow PDS makes the client refetch on the very next authenticated request rather than after the window — a per-request PDS fetch, which is exactly what the cache exists to prevent, in the case where the fetches are slowest.
- **Scope sketch.** Two independent fixes, and either removes the red check: (a) test-side — pin the clock (`vi.useFakeTimers` / `vi.setSystemTime`) around both warm calls so the TTL is compared against a controlled clock rather than wall time, or set `BLOCK_CACHE_TTL_MS` to a value that cannot be consumed by fetch latency; (b) product-side, the one worth doing — capture `Date.now()` before the fetch starts and pass it to both `replaceBlockRows` and `recordFetchError`, so the window is measured from when the read was due rather than from when a slow PDS answered. (b) also makes the backoff honest: a failed fetch that takes 90 s currently gets a fresh 60 s grace on top.
- **Acceptance.** `bun test --isolate packages/appserver/src/queries/userBlocks.test.ts` is green on **ten consecutive cold runs** (this ref gave 5 failures in 5), and the test still fails when the TTL comparison is deliberately broken — i.e. it keeps defending the window it names.
- **Suggested priority:** **P2** — a red CI check that has nothing to do with the diff under review, on a runner where it failed here 5 times in 5 cold runs, plus a real (if narrow) cache defect underneath it.
- **Not already tracked because.** Nothing in the queue or in any open PR names `userBlocks.test.ts`, the block-refresh stamp, or CI flake. The `#bugs`/`#todos` reports about "Save needs five clicks" are unrelated.

## Limits of the evidence

- **Proposal 1's mechanism is a source read; its consequence is not measured.** The parameter is sent (`membership-client.ts:65-73`), the handler does not read it (`getSpaceMembership.ts:95-96`), and the count it uses instead is Roomy `member`/`admin` edges (`:69-78`). What I could **not** verify: how many member edges any production space holds, so I cannot say that any current bridged tuple is mis-classified today — only that the two numbers are different populations by construction and that the wrong one is permanent. Nor could I count the bridge's bridged pairs: its config table is not readable from here, and the only pair count in the logs (13) is the fail-open subset. The call-rate arithmetic (23,300/24 h against 13 pairs × 288 sweeps) therefore shows the rate is unexplained, not that there are ~81 pairs — the burst structure (multiples of 13) points the other way.
- **Proposal 4's flake rate is measured on this host only.** `bun test --isolate` on the audited ref failed 5/5 full-file runs and 3/5 single-test runs here, and its one CI failure is the PR's; the other seven open PRs I sampled report `Test Appserver: success` on the same day, so the true rate is between "one CI run" and "always", and I did not sample enough CI runs to narrow it. The 94 ms / 40 ms stamp-age figures come from a throwaway probe (deleted; not in the diff) on this ref, and are the reason the second warm call refetches — not an independent measurement of production behaviour, where the TTL is 60 s.
- **Proposal 3's split is an inference.** Which of the 144 daily skips are polls, components or Lottie stickers, and which are genuinely empty, cannot be told from the log: the skip line carries no message type or payload sizes, and `ROOMY_SKIP_LOG` is unset in production so no skip record is written (`message-ingestion.ts:28,36`). I verified that the three classes *cannot* produce an attachment and are present in Discord's own message shape, not that they are what is being dropped. One sample was decoded (snowflake → timestamp) to show the drops are live traffic rather than backfill.
- **Every count here is an instant `count_over_time`.** Loki `query_range` with a `|=` filter returned `cannot use null as iterable (array or object)` on six queries this run (`aborted for`, `recordUnresolvedProfiles`, `db timeout`, `fatal`, `data dir ready`, `bridge starting`), and those counts are simply not quoted. Where a filtered range read did work, its result is what is quoted.
- **The queue is read from the embedded snapshot**, not from Meri's Forest `#tasks` (403 for a non-member channel, expected), so both the count and the task states are only as good as that paste — which again says 18 while its mirror list carries 19.
- **PR state is quoted from the API, not reproduced.** All 28 open PRs' `mergeable_state`, reviews and comments were read; the five `dirty` verdicts were then checked independently with `git merge-tree` against `origin/next`, which is the stronger evidence and agrees with the API. No `bun test`, Playwright run or build was executed.
- **Room reads are windows, not histories.** `#bugs`, `#todos`, `#meta`, `#roomy`, `#features` and `#general` each returned their full page at the limits above; `#general` has been quiet since 2026-10-11 apart from joins. Absence of a report is absence in the newest page.
- **No benchmarks and no browser this run.** Every number above comes from Loki, Mimir, Tempo, the two HTTP health endpoints, or a source read at `62cb7884`.
