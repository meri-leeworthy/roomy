### 2. An XRPC failure names neither the caller nor the space, so every error class in the log is unattributable

- **Evidence.** `packages/appserver/src/xrpc/router.ts:337` is the only line that names a failed route: `` log.error(`[xrpc] ${req.method} ${url.pathname} failed:`, err.message) `` — no DID, no params, no space. Its paired `scope=app` line carries the handler stack and likewise no identity. Three classes measured this tick are stranded by that:
  - **44** `Entity <id> is not a message (no room)` over 7 d (8 in the last 24 h) — proposal 3 below cannot say who asked or which client.
  - **60** `Caller has no read access to this room` over 7 d (4 in the last 24 h) — `packages/appserver/src/xrpc/authGuards.ts:144`.
  - **20** `POST /xrpc/space.roomy.auth.getConnectionTicket failed: Authentication required` over 7 d.
  The 10-24 record hit the same wall independently and recorded it as a limit: *"Tempo carries `roomy.room_id` but the appserver's failure lines carry neither the caller nor the space, so the cluster is counted and located but not attributed."*
- **Why now.** Three separate open questions — the 403 trio, the reply-target 400s, and the connection-ticket refusals — are blocked on one missing field, and the field is already in scope at the call site (`AuthCtx` is threaded to every handler).
- **Scope sketch.** Thread `AuthCtx` into the router's error path, and add `userDid`, plus `spaceId`/`roomId` when the handler resolved one, to **both** halves of the pair. Keep them out of the response body (a DID in an error the client renders is a leak the current design avoids). Where a handler resolved no space, log the param names it was given rather than nothing.
- **Acceptance.** Forcing a 403 by hand produces a single `scope=xrpc` line carrying the caller DID and the space DID; within 24 h of deploy, the three classes above are attributable to a DID without reading Tempo.
- **Suggested priority:** **P2**.
- **Not already tracked because.** Nothing in the queue names server-side error context. `TASK-146`(a) improved the *dispatch* prompt's self-check for `sock=`; it is a coordinator-side instruction, not appserver logging.

### 3. Reply targets that can never resolve are refetched on every load, and something is still writing them

Across the 7 d corpus the same ids recur on different builds and different days: `01M5FY42SNP3BMA3P3XR8X11AJ` **5×**, `01M57AW566FNNJCBN7NMRGGP70` **3×**, `01M5HMFHCQY0T0238CQ3JWNGEQ` **2×**. New ids also keep arriving: `01M5PS8Y27S36X4FAK86M75MW8` was requested at 2026-10-24T11:19Z and `01M5PS8WSWJBQ8VK45JBD4SQ4N` at 11:43Z — both ULIDs from that same morning.
  **Both defences exist and neither stops it.** The client guard is `packages/app-lite/src/lib/queries/room-ids.ts` (landed 2026-10-07 as part of `#373`, present in the deployed build) and its own docstring says "messages carrying such a target are historical — the writer that produced them is fixed at the appserver". The admission check is `packages/appserver/src/auth/writeAuth.ts:583` (`checkReplyTargets`), which rejects a target whose `entities.room` is null. Two writers remain outside the guard's reach: `ChatArea.svelte:133` (`revealMessage`) calls `px().query("space.roomy.message.getMessage", …)` directly with no `isNonMessageReplyTarget` test, and the guard's room index is empty on a cold load, so a reply to a room is asked once per cold start — which is exactly the recurrence pattern above.
- **Why now.** It is the largest *repeating* 400 class, each occurrence costs a round-trip and a console error on every load of the affected reply, and the record has now carried the reply-preview question across five ticks without closing it.
- **Scope sketch.** (a) Attribute the caller — genuinely needs proposal 2 first, or a one-off log of `auth.userDid` on this handler. (b) Apply the existing guard at `revealMessage`, and give the negative verdict somewhere to persist so a cold load does not re-ask (`retry: false` is already set, but the id is simply unknown on first paint). (c) Find the writer still admitting a non-message target: the admission check reads `entities.room` *at admission time*, so a target entity not yet materialised, or written in the same batch as its room, passes the check by not existing yet.
- **Acceptance.** Zero `is not a message (no room)` lines over 7 days, with the reply preview still rendering its "Reply unavailable" state for such targets.
- **Suggested priority:** **P3**.
- **Not already tracked because.** Nothing in the queue or the 15 open PRs names message reply targets, `getMessage`, or the client's room index. `TASK-27` (forwarded message resolution) is a different attachment kind.
