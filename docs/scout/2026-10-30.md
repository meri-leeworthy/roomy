  `Pages changed - roomy-meri` with `conclusion: failure` and the annotation
  `Deploy failed`. The flip is sharp: `#579` (created 11:11:32Z on 2026-10-28)
  has the same three checks `neutral`, i.e. the build was skipped; `#580`
  (opened 12:09:25Z, checks run at 12:12:19Z) has them failing. `#581` is a
  docs-only PR that adds one Markdown file and it fails identically, so the
  trigger is not the PR's content. Every other open PR and the last seven
  `next` commits are clean.
  `netlify.toml:22` sets `[build] ignore = "true"` and its comment states the
  intent: nothing but a dispatched `netlify deploy --build` should build this
  site, because only that path supplies `DEPLOY_URL`, which
  `scripts/netlify_build.sh:27` requires (`${DEPLOY_URL:?…}`). A preview build
  that runs therefore cannot succeed — it fails at that line.
- **Why now.** Three consequences at once: (a) every new PR is red regardless of
  its code, so a reviewer cannot use check state (five PRs now, and the number
  grows with every PR opened); (b) each failed deploy is a Netlify build that
  was supposed to be skipped, which is the build-minute cost the dispatch-only
  workflow exists to conserve; (c) the production client has not been redeployed
  since 2026-10-28T12:54Z, and if the site-side cause is broader than previews,
  the next dispatched deploy fails too.
- **Scope sketch.** Read one failing deploy's log on the `roomy-meri` site and
  decide whether the site's build settings (base directory, build command,
  "Deploy previews" toggle) were changed away from `netlify.toml`, or whether
  the `ignore` hook is no longer consulted for PR deploys; restore the skip, or
  replace it with an `ignore` command that exits 0 explicitly for the
  git-integration context. Independently, make `scripts/netlify_build.sh` fail
  with a message naming the missing `DEPLOY_URL` rather than the bare parameter
  error, so the next occurrence is diagnosable from the check annotation.
- **Acceptance.** A newly opened PR shows the three `roomy-meri` checks as
  `neutral` (skipped), not `failure`, while a dispatched `Netlify Deploy`
  workflow run still succeeds and `roomy.space/build.json` names the dispatched

### 3. A boot re-materialize over 15 streams applies zero events and skips 98 because they decode with no `$type`

- **Evidence.** The 07:00 deploy boot logged
  `re-materializing 15 streams from local events DB (4434 already up to date)`
  and then, for each of those 15 streams, a
  `[re-materialize] stream-done` warn with `applied: 0` and a non-zero
  `materializerErrors` — 22, 20, 17, 10, 7, 7, 5, 3, 1, 1, 1, 1, 1, 1, 1 —
  summing to exactly **98**, the number of
  `[materialize] no materializer for event … (kind: undefined) — skipping` lines
  in the same second (`07:00:28.007–.008Z`). `materialization/materializer.ts:30`
  takes the kind from `event.$type`, so `kind: undefined` means the decoded
  event has no type at all; the guard at `materializer.ts:33-37` turns that into
  a skipped event and a `status: "error"` bundle, and
  `streams/reMaterialize.ts:531-538` logs the per-stream total as a **warn**
  while the boot continues. `"kind: undefined"` appears **98** times in 7 d and
  **0** times before today: this is new since the previous deploy (the one
  24 h before logged 5 skips total).
- **Why now.** A stream that owed a replay re-applied nothing and every event it
  tried was refused, and nothing in the boot's outcome says so — the 4,434
  "already up to date" streams and these 15 are indistinguishable from the
  startup line alone. If the replay cursor advanced past them the events are
  gone from the projection; if it did not, the same 98 will be retried and
  refused on every boot. Either way the failure is silent at the level anyone
  reads.
- **Scope sketch.** Diagnose before fixing: read the local events DB rows for a
  handful of the ids this boot named (`01KD93TC6BNR0M3VEH74DF3VV3`,
  `01KDRHABR20S06EWP6YES1PSHR`, …) and determine whether the record is
  untyped by construction (written by an older writer, or by a path that omits
  `$type`) or whether the decode drops it. Then make the outcome explicit:
  count untyped events separately from "no materializer for this kind", and have
  the boot runner report a stream whose replay produced only errors as failed
  rather than leaving it to a warn line.
- **Acceptance.** A unit test that an event whose record carries no `$type` is
  either materialized or counted as a distinct `untyped` failure (not folded
  into `materializerErrors`); the next boot's `stream-done` records name which
  stream owed a replay and whether it was completed; and a boot whose replay
  applies 0 of N reports that stream as not caught up.
- **Suggested priority:** **P2**.
- **Not already tracked because.** `#526`/`TASK-402` adds *reporting* for
  skipped events — it would count these, not materialize them, and untyped
  events are a different fault from "no materializer for a known kind". No entry
  in the queue mentions re-materialization or `$type`.
