### 1. Link-embed enrichment has stalled again: 5,083 links pending, `enrichedOk` frozen at 6, and the gauge named "awaiting enrichment" reports 0

  **The alertable signal is structurally blind to this.** `roomy_embed_pending` — declared `"Embed links awaiting enrichment."` at `appserver.ts:740` — is set at `appserver.ts:864` from `embed.priorityQueue`, which is `priorityLinks.size` (`embed/sweeper.ts:160`), the in-memory set of *freshly-poked* URLs only. The DB backlog is a different number, computed only for the health endpoint at `appserver.ts:795` via `countPendingLinks(openGlobalDb())` (`embed/enricher.ts:393`). So `roomy_embed_pending` reads **0** while 5,083 rows await enrichment, and a Grafana alert on it can never fire.
  Mechanism candidates in the code, both consistent with the flat counters: `sweepCycle` returns `pending.length >= SWEEP_BATCH` (`sweeper.ts:420`) as "full" and `runSweeperLoop` `continue`s without sleeping (`:431`), while `findPendingLinks` excludes in-memory backoff URLs server-side (`enricher.ts:158-181`) and `backoffMs` reaches a 6 h cap (`enricher.ts:221-225`) — so a batch that is entirely in backoff yields an empty cycle that returns `false` and sleeps to the next 30 s poll (`IDLE_POLL_MS`, `sweeper.ts:56`). With `dbErrorCount: 0` and `dbBackoffActive: false` nothing is erroring; nothing is progressing either. **[INFERENCE — the mechanism is not reproduced; the frozen counters and the blind gauge are measured.]**
- **Why now:** link cards are the visible half of link embeds, and the same data feeds the links view that landed today (#224). 5,083 links is a backlog, not a sample; a link posted now has no card and no signal says so. Re-measurement matters too: the 2026-09-16 scout flagged "appview returned 400" noise here and the 09-18 run reported the sweeper healthy — the state has changed since.
- **Scope sketch:** two separable changes. (1) Make `roomy_embed_pending` the number the gauge's own docstring promises — set it from the same `countPendingLinks` the health handler already calls (or expose both, with distinct names). (2) Determine why a cycle selects nothing while `pending_links` is non-empty — the backoff filter, the full-batch `continue`, or a `pending_links` write path that is not being drained — and make the stall self-evident (a periodic `level=info` line with `pending`/`inFlight`/`backoffSize`, or a second gauge). Do **not** simply lower the retry cap without the measurement; a 6 h cap is a deliberate choice for genuinely-down hosts.
- **Acceptance:** `roomy_embed_pending` equals `/health/embed`'s `pending`; over a 30-minute window with work outstanding, either `enrichedNull` advances or a log line explains why it does not.
- **Suggested priority:** **P1** — user-visible feature data is frozen with no signal, and the one gauge that should catch it is wired to a different number.
- **Not already tracked because:** no open task mentions the embed sweeper. TASK-143 (agent-chatter write cost) and TASK-137 (the links *view*) are adjacent but neither is about enrichment draining.

Nothing comparable appears before or after; the last occurrence in the whole week is 2026-09-16T10:13:55Z.
  Cause: `getActivityFeed.ts:35` throws `AuthRequired` when `parseUserDid(auth) === null`; the home route renders `<ActivityFeed limit={20} />` (`routes/+page.svelte:68`) as soon as `spacesQuery.data` is present, and `createActivityFeedQuery` (`lib/queries/activity-feed.ts:26`) sets **no `enabled`** — so the query runs while `auth.authenticated` is still false. The not-logged-in overlay only replaces the tree once `requireAuth.value` is true (`routes/+layout.svelte:232`), and `requireAuth` is set inside `onNavigate` (`:131`), i.e. on the *first navigation*, not the first paint. `client.ts` sets `staleTime: Infinity` but leaves the default `retry: 3`, so one page view costs up to four requests.
- **Why now:** it is the single largest error-message class in the week's appserver logs (an order of magnitude above `getInvites`, which was worth a task), each occurrence is logged twice at `level=error` with a full stack, and it is a plain unauthenticated page view — the first thing a logged-out visitor or a pre-auth PWA load does.
- **Scope sketch:** one line in `lib/queries/activity-feed.ts` — pass `enabled: () => auth.authenticated` (mirroring how `spaces.ts` already gates the page's own render), plus `retry: false` for the 401 class, matching the reasoning already written into `invites.ts:25-28`, `roles.ts:24-27` and `bridge-tokens.ts:32-34`. Consider whether the *server* should answer an unauthenticated feed with an empty list rather than a 401, as `getSpaces` already does (`getSpaces.ts:28-31`, "Anonymous users get an empty list for now") — that is the decision to state, not to assume.
- **Acceptance:** loading `/` while logged out issues zero `getActivityFeed` requests; re-measured over 24 h, the signature is 0 (vs 10,955 in the week).
- **Suggested priority:** **P2**.
- **Not already tracked because:** nothing in the queue names the activity feed, and TASK-113/161 covered `getInvites`/`getRoles` — different handlers on different pages.
- **Confidence caveat:** I could not reproduce the storm. The ~15-per-2-second cadence is *not* TanStack's retry backoff; it looks like repeated component re-mounts, and I did not pin what drove them. The fix above removes the request entirely for the unauthenticated case, so it holds regardless of which of those it is.

  Client side: those messages render through `ChatMessage.svelte:379` → `MessageContext` → `MessageContextReply.svelte:16` → `createMessageQuery`, which is constructed unconditionally (`queries/message.ts:16-25`: `enabled: options?.enabled ?? true`) and — unlike its three siblings `invites.ts:28`, `roles.ts:27`, `bridge-tokens.ts:34` — sets **no `retry: false`**, so a deterministic 400 is tried up to four times.

- **Acceptance:** no new `getMessage → 400 not a message`; the existing 182/week signature decays to zero; the affected messages' reply previews render.
