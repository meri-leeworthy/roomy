## Proposals (ranked)

### 1. The batched HappyView profile fetch never sends the client key, so every batch is rejected

- **Evidence.** **55** `HappyView returned 401 for N DIDs` lines in 24 h, every
  one `env="staging"` (111 in 7 d, so half of them are today-ish). The batches
  are the only HappyView calls that fail — the single-DID path logs no
  rejections. In the tree, `getProfilesFromHappyView`
  (`packages/appserver/src/materialization/roomyProfile.ts:135-143`) builds its
  header map empty and adds **only** `X-Client-Secret`; the single-DID
  `getProfileFromHappyView` in the same file
  (`packages/appserver/src/materialization/roomyProfile.ts:187-192`) sends
  `X-Client-Key` **and** the secret. `packages/appserver/src/happyview.ts:41-46`
  documents the key as "Required — HappyView rejects requests without it", and
  `happyview.ts:56-57` enables the feature on `HAPPYVIEW_CLIENT_KEY` being
  present — so a deployment configured with the documented minimum sends an
  entirely unauthenticated batch request, and one that also sets the secret
  still omits the header HappyView requires.
- **Why now.** A 401 means the batch contributes nothing:
  `getProfilesRoomyFirst` falls through to the Bluesky appview per DID
  (`materialization/profiles.ts:8-20`), which is the slow path the pipeline
  exists to avoid, on every cold batch. Nothing surfaces it — the only trace is
  a `warn`, and there is no log line saying whether HappyView is configured at
  all, so "unconfigured" and "rejecting every request" are indistinguishable.
  That is why production cannot be cleared from here (see the limits).
- **Scope sketch.** Add `X-Client-Key` to the batch header map alongside the
  secret, matching the single-DID path; emit one startup line (or a
  `roomy_happyview_configured` gauge) recording whether the pipeline is enabled;
  add a request-building test that asserts both call sites send both headers.
- **Acceptance.** A test that fails on pre-fix code and passes after; staging
  logs zero `HappyView returned 401` for a 24 h window and `getProfiles` returns
  profiles from it; the startup line makes "enabled" observable per environment.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No task names HappyView. `TASK-277` is about
  avatar blob bytes, `TASK-439`/`TASK-438` are the Rust follower, and CF16 is
  the admin allowlist — a different missing piece of the same staging
  environment.

  sign-out. The user report and the measured loop are recorded above as the
  corpus that PR's cause classification needs, which is more useful to it than a
  competing task would be.

  `MAX_RELOADS = 3` per 60 s (`lib/error-recovery.ts:42-44`) is more than the
  budget allows, and I could not reconstruct the accounting: Faro drops queued

  undercounted by an unknown amount. `#549` bounds a dead session to a single
  reload regardless, so the discrepancy has no work attached.

  events worker. Not a recurring cost.

  is not separable from a real hang. Not a task; noted so nobody re-derives it.
