### 2. Discord-bridge archived-thread backfill fails permanently on Discord's 15-minute window, silently truncating bridged history

- **Evidence:** `{service_name="discord-bridge"} |= "getPublicArchivedThreads failed"` — the single most frequent bridge error signature, present on 21 of 24 recent hourly buckets (peak 63/h). The error body is `"Failed to send request to discord."`, and the failing call passes **no cursor**: `before=-` for 6 of the failures on parent channels `1473104502436528138`, `750401468569354431`, `571775594002513921` (e.g. 2026-09-16T02:02:19.395Z, after 3 attempts). The pagination `before` is derived from the thread's `thread_metadata.archive_timestamp` (`threadTimestampToCursor`), and Discord's `GET /channels/{id}/threads/archived/public` **requires** `before` to fall inside the last 15 minutes; one older than that is rejected as a bad request. The retry policy cannot help — `live-data-source.ts:143–173` retries a deterministic 400 three times, then throws, and the caller aborts the parent channel's whole archived-thread pass (`services/backfill.ts:638` → `Failed to backfill archived threads for parent channel …`).
- **Why now:** it runs on every bridge boot for every guild, so the recurring error line is itself the noise; the real cost is that Discord history for those channels is missing from Roomy with no user-visible signal. TASK-139 (multi-phase backfill) will make this worse, not better, if the cursor rule is not fixed first.
- **Scope sketch:** compute the `before` cursor as `min(archive_timestamp, now - 1 min)` so it is always inside the accepted window; separately, stop a single deterministic 400 from aborting the parent channel (distinguish retryable from non-retryable failures — TASK-124 built the retry loop, this is the other half of that decision).
- **Acceptance:** on a guild with archived threads older than 15 minutes, `getPublicArchivedThreads` returns a page rather than erroring, and no `Failed to backfill archived threads for parent channel` line appears on a fresh boot.
- **Suggested priority:** P1.
- **Not already tracked because:** TASK-124 (merged) fixed the *snowflake→epoch* overflow in the same call and added the retry loop; the 15-minute window rule is a different, still-live failure, and no open task mentions it.

### 3. Client fires space/room summary queries for URL text that was never a room link

- **Evidence:** `{service_name="roomy-app-lite"} |= "failed (404)"` — 73 in 24 h, with 19 distinct targets including `Space not found: profile` (18), `muni-town` (18), `workshops` (14), `accounts` (6), `eu-digital-identity-wallet` (6), `watch` (4), `code` (4), `terms`, `essays`, `artifact`, `d` (e.g. 2026-09-16T06:53:19–22Z, one page load producing 6 of them).
- **Why now:** low volume, but it is a **client-originated 404 with no retry guard** — TanStack's default `retry: 3` (`@tanstack/query-core@5.100.10` `retryer.js:86`) turns one miss into four appserver requests, and the queries are never `enabled:false`-guarded on validity. It is also a correctness gap in the "internal links" feature: `https://roomy.space/muni-town` is a Roomy URL but is neither a DID nor a ULID, so it renders as an ordinary link while still being marked internal by the renderer (`packages/design/src/utils/markdown.ts:20–39` marks anything under a known Roomy domain).
- **Scope sketch:** in the two extractors (`app-lite/.../enrich-internal-links.ts:63` already validates; `prefetch-link-summaries.ts:67` delegates to it), apply the **same DID/ULID validation the SDK already performs** to the *renderer's* marking decision, so only true space/room refs are marked and mounted; then add `retry: false` for these two queries — a 404 that says "Space not found" will never succeed on retry (the repo already does exactly this for `invites.ts:25` and `bridge-tokens.ts:32`, with the same rationale in the comment).
- **Acceptance:** loading a room whose messages contain `https://roomy.space/profile` produces zero `getSpaceSummary` calls, and a 404 summary query is attempted once, not four times.
- **Suggested priority:** P2.
- **Not already tracked because:** the guard added in `99039009` (2026-08-17) fixed the prefetcher's *href* path only; the renderer's `data-roomy-internal-link` marking and the query-retry policy are untouched, and the residual 404s are still arriving daily.

### 5. Fifteen appserver handlers await a global-DB membership read whose result none of them use

- **Evidence:** `hydrateUserMembership` is awaited at the top of 15+ handlers (`getMessages`, `getThreads`, `getMetadata`, `getActivityFeed`, `getSpaces`, `getRoles`, `getMembers`, `message.getMessage`, `message.getReactions`, `search.messages`, `search.rooms`, `updateSeen`, `getInvites`, `getBridgeTokens`, `grantBridgeToken`, …). Every one of them **discards the return value**; `intendedSpaceDids` has zero consumers outside `userHydration.ts` itself. Access decisions are taken from each space's own DB (`requireRoomRead` / `requireSpaceRead` / `requireSpaceAccess`), which the handler calls separately. The awaited call is a global-DB `select space_did from user_space_membership where user_did = ? and state = 'joined' order by updated_at desc` (`queries/userSpaceMembership.ts:106-119`), and it is the **dominant cost of the request**: `getMessages.hydrateMembership` 2 276 ms of a 2 296 ms request; `getThreads.hydrateMembership` likewise accounts for the top of that endpoint's waterfall.
- **Why now:** this is the mechanism behind proposal 1 — the slowest phase of the most-used read is a query whose result is thrown away. Removing it from the hot read paths is a bounded change with a large latency win.
- **Scope sketch:** drop the `await` from handlers that do not read the result (keep the fire-and-forget form already used at `updateSeen.ts:60`, `void hydrateUserMembership(userDid).catch(() => {})`, if the warm-up is still wanted), or make the read cheap enough to keep. Confirm the per-user in-flight dedup (`userHydration.ts:37-46`) actually coalesces under concurrent load.
- **Acceptance:** `room.getMessages` and `space.getActivityFeed` p99 drop measurably on the production-shaped dataset, with space access still enforced (the existing auth-guard tests cover that path).
- **Suggested priority:** P2.
- **Not already tracked because:** no open task mentions hydration; TASK-116 (done) optimised `admin.listSpaces`, a different endpoint.
- **Honest limit:** I traced call sites and the trace waterfall, and read the SQL — I did not run an A/B to prove the p99 recovers. Treat "removing it improves latency" as a hypothesis this task should test first.

### 6. The client's link prefetch trusts stored `#roomRef` facets that were never validated

- **Evidence:** the SDK's `extractInternalLinkTargets` (`sdk/src/richtext/convert.ts:747-786`) pushes every stored `#roomRef` feature straight through with no validation, while the app-lite path validates. Probed directly against the working tree: `extractInternalLinkTargets` on a block containing a stale facet returns `[{"spaceId":"muni-town"}, …]`, and `parseInternalLinkHref("https://roomy.space/muni-town")` returns `null` — i.e. the two paths disagree, and the unvalidated one is what drives `prefetch-link-summaries.ts`'s `ensureQueryData` fan-out.
- **Why now:** it is the durable half of proposal 3. Validation was added at the **href** layer in `99039009` (2026-08-17), so newly-typed links are clean, but any facet persisted before that — or written by a path that still bypasses validation (`discord-bridge/src/services/mention-resolver.ts:452` constructs `#roomRef` directly from its own mapping, with no DID/ULID check) — keeps producing 404 summary fetches forever.
- **Scope sketch:** validate inside `extractInternalLinkTargets` (`Did(spaceId)` / `Ulid(roomId)`, mirroring `parseInternalLinkHref`), and have the bridge's channel-mention resolver emit `#roomRef` only for a validated pair.
- **Acceptance:** a block carrying a non-DID `spaceId` facet yields no prefetch target; existing valid refs still surface.
- **Suggested priority:** P3 (correctness/hygiene; the user-visible volume is small).
- **Not already tracked because:** the 2026-08-17 fix was scoped to `parseInternalLinkHref` and is documented as such in its own comment; the facet-read path was left unvalidated.
- **Honest limit:** I did not find a live message in production whose stored facet is the source of the current 404s — the reproduction above is against a synthetic block. The 404 targets in proposal 3 are equally consistent with the markdown path, which is why proposal 3 leads.
