### 2. A Discord channel whose type is outside `{GuildText, GuildAnnouncement}` is never given a Roomy room, and every message in it is dropped with one warn line — 3,386 in 30 days

- **Evidence.** The bridge's room-creation gate is a two-element type set, duplicated in two files: `discord/data.ts:171` and `discord/types.ts:119` both read `export const CHANNEL_TYPES = new Set([0, 5]); // GuildText, GuildAnnouncement`.     log.warn(`No Roomy room mapping for channel ${channelId} in ${spaceDid}, skipping message`);


Per channel over 30 d: `1557214567132565544` **2,980**, `1518959421974384763` 277, `1518983746165018654` 52, `1562261624868577290` 11, `1536149224721354822` 10.
  The live instance is dated to the second. Channel `1562260801342013482` was created `2026-10-21T00:26:40Z` (Discord snowflake). A thread under it was created at `00:29:56Z`; `handleThreadCreate` logged `No Roomy room for parent channel 1562260801342013482 … skipping thread` at `00:29:56.839Z` and again at `00:30:48.967Z`. ### 4. Push delivery has no retry and never prunes a device it cannot reach, while its own docstring promises a backoff that does not exist

- **Evidence.** The dispatcher's header says outbound calls *"run with bounded concurrency and a self-healing backoff on 429/5xx"* (`push/dispatcher.ts:12`). The failure branch does neither — it counts and logs, and the job is gone:
  ```ts
  } else {
    statsFailed++;
    log.warn(`[push-deliver] FAILED kind=${sub.kind} status=${res.status ?? "?"} …`, …);
  }
  ```
  (`:449-455`). There is no requeue anywhere in the file — `queue.push` appears only in `pokePushDispatcher`, and `selectSubscriptions` (`queries/pushSubscriptions.ts:76`) reads every row unconditionally, so nothing is ever held back. `push_subscriptions` (`db/readStateSchema.sql:138-149`) has no `attempts` / `retry_after` columns at all, unlike `link_embeds` (`db/schema-global.sql:110-111`), which is where the backoff wording was copied from.
  **Measured:** `FAILED kind=` lines are **50 in 30 d**, **5 in 24 h** (instant counts, all of them `kind=apns`), and the raw 30 d retrieval returns **33 lines**, **31 of which name the same APNs token** (`fcd95651…`, truncated identically every time). Every one of those 31 reads `status=? … : HTTP null` — the transport reported a stream failure with no response line (`push/transports/apn.ts:158` leaves `status` null), classified `retry` (`:272-276`), and the dispatcher then drops it. The 20 `GONE (pruned)` lines in the same window are all Web Push endpoints (`updates.push.services.mozilla.com` 13, `fcm.googleapis.com` 4, `web.push.apple.com` 2, `jmt17.google.com` 1) — **none names that token**, so it is neither delivered nor pruned; it will fail on every message to that user forever.
- **Why now.** It is a one-user report in the making and the code cannot even tell "device is dead" from "the network blipped" — the two outcomes the transports were built to distinguish. The docstring/adjective mismatch is also the kind of thing that makes the *next* reader trust a retry that is not there.
- **Scope sketch.** Smallest honest change: make the failure branch durable the way the bridge's send queue is (`discord-bridge/src/services/send-retry.ts` — a row, an attempt count, a backoff, a terminal state), either on `push_subscriptions` or in a sibling table; prune after N consecutive transient failures so a dead token stops costing every message. If the decision is "no retry", then fix the docstring and log the drop as terminal — but pick one, because the current line promises a queue to every reader.
- **Acceptance.** A subscription whose first delivery raises a network error is attempted again after a backoff, and its `attempts`/`last_error` are readable from `/health/push` (or the DB); a subscription that fails N times is pruned with a `GONE`-shaped line instead of failing forever; the module docstring matches the code either way.
- **Suggested priority:** **P3** — one device today, bounded, and no message loss on the Roomy side; but the earliest same-token failure retained is 2026-10-07, so every push to that user has been silently dropped for at least a fortnight, and the code's own documentation says otherwise.
- **Not already tracked because.** Nothing in the queue or any PR names push retries, `push_subscriptions` columns or APNs failure handling. `TASK-16` is the OAuth "token was not issued to this client" error; `#474` is process boot time.

## Limits of the evidence

- **Proposal 1's mechanism is verified end to end; its population is not.** The live browser load of `https://roomy.space/home` returning "404 / No space at "home"" is observed, and the guard is the only code that can produce that string. What I **cannot** measure is how many installed PWAs still carry the old `start_url`: the manifest history is in git (correct since 2026-07-09) and the two reports are six weeks apart, but there is no telemetry that names the entry URL of a launch, so the affected count is unknown and may be two users.
- **Proposal 2's type is an inference for the channel that produced the evidence.** The log line the bridge emits for an unmapped parent names the channel and says "skipping thread"; it does not name the channel's type. I inferred that `1562260801342013482` is a type outside `{0, 5}` from three facts — its creation timestamp, the absence of any `Created Roomy room` line for it in 30 days, and the presence of such a line for its sibling channels created the same night — and from the type guard being the only path in `handleChannelCreate` that returns without logging. Whether it is a forum (15), a media channel (16) or something else is **not** established. Which of the 3,386 drops are forum-class versus a thread/room race is likewise unresolved: 7 of the 30 d drops (across 5 threads) landed before their thread's room was created, i.e. a different mechanism.
- **Proposal 3's "no toggle" is a source read.** A grep of `packages/` for join/notice settings returns nothing outside the bridge's capacity notifications, and `getSpaceMetadata` has no such field. I did not check the mobile/desktop shells (`src-tauri/`), which render the same web bundle.
- **Proposal 4's "no retry" is a source read of one file plus its schema.** The transports never throw and the dispatcher never requeues; I did not exhaustively search for a retry driven from another module, though nothing on the push path (`dispatcher.ts`, `evaluate.ts`, `pushSubscriptions.ts`) holds one. The 31 same-token failures are counted from log lines, not from the subscriptions table, which is not readable from here.
- **Every count here is an instant `count_over_time` where a range read failed.** Loki's filtered `query_range` returned `cannot use null as iterable (array or object)` on nine queries this run (`Cannot resolve name` ×6 windows, `push-deliver GONE`, `push-apns token rejected`, `Could not resolve handle`); those counts are either omitted or quoted from the instant query and marked as such. The `Cannot resolve name` figure (239 in 30 d) comes from that instant query and its raw lines could not be retrieved — I make no claim about which channels it names.
- **The `Discord bot connected` / restart split is a count, not a timeline.** 21 READY lines against 11 `bridge starting` lines in 30 d, and only 5 READY lines could be retrieved from raw range reads; the per-minute capacity trace is what corroborates the duplication, and it is a shape, not a count of the extra sweeps.
- **The queue is read from the embedded snapshot**, not from Meri's Forest `#tasks` (403 for a non-member channel, expected), so both the count and the task states are only as good as that paste — which again says 18 while its mirror list carries 19.
- **PR state is quoted from the API.** All 34 open PRs' `mergeable_state`, reviews and comments were read one by one; no `bun test`, Playwright run or build was executed, and no local branch was diffed against `next`.
- **Room reads are windows, not histories.** `#bugs`, `#todos`, `#meta`, `#roomy`, `#features` and `#general` each returned their full page at the limits above. Absence of a report is absence in the newest page.
