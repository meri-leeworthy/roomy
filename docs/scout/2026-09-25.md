### 2. A jitter draw of exactly 0 permanently and silently disconnects a bridged space — the bridge re-implemented the SDK's backoff without the floor the SDK added after this exact incident

- **Evidence.** The bridge supplies its own reconnect-delay generator — `packages/discord-bridge/src/roomy/live-gateway.ts:141` `reconnectDelay: () => this.#reconnectDelay()`, implemented at `:367-374`:
  ```ts
  const cap = Math.min(base * 2 ** failures, max);
  return Math.floor(Math.random() * cap);
  ```
  `Math.random()` can draw exactly 0, so this returns `0`. The SDK reads a non-positive delay as an **explicit instruction to stop reconnecting** — `packages/sdk/src/sync/connection.ts:913-921`:
  ```ts
  const delay = this.#reconnectDelay(attempt);
  if (!Number.isFinite(delay) || delay <= 0) {
    // The caller's explicit "stop reconnecting" signal …
    this.#log(`Not reconnecting: reconnectDelay returned ${delay} on attempt ${attempt + 1}` …);
    this.#setStatus({ state: "closed", intentional: false });
    return;
  ```
  The SDK's **own** default generator was floored for precisely this, and the comment names the production incident — `connection.ts:301-312`: *"a draw of exactly 0 is indistinguishable from the documented 'return a non-positive number to disable auto-reconnect' signal … an unlucky RNG permanently and silently stopped reconnecting (observed in production: a bridge logged `Closed: code=1006 intentional=false`, then never logged a reconnect attempt again while its process stayed alive and every liveness probe read healthy)"* — `return Math.max(1, Math.floor(Math.random() * cap))`. That fix is `b7d02142` ("never let a zero jitter draw disable reconnect (#192)"); the bridge's generator predates it (`d43a1572`, "#105") and was never updated. Passing an explicit `reconnectDelay` is exactly how a caller opts out of the hardened default.
  The bridge's unit test **pins the zero as correct behaviour** — `src/roomy/live-gateway.test.ts:626` `expect(reconnectDelayMs(0, 1000, 100_000)).toBe(0)` — so CI cannot catch this.
- **Why now.** It is silent, permanent for the life of the process, and indistinguishable from a healthy idle socket on every existing surface (the SDK's own words). **Honest scope: it is latent, not currently firing** — a 30-day Loki query for `"Not reconnecting"` and for `"auto-reconnect disabled"` across all three services returns **0 lines**. - **Scope sketch.** One line in `live-gateway.ts:373` — floor the jitter the way the SDK does (`Math.max(1, Math.floor(Math.random() * cap))`) — plus updating `live-gateway.test.ts:626` so the test asserts the floor instead of pinning the hazard. - **Acceptance.** `reconnectDelayMs` never returns ≤ 0 for any `failures`/`base`/`max`; a test that fails pre-fix (e.g. asserting over many draws, or asserting `>= 1` at `failures=0`); and no `Not reconnecting` line for the bridge in a post-deploy window.

This is the *caller* that opts out of the SDK's fix; it needs no SDK change and the SDK half is already correct.
