### 1. A block list with a repeated subject aborts the whole write, so the user silently keeps every block they just removed

- **Evidence.** `[userBlocks] background fetch failed for <did>: UNIQUE constraint failed: user_blocks.user_did, user_blocks.blocked_did` — **1,964 lines in 24 h and 1,964 in 7 d**, across **11 distinct DIDs**. The two windows being equal is the point: the *first* occurrence anywhere in 7 d is `2026-10-13T22:18:43.335Z`, 15 seconds after the `a17f20a0` boot, i.e. the feature began failing the moment user-blocks Phase 2 reached production — so the whole population is **9.5 hours old**, sustained at 132–317/hour. 133 of the lines are on the build serving now (`f1472c24`), 367 on `437f70fb`, the rest on `a17f20a0`. The mechanism is read on this ref and **reproduced**: `queries/userBlocks.ts:302-336` builds one transaction of `delete from user_blocks where user_did = ?` followed by one `insert` per fetched record, and `db/worker.ts:1189-1219` executes that array inside a single `db.transaction(...)`. `materialization/blocks.ts:169-179` builds one record per PDS record and **does not deduplicate by `subject`** — and a repo can hold two records naming the same account (an old Bluesky block and a new Roomy one, or a re-block). I reproduced the abort in `bun:sqlite` against the real schema: the transaction throws `UNIQUE constraint failed: user_blocks.user_did, user_blocks.blocked_did`, **and the rollback takes the `delete` with it**, so the table keeps the *previous* rows and the `user_block_fetches` stamp is never written. The 11 affected DIDs are real: a direct `listRecords` page walk against each one's PDS finds duplicate subjects in every case I could read — `did:plc:qrt5rykojeg5sbsajbu4zdke` 11,186 duplicates over 16,651 records, `did:plc:avvpb4ypfttlslmobsjqt7qq` 180 over 3,884, `did:plc:qrllvid7s54k4hnwtqxwetrf` 180 over 4,374, and smaller counts on the rest (`did:plc:uwbl4k3tza7eyjv3morkrld2` returns 403 to an anonymous read, so it is unverified).
- **Why now.** The consequence is the one failure mode the feature exists to prevent, in reverse: `replaceBlockRows`' own comment says a stale set "is the safe direction", and a *rollback* is exactly a stale set — but here it is refreshed forever, because the failed fetch also never stamps, so the next read retries and fails again. A user who unblocks someone in Roomy, or blocks the same account twice, keeps the old set indefinitely and **no read path can tell them**. Two of the 11 DIDs are re-fetched hundreds of times a day (the hourly series is flat at 132–317), each attempt issuing a PDS `listRecords` walk over a repo of up to 16,651 records.
- **Scope sketch.** Two changes, both small. (a) **Bound the duplicate before it reaches the transaction**: collapse `fetchBlockRecords`' output to one record per `subject` in `materialization/blocks.ts` (the newest `createdAt` wins, which is the one that describes the current state). The `source` column already exists to record which collection won; it does not need to record both. (b) **Make the write idempotent at the SQL level**, so a future producer cannot reintroduce the abort: `insert … on conflict(user_did, blocked_did) do update set source = excluded.source, created_at = excluded.created_at`, matching the `on conflict` the `user_block_fetches` step already uses. Either alone fixes the abort; together, (a) keeps the fetched set honest and (b) removes the cliff. **A regression test that fails on the current code**: one user, two PDS records naming the same subject, `refreshBlockSet` succeeds and the row count is 1.
- **Acceptance.** A user whose repo holds two records naming the same account fetches successfully — `UNIQUE constraint failed: user_blocks` is 0 on a build carrying the change, the user's stored set equals the deduplicated repo contents, and the fetch stamp advances (asserted by a unit test over `replaceBlockRows` with a duplicate-subject input that fails before the change).
- **Suggested priority:** **P2** — no crash and no data loss, but a silent, permanent correctness failure on the blocking feature itself, on 11 known accounts, on the build serving now.
- **Not already tracked because.** Nothing in the queue names `userBlocks`, `replaceBlockRows`, or the block fetch; `TASK-344`/`TASK-345` are the *read-surface* phases of the same feature (redacting other people's messages at read time and on the live path) and neither touches the fetch-and-store path in `queries/userBlocks.ts`, which is what fails here.
- **In flight as this is written, and it should be read together with this entry.** `sorrel/task-351-userblocks-delete-cost` (`9e1e623f`, PR **#451**, opened `2026-10-14T07:45:39Z`) replaces `replaceBlockRows`' per-record insert with one set-based statement and — in its own words, citing the same measurement — deduplicates by `blocked_did` because "a row per record aborts the insert on the primary key, leaving that account's previous set in place". That is this proposal's mechanism, its fix and its evidence, reached independently. **The worker's diagnosis is correct and the correctness half is done**; what this entry adds on top of it is the log-side proof that the abort is live in production on 11 known accounts (1,964 lines, first at `2026-10-13T22:18:43.335Z`) and the acceptance check stated as a count rather than a unit test. If #451 merges as written, this proposal is closed; if the write-path cost is separated from the dedup, the dedup is the part that must not be dropped.

### 2. Two message-move events abort their whole space's boot rebuild, every boot, for fourteen days

- **Suggested priority:** **P2** — one space, no user-visible crash, but a permanent unbounded boot cost and a space whose projection is known-incomplete, in the class the Rust port's oracle assumes away.
