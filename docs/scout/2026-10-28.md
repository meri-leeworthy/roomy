## Proposals (ranked)

### 1. Client telemetry cannot name the build it came from, so no client fix can be confirmed live

- **Evidence.** Every one of the **11,515** `roomy-app-lite` telemetry records in
  24 h carries `app_version=0.2.0` and nothing else identifying the bundle —
  that value is `package.json`'s version
  (`packages/app-lite/vite.config.ts:17`), constant across deploys. The bundle
  *does* know its commit: `__BUILD_ID__` is inlined at build time and served as
  `/build.json` (`packages/app-lite/src/lib/build-id.ts:12-16`,
  `src/routes/build.json/+server.ts:20`), and its only consumers are the
  persisted-cache version (`src/lib/client.ts:159`) and that route. The Faro
  config sets `app.version = __APP_VERSION__`
  (`src/lib/telemetry/faro.ts:63-68`) and no build attribute. The cost of the
  gap is measurable today: `#555` drops the exact `ResizeObserver loop
  completed with undelivered notifications.` text at the `beforeSend` boundary
  (`src/lib/telemetry/scrub.ts:81-117`), the filter is in the deployed build,
  and yet **38** items with exactly that text arrived in 24 h — **34 from
  Firefox**, 2 Safari, 2 Brave, 1,660 in 7 d. Either those sessions run a
  pre-`#555` bundle (a SPA has no forced update; a long-lived PWA tab keeps its
  JS) or the filter misses a path they take. Nothing in the record can
  separate the two.
- **Why now.** Production is nine commits behind `next` and staging is current;
  both serve `app_version=0.2.0`. Every client-side question in this record
  ("is the `#555` filter live?", "did the `#558` tile change this exception?",
  "which build threw `parentNode`?") is unanswerable for the same reason, and
  the answer is one field.
- **Scope sketch.** Send the build id with the telemetry: add the resolved
  `__BUILD_ID__` to the Faro `app` meta (or a constant `meta`/global attribute
  so it rides every item), and make the collector expose it as a Loki label
  the way the appserver's `build_id` already is (`deploy/alloy/config.alloy`,
  `loki.process` for the Faro path). Do not reuse `app.version`: the version is
  a release number, the build id is the revision.
- **Acceptance.** After a deploy, a Loki query splits client exceptions by
  build (`sum by (build_id) (count_over_time({service_name="roomy-app-lite"} |=
  "ResizeObserver" [1h]))` returns a row per build in the field); the
  `ResizeObserver` residual is attributable to a build rather than guessed at;
  and a client record from a stale bundle is identifiable without asking the
  user.
- **Suggested priority:** **P2**.
- **Not already tracked because.** `TASK-426`/`#552` added `env` to all three
  signals and `TASK-435`/`#564` added it to the collector's browser records;
  neither touches build identity, and `BUILD_ID` exists for the appserver and
  the bridge already, so the client is the one service whose records cannot be
  tied to a revision.

  `api.roomy.space`, `hv.roomy.space` — never a path
  (`packages/app-lite/src/lib/telemetry/scrub.ts:24-45`, which replaces an
  absolute URL with its host by design, because a `getServiceAuth` URL carries
  a signed `exp`/`lxm`). Measured over a 4,344-span sample of the last 24 h:
  p50 **0.52 s**, p90 **1.31 s**, p95 **1.92 s**, p99 **10.06 s**, with **113**

  client's 47 %-failing `getActivityFeed` poll (proposal 3) cannot be tied to a
  browser session.
- **Why now.** The appserver's own view of the same traffic is clean (zero 5xx,
  no trace above 300 ms in 24 h, DB wait p99 14 ms), so the only signal that
  something is slow from a user's seat is this one — and it is deliberately
  blinded. Two client-side questions already open in this record need it: the
  10 s p99, and the 186 client 401s.
- **Scope sketch.** Keep the redaction, recover the identity: for the app's own
  origins, rewrite `event_data_url.full` to `host + pathname` with the query
  string dropped (`/xrpc/<nsid>` carries no secret; XRPC params do), and leave
  every other origin host-only. Any capability that lives in a path, if one
  ever exists, must stay host-only — enumerate the exceptions rather than
  weakening the rule.
- **Acceptance.** A client fetch span for an XRPC call reports
  `api.roomy.space/xrpc/space.roomy.room.getMessages`; a Loki query groups
  client-observed latency and status by endpoint; no query string, ticket or

- **Suggested priority:** **P2**.

  `#549` (CF12) classifies session failures at the appserver, and CF2 is about

### 3. Two clients poll `getActivityFeed` unauthenticated every five minutes, and half of that endpoint's traffic is now 401

- **Evidence.** Production, 24 h: **312** `GET /xrpc/space.roomy.space.getActivityFeed
  failed: Authentication required` lines, each with its paired `scope=app`
  stack, against none in the six days before it (a 7 d read returns 315, all but a
  handful inside this burst). The live
  counters agree: 351 `200`s vs 314 `401`s for `GET` — **47 % of the endpoint's
  calls fail**. The arrival pattern is two fixed timers, not user activity:
  one at `hh:X0:01`/`hh:X5:01`, another at `hh:X1:10`/`hh:X6:10`, giving 24
  requests/hour exactly, from 2026-10-27T18:05:02Z onward with no gap. The
  client already guards the obvious case — `enabled: () => auth.authenticated`
  and `retry: false`, with a comment naming this exact 401 spam
  (`packages/app-lite/src/lib/queries/activity-feed.ts:60-66`) — so the
  requester is a session that *passes* that guard and still fails verification,
  or a non-SPA caller. It cannot be named: `requireAuth` throws the same
  `401 AuthRequired / "Authentication required"`
  (`packages/appserver/src/xrpc/authGuards.ts:57`) whether the request carried
  no credential or an expired one, and the router's failure log carries the
  route and message only (`packages/appserver/src/xrpc/router.ts:337`).
- **Why now.** It is the *only* error class in production this tick — 624 of the
  appserver's 662 production error lines — and it has been running for 13
  hours, unattributed and unrecovered. The endpoint is also one of the four
  cache consumers (CF1: 43 hits / 621 misses / 253 evictions), so a
  permanently-missing caller inflates the cache's miss rate too.
- **Scope sketch.** Two small halves. (a) Make the 401 attributable without
  inventing identity: log whether an `Authorization` header was present and
  the verification outcome (absent / malformed / expired / wrong-audience),
  plus the build id from proposal 1 — no DID, because an unauthenticated caller
  has none. (b) In the client, treat a 401 from an authenticated-looking
  session as session death: hand off to the login path the way CF12 (`#549`)
  proposes, and stop the poll that produced it.
- **Acceptance.** A 401 line in Loki distinguishes "no header" from "expired
  token" as a count; the two five-minute pollers are identifiable as client
  sessions (once proposal 1 lands) or provably not the SPA; and the 24 h 401
  count on `getActivityFeed` falls to zero or to genuine logged-out reads.
- **Suggested priority:** **P3** — not user-visible by itself, but it is the
  appserver's whole production error budget and the evidence CF12 needs.
- **Not already tracked because.** `#549`/CF12 classifies *failed sync
  connects*; this is an HTTP read that keeps succeeding at the network level
  and failing at auth, from a client state that no current log line describes.
