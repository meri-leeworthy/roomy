## Proposals (ranked)

### 1. A tab whose OAuth session is rejected retries it forever: the client never reaches its own recovery path

- **Evidence.** Client telemetry (faro fetch spans) to the HappyView origin over
  the last 7 days:

  | origin | requests | 401 |
  |---|---|---|
  | `hv.roomy.space` | 32,083 | **19,716** |
  | `api.roomy.space` | 23,781 | ~1/day outside the episode below |

  The 401s are not background noise, they are a loop: hourly counts hold at
  **~225/hour (one request every ~16 s)** from 2026-10-30T08:00Z through
  2026-11-02T09:00Z, then again from 2026-11-02T14:00Z to 2026-11-03T17:00Z, then
  stop. **18 distinct sessions** carry them in 7 days; the largest four carry
  887, 638, 345 and 337 each. One of them, `XxGziFGi8H`, is a Firefox tab on a
  room URL with **345 consecutive 401s between 14:52 and 16:19 on 2026-11-03**,
  and in that window the tab emits no other client record at all — no log line,
  no navigation, no reload. The same session then hits
  `[error-recovery] Recoverable ATProto error detected — reloading page in 600ms`
  twice and `no auto-reloads remain — handing off to the login path` at
  16:19:12Z, i.e. the recovery machinery works, it simply never fired for 86
  minutes of continuous failure.
- **Why the recovery never fired.** Recovery has exactly four triggers, all of
  them `scheduleAutoReload`: the TanStack query and mutation caches
  (`packages/app-lite/src/lib/client.ts:87,90`), `init()` failure
  (`packages/app-lite/src/lib/auth.svelte.ts:385`), the window
  `error`/`unhandledrejection` handlers
  (`packages/app-lite/src/lib/error-recovery.ts:324,329`), and one chat-input
  path (`components/chat/ChatInputArea.svelte:452`). A rejected session request
  raised by the OAuth client reaches none of them: the two app paths that do
  touch the session swallow it — `console.warn("Failed to record scope grant:")`
  at `auth.svelte.ts:206` and `console.warn("Failed to fetch profile:")` at
  `auth.svelte.ts:680` — and both of those are the lines the tab emitted, once
  per reload, at 16:19Z.
- **Why now.** This is the client-side shape of the reports in `#bugs` on
  2026-10-28 (fei: "infinitely reconnecting and reloading … after several of
  that pattern, I got logged out") and 2026-10-29 (Zack Brown: "after a minute of
  spinning I got logged out"); both are still unanswered and both still happen —
  the same `Sync connect failed: session expired` → reload → hand-off sequence
  runs at 06:32Z today for a different user. The cost is a tab burning ~4
  requests/minute indefinitely on a session it can never use, rendering from the
  persisted cache `[INFERENCE — the tab's page shows a room deep link and the
  client's `staleTime: Infinity` cache keeps that render alive]`, and the user
  only learns about it when something unrelated trips the reload budget and logs
  them out. The server sees almost none of it: **2** appserver `Authentication
  required` failures in the same 24 h, because a dead session never reaches
  `api.roomy.space` at all — which is why this has never shown up in the
  appserver numbers.
- **Scope sketch.** The seam already exists and is unused: `createHappyViewClient`
  forwards an optional `fetch` into `HappyViewBrowserClient`
  (`packages/sdk/src/browser/oauth.ts:583`), and `sessionOptions()` in
  `auth.svelte.ts:246` does not pass one. Wrap that fetch, count consecutive
  401s (and `status: 0` network failures) **per origin**, and when the count
  crosses a bound — the natural one is a handful of minutes at the observed
  cadence, not the first failure, so a transient HappyView blip does not log
  anyone out — hand the failure to `scheduleAutoReload` so the existing budget
  decides between one more reload and the login path. Add one telemetry counter
  (consecutive session failures, reset on success) so the next occurrence is
  measurable without reading spans.
- **Acceptance.** A unit test that N consecutive 401s from the session origin
  escalate exactly once and that a success resets the count; a test that the
  first 401 does not escalate; and, in production, no session with more than a
  bounded number of consecutive 401s that never produces a reload or a hand-off.
- **Suggested priority:** **P1**.
- **Not already tracked because.** `#549`/TASK-19/TASK-16 all concern what the
  client does *after* it notices a dead session (name the cause, stop spending
  reloads, re-authenticate). Nothing in the queue concerns a session failure that
  is never noticed at all.

## Limits of the evidence

Proposal 1 establishes the loop's rate, duration, session count and the code
path that lets it continue; it does not prove *why* HappyView rejects those
sessions (expired, revoked, and a token-registration failure all 401 alike), and
it cannot name the endpoint being polled, because client telemetry records only
the origin (CF14). The poller itself lives in `@happyview/oauth-client-browser`,
a dependency rather than this repo, so the interception point proposed is the
fetch the SDK already allows to be passed in, not the polling code. The
`~225/hour` cadence and the "one tab" attribution come from grouping spans by
`session_id`; the 7-day per-session counts are truncated by Loki's 3,000-row
limit on the query that produced them, so the top sessions are a floor, not a
total. Whether an affected tab shows the user an error, a stale-data banner, or
a blank room is not in the telemetry and I did not reproduce it.

The queue audit is limited by the same stale snapshot as the previous four runs.
CF21's trend is one route's `duration_ms` series, hourly, over 17 hours; the
`db-slow` counts are a fixed-threshold counter and say nothing about the 40–49 ms
band where the regression started. I have no shell on the production host, so the
host-side storage measurement that would name the regression's mechanism is still
open — and now the only part of TASK-460 that is.
