A Tempo span on one such request ties it to a **room read**: `trace 10e2d1b83eeee424d3a3c1708a204423` → `space.roomy.room.getMessages` **34.8 ms** with `roomy.room_id=01M0M00D2C3VY2Q6SEDGKZDBYA`, `roomy.message_count=2`, and the `defaultGetProfiles` warn shares that trace id. Exporting that room through the CLI shows why: it holds **a message whose `authorDid` is the empty string** (`roomy-export-…-2026-10-13T07-33-45-629Z.json`, row 1: `authorDid ""`, `authorName ""`, `text ""`, `2026-08-22T05:44:57.453Z`; row 2 is a normal did:plc author). The read path hands message DIDs to `hydrateProfiles` → `resolveProfiles` → `resolveFromGlobalDb` → `hydrateMissingProfiles` → `getProfilesRoomyFirst` → `defaultGetProfiles` (`queries/selectMessages.ts:584`, `queries/profileStore.ts:352`, `:310`, `:331`, `materialization/profiles.ts:231`, `:159`), which chunks into 25 and appends each DID as a repeated `actors=` key (`profiles.ts:167`). The empty string survives `allowNetworkFetch` and the negative cache — `isProfileFetchBackedOff("")` is false, since no earlier *successful* lookup resolved `""` — and the appview, probed directly this run, answers the resulting request with `400 {"error":"InvalidRequest","message":"Invalid app.bsky.actor.getProfiles params: …"}`. **The whole chunk is discarded**: a real DID travelling in the same 25-DID batch gets no profile, hence a blank name and avatar wherever it is rendered, and is retried into the same failing request on every subsequent read.
- **Why now.** It is a 274-a-day failure that cannot succeed, on the app's most-used read (`room.getMessages` n=683 for this process), and it is invisible: the request is a raw `fetch`, so it contributes no `roomy_xrpc_*` series, and the only trace of it is a `warn` naming a DID count rather than a DID. Its user-visible half is a blank author on a rendered message; its silent half is the chunk-mate whose profile never arrives. It also explains a standing observation in `TASK-277`'s neighbourhood — "the appserver RETURNS agent name+avatar (verified across every room)" is true for the rooms sampled there and is exactly what this breaks for the rooms it is not.
- **Scope sketch.** Two changes, both small and both in `materialization/profiles.ts`. (a) Drop non-identifier entries before the request: filter the chunk to values that look like an AT identifier, so `""` never becomes an `actors=` key — and log the dropped value once, at `warn`, so the next occurrence names what it dropped instead of a count. (b) Make the `!resp.ok` branch say *what* was rejected: the appview's 400 body carries `Invalid AT identifier`, and today the handler reads only `resp.status`. Whether the *source* of the empty DID is also fixed (a materialiser writing a message row with no author, or a read path that should skip a blank author) is a separate question the worker should answer with the log line from (a) — do not guess it from this report.
- **Acceptance.** `count_over_time({service_name="appserver"} |= "appview returned 400" [1h])` is 0 on a build carrying the change, and a room read that includes a blank-author message still resolves every other author in the same batch (asserted by a unit test on `defaultGetProfiles` with one invalid and one valid DID in the same chunk).
- **Suggested priority:** **P2** — no crash and no data loss, but a permanent 274/day rejection, a silently-blanked chunk-mate, and no user report because the failure mode is an absence.
- **Not already tracked because.** Nothing in the queue names `defaultGetProfiles`, the appview's rejection, or profile batching; `TASK-277` is about avatars whose *blob bytes* are gone at the PDS (a different mechanism, and it is blocked), and `TASK-16`/`TASK-19` are session/JWT paths.

### 2. `Sync topic access check failed for space:undefined` silently ignores a subscription, and it fired twice on the current build four minutes before this run started

- **Evidence.** `2026-10-13T05:39:57.294Z` and `05:40:00.578Z`, `build_id f6fdb80f`: `Sync topic access check failed for space:undefined: undefined is not an object (evaluating 'spaceDid.length')`. Mechanism read on this ref: `packages/appserver/src/sync/handler.ts:279-280` gates a `{type:"sub", topic:"space"}` frame through `#handleTopicSub` (`:341`); `#canReadTopic` (`:397`) calls `this.#db.openSpaceDb(id)` at `:417` — which reaches `hashSpace(spaceDid)` at `packages/appserver/src/db/pool.ts:110` — inside a `try` whose `catch` (`:425-427`) logs and `return false`s. The `spaceDid.length` deref is `pool.ts:52`, and the `undefined` in the message is the frame's own `id`, so the client sent `{type:"sub", topic:"space"}` with no `id`. **What makes it worth a task is the failure mode, not the crash:** a denied topic sub is *always* silently ignored (`handler.ts:276-279` documents this as intentional, matching the mentions topic), so the connection stays open, no error reaches the client, and that user receives no invalidation frames for the space until something reconnects — the client has no way to tell a refused subscription from a quiet room.
- **Why now.** Two occurrences on the build that is running right now, four minutes before this audit — the first on any build since `2026-09-29/30`. It is cheap and bounded, it touches the auth surface, and the shape (an id-less frame reaching a hash that assumes a string) is one guard away from being correct.
- **Scope sketch.** Two independent fixes, either of which closes the crash: (a) reject a `sub` frame whose `id` is not a non-empty string at the message boundary in `handler.ts`, before it reaches the access check — the frame is malformed, and dropping it is the documented behaviour; and (b) make the silent-ignore observable, so a refused space/room subscription is distinguishable from a quiet one (today the client sees nothing either way). (a) is the correctness fix; (b) is what stops the next occurrence from being invisible. Do not change the mentions-topic ignore.
- **Acceptance.** A `{type:"sub", topic:"space"}` frame with no `id` leaves no `Sync topic access check failed` line and does not throw, and a subscription that *is* refused is reported to that connection in a form a client can log.
- **Suggested priority:** **P3** — 17 lines in 30 d, no user report, but the failure is silent on the auth path and the last two fired today.
