## Proposals (ranked)

### 1. A dead session becomes a rejected-request loop that never backs off, and the client never learns it is being rejected

- **Evidence:** client telemetry, 24 h to 2026-11-17T07:05Z —
  `sum(count_over_time({service_name="roomy-app-lite"} |= "status_code=401" [24h]))`
  = **5,415** of 9,231 fetch spans (**58.6 %**), and
  `|= "hv.roomy.space" |= "status_code=401"` = **5,414**, i.e. all but one of
  them on the HappyView origin. Three sessions account for 1,694 rejections in
  the 5,000-line tail of the day (2026-11-16T22:50Z → 2026-11-17T07:01Z):
  `y67` 911 over **4 h 00 m**, median inter-arrival **15.9 s**, p90 27.9 s,
  **max 42 s**; `91iy3` 424 over 1 h 42 m (median 14.0 s); `3cu76k7tj3` 359
  over 1 h 40 m (median 17.0 s). In the same window the server side served
  **264** `space.roomy.sync.subscribe` calls in 5.1 h (one per 69 s) and the
  client logged 11 `[sync] Sync connect failed: session expired,
  please re-authenticate` exceptions — the socket and the refetch fail
  together, and the refetch repeats on every attempt.
- **Why now:** this is the same population of sessions as CF12, but #549
  (merged today, undeployed) bounds **reloads**, not requests: it stops the
  page from reloading, then leaves a tab asking a permanently-rejecting origin
  every 15 s for hours. 5,414 rejections a day is load on the HappyView layer
  that custodies every session, on the battery of every affected client, and
  in the log budget of the one signal that would show the next session bug.
- **Scope sketch:** in the client's query layer, treat a **401 from the
  session-custody origin as terminal for the current session token** — no
  refetch of that key until the token changes, no automatic retry — and give
  the existing recovery path the count (`sessionStreak` already exists from
  #549) so the user sees "your session ended" once instead of paying for a
  loop. Do not change what happens on 5xx/0/network errors: those are
  transient and should still retry. No server change, no protocol change.
- **Acceptance:** a test that a 401 from the session origin yields exactly one
  request per query key per session token (today it yields one per 15 s); a
  test that a 5xx or a status-0 still retries; and a 24 h post-deploy read of
  the same Loki count showing the 401 volume follow the number of dead
  sessions rather than the time they stay open.
- **Suggested priority:** P1 — 58.6 % of every client fetch is a rejection, the
  rate is still climbing (57 % → 58.6 %, 3,054 → 5,415), and the loop is what
  makes a single expired session cost thousands of requests.
- **Not already tracked because:** CF12/TASK-425 is the *classification* of a
  session failure and #549 (now merged) is the *reload* budget; CF14/TASK-448
  names the endpoint in a span, CF17/TASK-450 stops the server rejecting the
  batch profile fetch. None of them stops a client from re-asking a 401.
  There is no backoff, no terminal state for a rejected token, and no counter
  in the client that would show this if the logs were not already counted.

**One proposal this tick.** Everything else the day produced is queue state —
a rewritten branch, 26 conflicts, three deliverables merged and undeployed, a
bridge back from 82 h — not new work. I would rather say that than pad the
list.
