### 1. A permanently-failing link is retried forever: `attempts` has no cap, so 7,634 URLs are parked in a 6-hour retry loop and the embed backlog has not moved in two days

- **Evidence.** `/health/embed` at 07:01Z and again at 07:03Z:
  `{pending 8363, selectableRows 0, parkedRows 8363, backoffUrls 7634, inFlight 0, sweepCycles 5433, sweepThrottled 783, enrichedOk 168, enrichedDefinitive 52, enrichedTransient 23146, backlogStuck true, backlogStuckSince 1790490277776, backlogStuckTransitions 301, lastStallCause "all-parked"}`.
  Lifetime success rate is **168 ok / (168 + 23198 null) = 0.72%**; `enrichedTransient` (23,146) is **99.8%** of every null outcome ever recorded, against 52 definitive. `backlogStuckSince` decodes to **2026-09-25T22:24:37Z** — the stall has held for ~33 hours.
  Code, `packages/appserver/src/embed/enricher.ts:220-224`: `backoffMs` runs the schedule `[1m, 5m, 30m, 2h]` **and then returns a flat `cap` (default 6h) for every attempt beyond the fourth, forever**. There is no attempt ceiling anywhere: `grep -n attempts packages/appserver/src/embed/enricher.ts` returns the `+1` bump at `:251`, the `attempts = 0` reset on the ok/definitive path at `:273`, and the read at `:248-250`, and nothing that ever terminates a URL. Every one of the 23,146 transient outcomes is therefore an unbounded retry; at the 6h cap, 7,634 parked URLs generate ~1,272 fetches/day against hosts that have already failed hundreds of times.
  The classification is the crux: per `sweeper.ts:130-134`, `definitive` covers "page loaded with no OG/oEmbed, **or a stable 4xx**" and leaves the backlog; `transient` covers "timeout / 5xx / 429 / network" and stays. A URL whose host is permanently gone but answers with a timeout or a 5xx can never be classified definitive, so it is retried until the heat death of the process.
- **Why now.** Two of the three signals that would describe this are healthy: `enrichedNull` is `definitive + transient` (`sweeper.ts:514`) so the headline "null" number looks like normal no-OG data, and `selectableRows 0` makes the sweeper report a *parked* queue, which reads as working-as-designed throttling. The only number that says "this never drains" is `lastStallCause "all-parked"` against a `pending` that has not decreased in 33 hours. `#296` (merged, undeployed) makes the stall *gauge* honest; it does not stop the retries.
- **Scope sketch.** Give a transient failure a terminal state. Either cap `attempts` (e.g. after N consecutive transient failures across a bounded total window, settle the row as `definitive`-with-reason so it leaves `pending_links`), or keep retrying but expose the distribution so a permanently-dead set is separable from a slow one — `enrichedTransient` is currently one undifferentiated counter. Do not raise the cap; do not add a second throttle. Surface the attempt histogram or the count of URLs above a threshold on `/health/embed`.
- **Acceptance.** On a build carrying the change, `roomy_embed_pending` over 24h falls, or a `/health/embed` field reports how many parked URLs have exceeded N attempts and how many have permanently-failed hosts — enough that "all-parked" is attributable to a set rather than to the queue.
- **Suggested priority:** **P2** — no user-visible break, but ~1,272 wasted outbound fetches/day and a gauge that cannot distinguish "working through a backlog" from "stuck forever".
- **Not already tracked because.** TASK-197/`#258`, TASK-201/`#270`, TASK-186, TASK-179 and TASK-221 all concern the sweeper's *latch, backoff persistence, gauge and log* — the retry policy itself is `#270`'s delivered behaviour and was never questioned. `#296` (undeployed) is the latch fix, not this.

### 4. The auth-error auto-reload guard fires on per-resource 401s, because its `nsid` exclusion is bypassed by its own message fallback

- **Evidence, client.** `roomy-app-lite` carries `[error-recovery] Recoverable ATProto error detected — reloading page in 600ms. Error: XRPC space.roomy.getFlags failed (401): Authentication required` — **64 lines / 7d**, **7 / 24h**, level `warn`, `sdk_name=faro-web`, with full browser metadata (the sampled line: `page_url=https://roomy.space/`, Firefox 156.0 on Linux). Server-side twin: `GET /xrpc/space.roomy.getFlags failed: Authentication required` — **14 / 24h**, **16 / 7d**, from `handlers/space.roomy.getFlags.ts:27`.
  Code: `packages/app-lite/src/lib/error-recovery.ts` deliberately narrows what may trigger a reload. Its comment states the rule — *"we do NOT auto-reload on generic appserver XRPC errors (e.g. a 401 for a space the user lacks access to) — those have an `nsid` attached … We exclude errors that carry an `nsid`"* — and the first two arms honour it (`if (status === 401 && !nsid) return true; if (errorType === "AuthRequired" && !nsid) return true;`). The **third arm does not**: the `patterns.some(p => p.test(message))` fallback includes `/\bauth(?:entication)?\s+(required|failed)\b/i` and is reached with no `nsid` check at all. The appserver's per-resource `AuthRequired` 401 is thrown with the literal message `"Authentication required"` (`getFlags.ts:27`, and identically at `getConnectionTicket.ts:10`), so every such response matches the regex and reloads the page — the exact case the guard documents itself as excluding.
- **Why now.** A page reload is disruptive (it discards scroll position and any in-progress composer state), and it is being triggered by an error the code explicitly decided not to reload on. The instrument is already correct and cheap; the bug is one missing condition. Volume is modest (7/24h, 64/7d) but the failure mode is a false positive in the arm that exists to *prevent* reload loops — and `MAX_RELOADS = 3 / WINDOW_MS = 60s` bounds the damage only per window.
- **Scope sketch.** Apply the `nsid` exclusion to the message fallbacks as well, or return early when `nsid` is set before reaching the patterns. One condition; no change to the OAuth-class arms, which are the reason the module exists.
- **Acceptance.** A `getFlags` 401 (or any appserver XRPC 401 carrying an `nsid`) no longer schedules a reload, while `TokenRefreshError`-shaped errors still do; a unit test over `isRecoverableAtprotoError` covering both, since the module is already exported and testable.
- **Suggested priority:** **P2** — a documented invariant that the code does not hold, with 64 disruptive reloads/week behind it.
- **Not already tracked because.** No queue entry mentions `error-recovery.ts`. TASK-19/TASK-16 are about *session* auth failures (the genuine class this module should catch) and TASK-180 was a 401 on `getActivityFeed` before auth landed; none concerns the guard's own over-match.

### 7. The invite surface is a dead end for a member in a space with member invites disabled

- **Evidence.** `GET /xrpc/space.roomy.space.getInvites failed: Member-created invites are disabled in this space` — **8 / 24h** (`topk` over `scope="xrpc"`), thrown at `handlers/space.roomy.space.getInvites.ts:49` when the caller is not an admin and `comp_space.allow_member_invites !== 1`.
  The settings page gates correctly: `routes/[space]/settings/invites/+page.svelte:27-33` derives `canViewInvites` from `isAdmin || (isMember && joinPolicy.allowMemberInvites)` and passes it as the query's `enabled`, with an explanatory comment about exactly this rejection. **`lib/components/InviteModal.svelte:19-21` does not**: it enables the same query on `() => open` alone, so any member who opens the modal in such a space issues a request that is a guaranteed 403.
  The dead end is what happens next. The page's `onCreate` is `creating = true; try { await createInvite(spaceId); } finally { creating = false; }` (`+page.svelte:41-47`) — **no catch**, and `InviteModal`'s `onCreate` is the same shape. `createInvite` (`lib/mutations/invite.ts:11`) sends `space.roomy.space.createInvite.v0` through `sendEvents`, so the refusal rejects `onCreate`'s promise; the modal renders "No active invite links." with a live "Create invite link" button and reports nothing when it is pressed.
- **Why now.** It is the same shape as TASK-223 (`#298`, merged 2026-09-26): a refusal the client already knows how to render, surfaced as nothing. The gating predicate required to prevent it already exists twelve lines away in the sibling route.
- **Scope sketch.** Either gate `InviteModal`'s query on the same `canViewInvites` predicate the settings page uses (passing metadata through, or querying it in the modal), or catch the refusal in both `onCreate`s and render the reason the server gave. Prefer the first — the modal should not ask a question whose answer cannot exist — with the second as the backstop.
- **Acceptance.** A member in a space with `allowMemberInvites` false sees no `getInvites` request when opening the modal, and never sees a Create button whose press is silent.
- **Suggested priority:** **P3** — low volume (8/24h), deterministic, and confusing rather than breaking.
- **Not already tracked because.** TASK-161/TASK-202 and `#271` covered invite-query *retry* behaviour; nothing covers the modal's enable predicate or the unhandled `createInvite` rejection.
