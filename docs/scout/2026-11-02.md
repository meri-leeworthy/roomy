### 2. Nothing in the appserver measures statement time, so a 5× latency regression raised no metric

- **Evidence.** The 54 `roomy_*` series Mimir holds include
  `roomy_db_wait_seconds` (a pool-queue histogram), `roomy_db_queue_depth`,
  `roomy_db_open_space_dbs`, `roomy_db_space_cache_kib` and
  `roomy_db_max_space_dbs` — and **no statement-duration series at all**. The
  live `/metrics` confirms it: `roomy_db_wait_seconds{type="query"}` types are
  `query`, `transaction`, `init`, `analyze`, `health`, and each one measures
  time spent *waiting for a worker*, not time *inside* it. The only execution
  signal is the `db-slow` warn line at a fixed 50 ms threshold
  (`packages/appserver/src/db/worker.ts:151`,
  `packages/appserver/src/db/asyncDatabase.ts:213`), which is a counter over a
  threshold, not a distribution — it cannot distinguish "one query got slow"
  from "every query got 5× slower", and it says nothing about the 40 ms–49 ms
  band where today's regression began. That gap is why proposal 1 went unnoticed
  for eleven hours and was only found by sampling Tempo; the same gap is why
  CF2's broken `increase()` had nobody to contradict it.
- **Why now.** A regression that touches every route and every space produced
  **zero** metric movement: `roomy_pool_worker_pending` is 0,
  `roomy_db_timeouts_total` does not exist, and the queue-wait histogram is flat.
  The number is already computed and already on the wire — every `xrpc` log line
  carries `duration_ms` (`packages/appserver/src/appserver.ts:1396`), which is how
  proposal 1 was measured — but it goes to Loki, where nothing aggregates it and
  CF2 makes any Mimir `rate()`/`increase()` over `roomy_*` untrustworthy anyway.
  Meanwhile the discovery method — `db-slow` — now emits a full SQL statement per
  slow query at `warn`, 3,710 lines in 24 h against ~600 before the regression,
  so the one signal that did fire is also a log-volume event.
- **Scope sketch.** Emit `roomy_db_statement_seconds` (histogram, labelled by the
  worker's existing `type` and `targetDb`, **not** by SQL text) from the same
  place `selfMs` is already computed in
  `packages/appserver/src/db/worker.ts:885`, and expose its p50/p90 on
  `/health/pool` beside the queue-wait figures so the two are read together.
  Leave `db-slow` alone — it is a useful tail marker.
- **Acceptance.** `roomy_db_statement_seconds_bucket` appears in the live
  `/metrics` with a real distribution, and a replay of today's regression would
  show its p50 moving while `roomy_db_wait_seconds` stays flat. A unit test that
  fails without the histogram.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No task names DB instrumentation. The closest
  is CF2 (Mimir's label merge), which is about the collector misreading series
  that do exist, not about a series that does not exist.

  is not evidence either way. Recorded so the next run does not treat it as

  abandoned it. Any `quantile_over_time`/`avg_over_time` over the `xrpc` stream
  in `query_range`
  returns `maximum number of series (500) reached` unless wrapped in an outer
  aggregation, and the only outer aggregations available (`max`, `min`) collapse

  same number as `max(quantile_over_time(0.5, …))` — 7,716 ms on 2026-10-30T09Z
  where the mean was 117 ms. The ratio form
  (`sum(count_over_time(… | duration_ms > 100)) / sum(count_over_time(…))`) is
  the one that works, and is what proposal 1 quotes.
