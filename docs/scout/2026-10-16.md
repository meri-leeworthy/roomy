## Proposals (ranked)

### 1. Every message edit and delete full-scans the global `mentions` table, and the delete then looks for rows it has already removed

- **Evidence.** `delete from mentions where message_id = ?` (`queries/mentions.ts:159` on the edit path, `:183` on the delete path) appears in the `db-slow` sample **51 times in 24 h with p50 1,109 ms, p90 1,512 ms, max 1,540 ms**, all on the `global` worker, and **782 times in 7 d with p50 1,234 ms**, of which **542 exceed one second**. `selfMs` equals `totalMs` to within 1 ms on every row — the time is the statement, not the queue. In the 24 h sample that is **51 s of wall time on the shared global worker, 8.2% of all `[db-slow]` wall time**, from a table that is written once per mention.
  **The plan is a full scan.** Explaining the same statement against the real schema in `bun:sqlite` (3,000,000 rows, 482 MB on disk, the schema and the one existing index copied verbatim from `db/schema-global.sql`) gives `SCAN mentions USING COVERING INDEX sqlite_autoindex_mentions_1` — the primary key is `(did, message_id)`, so `message_id` is the second column of the key and a lookup on it alone cannot seek. Measured on that same database: `delete … where message_id = ?` **155 ms**, versus **0.1 ms** for `delete … where did = ? and message_id = ?`, which is a primary-key seek. The 155 ms is the in-memory-and-page-cache-warm case; production's 1,109 ms median is the same scan with a colder page cache and a larger table, which is why the absolute numbers differ and the shape does not.
  **And the same file has a second reader of the same column.** `getMentionedDidsForMessage` (`queries/mentions.ts:251-258`) runs `select did from mentions where message_id = ?` — the same scan, `SCAN mentions USING COVERING INDEX sqlite_autoindex_mentions_1` in the same benchmark, **~150 ms per call**. It is called from `inferSignals`' delete path to emit one `mentionDiff remove` per DID.
  **The second half is a bug, and it is reproduced.** `invalidation/router.ts:105-106` runs `syncMentionsIndex` — which, for a `deleteMessage`, issues the `delete from mentions` — **before** `router.ts:113-117` runs `inferSignals`, whose delete handler calls `getMentionedDidsForMessage` to read those rows back. The rows are gone, so the loop body never runs and **no `mentionDiff remove` is ever emitted for a deleted message**. Reproduced by driving the real `Router` over a seeded `mentions` row in a throwaway test: `await router.onEventsApplied(STREAM, [deleteEvent], {isBackfill:false}, db)` yields **0** `mentionDiff` events and leaves the table empty, while calling `inferSignals(deleteEvent, db)` directly with the row present yields **1**. The existing test at `invalidation/inferSignals.test.ts:965` passes because it seeds the `mentions` row and calls `inferSignals` directly — it tests the reader, not the path the server runs.
- **Why now, and how far it actually reaches.** The cost half is live and paid on every edit and every delete, on the one worker every space shares. The correctness half is currently **unobserved**: the only subscriber to the `mentions:<did>` topic in the fleet is the agent bridge (`roomy-agent/src/index.ts:208`), and it handles only `op.op === "add"` (`:182`, `:200`), discarding every remove op; `packages/app-lite` subscribes to `space:` and `room:` topics only (`routes/[space]/+layout.svelte:95-98`, `routes/[space]/[room]/+page.svelte:128-131`), and no in-tree caller invokes `space.roomy.mention.getMentions`. So the defect's blast radius today is a dead code path and a misleading test — which is exactly why it should be fixed now, while the cost half makes the file worth opening, rather than after a client is built on the frame. A mention of a message that has since been deleted cannot be cleared from a subscriber's list today, and nothing would notice.
- **Scope sketch.** Two independent halves, both small. (a) **Add the index the read needs**: `create index if not exists idx_mentions_message on mentions(message_id)` in `db/schema-global.sql`, following the file's existing `create index if not exists` convention (the surrounding DDL is additive and idempotent on any schema version, and `globalSchemaMigration.test.ts` already asserts the index list is unchanged when a table is re-created). That turns both the delete and `getMentionedDidsForMessage` from a scan into a seek. (b) **Order the two steps so the reader sees the rows**: the delete's `mentionDiff remove` needs the DIDs that existed *before* the rows were removed, so resolve them first — either pass the resolved DIDs into `syncMentionsIndex` (its `opts` already carries `replyToAuthors`, which is the same "resolve once per batch, not per event" shape) or have the router read them before it deletes. Whichever way, the assertion that belongs in the suite is the one that is missing: drive `Router.onEventsApplied` with a `deleteMessage` whose mention row exists, and assert a `mentionDiff remove` comes out.
- **Acceptance.** After the change, `delete from mentions where message_id = ?` no longer appears in `[db-slow]` for a table of any size (asserted in `bun:sqlite` against a seeded table, with `explain query plan` showing a `SEARCH … USING INDEX` rather than a `SCAN`), and a router-level test on a seeded `mentions` row emits exactly one `mentionDiff remove` keyed by the deleted message id.
- **Suggested priority:** **P2** — a live per-write cost on the shared global worker (1.1 s median, 51 s/day in the sampled window) and a reproduced correctness defect on the same three lines. Not P1: nothing user-visible fails today, and the frame that is lost has no subscriber that acts on it.
- **Not already tracked because.** Nothing in the queue names the `mentions` table, its indexes, `syncMentionsIndex`, or `getMentionedDidsForMessage`; `TASK-277` is the profile/avatar path and `TASK-143` is agent-chatter write cost as a general principle.

The worst is a single statement: `selfMs` 7,873 of a 7,874 ms total, on worker `space-6` at `2026-10-16T04:41:13.300Z` — and the request it sat inside was a `sendEvents` that logged `duration_ms 7940`, i.e. a user's write spent 7.9 s waiting on this statement. The hourly series shows where they come from: 1, 2, 5, 8, 5, 4 in the small hours and **13 in the single hour 2026-10-15T15**.
  **The shape is a full re-derivation of every message in the rooms named**, and the caller decides how many rooms that is. Two read paths reach it: `threadActivity.ts:243`'s warm-on-miss calls `rebuildRoomActivity(db, roomIds)` with **the whole page's room set**, and `roomActivityProjection.ts:489` (`readRoomActivityProjectionFor`) calls it with `read.missing` — only the rooms that had no row. The narrow caller is the careful one; the board path is not, so a board whose projection is cold rebuilds every room on it in one statement. The write paths (`materialization/deleteMessage.ts:47`, `moveMessages.ts:124`) deliberately rebuild from the post-event tables and are bounded by the rooms an event touched, which is correct.
  The rows are cold for reasons the module documents and does not bound: a blue-green rebuild invalidates without populating, and a room with no messages never gets a row (`roomActivityProjection.ts:36-46`), so a single quiet room sends the page back to a rebuild on every read until it has one.
- **Why now.** This projector was the fix for the 7.4 s p95 on `space.getThreads` (the 2026-09-22 record's proposal 3, landed as `#244`) — and it is now the third-largest `db-slow` shape by wall time and the cause of the slowest single statement in the window. It is a warm-on-miss whose miss is expensive and whose cost is set by the caller, on the shard that serves the busiest space (`space-3` and `space-6` between them own 60 of the 62). The fix that made the board fast is one unbounded call away from making a write slow instead.
- **Scope sketch.** Bound the warm on the board path to what it can justify: pass the rooms that are actually missing (`threadActivity.ts` already knows them — `readRoomActivityProjectionRows` returns `missing` alongside `rows`, and `fetchProjectedRoomActivity` discards it) rather than the page, so a cold page warms incrementally instead of in one statement. If a page must be covered before it can be served from the projection, cap the warm per read and let the remainder stay on the scan fallback, which is what the projection exists to replace rather than to require. Do **not** change the write paths — their bounded rebuild is what keeps the projection honest after a delete or a move.
- **Acceptance.** After the change, a `space.getThreads` whose projection is entirely cold warms at most N rooms in one statement (asserted by a unit test over a page larger than N), a second read of the same page is fully projected, and the p90 of the `db-slow` row for this statement falls below the 1,134 ms measured here while the fallback scan still answers a page correctly.
- **Suggested priority:** **P3** — no wrong answer is served, and the median is 330 ms; but the tail is 7.9 s, it lands on user writes as well as reads, and the missing bound is a one-argument change at a call site that already has the set.
- **Not already tracked because.** Nothing in the queue names `room_activity`, `rebuildRoomActivity`, `roomActivityProjection.ts` or `threadActivity.ts`. The 2026-09-22 record's proposal 3 was the *deploy* that landed this projector and was closed when the deploy happened; the cost of its warm-on-miss path is new.

### 4. The bridge permanently drops Discord→Roomy messages when the appserver is unreachable, and the 470 it dropped are still unreachable

- **Evidence.** `Discord→Roomy send abandoned after re-offers` (scope `send-retry`, level `error`): **472 lines in 30 d, 470 in 7 d, and 0 in the last 24 h** — i.e. the whole population is still the one afternoon of 2026-10-14, and nothing has been added to it since. 223 distinct `discordId`s, every one abandoned-only (0 appear in the `re-offer landed` set of 147 ids), across all four bridged spaces. The `error` field is a Cloudflare 502 from `api.roomy.space` in 396 of 470 and a 404 in 69. The budget is 8 attempts — `SEND_SWEEP_MAX_ATTEMPTS = 8` with `SWEEP_BASE_MS = 30 s`, doubling and capped at 30 min — so roughly **91 minutes** of wall clock from first failure to terminal, against outages of 1 h 31 m and 2 h 08 m. `getStaleFailedSends` selects `WHERE terminal = 0`, `markFailedSendTerminal` is a one-way door, and the only reader is `GET /sends/failed`, which lists and counts them. There is no path back: the entry's `event_json` is still there, the mapping is still there, and nothing ever offers it again.
- **Why now.** The fix has been written up twice and is still not in the tree; the deployed bridge is 4 merges behind (CF5) so it is not on the way by accident either. Nothing new has been lost since 2026-10-14 — which is the point: the defect is dormant, not fixed, and the next appserver outage of an hour re-creates it at the same rate. The cheap half of the fix is a one-line decision.
- **Scope sketch.** Two halves, and the first is a decision. (a) **Make the budget cover an outage rather than a blip**: raise `SEND_SWEEP_MAX_ATTEMPTS` (with the cap at 30 min the marginal cost of a 24 h budget is 48 extra attempts on an entry nobody is looking at) and stop counting attempts against wall clock rather than failures — the entries above already read `attempts: 11` and `12`, i.e. the counter is also bumped by `enqueueFailedSend`'s `ON CONFLICT … attempts = failed_sends.attempts + 1`, so the budget is consumed twice per failure and the 91-minute figure is an over-estimate of what remains. (b) **Give terminal rows an operator path**: `failed_sends` keeps every field a replay needs (`event_json`, `mapping_key`, `discord_id`, `space_id`, `room_id`), so a `POST /sends/:id/replay` that clears `terminal` and re-offers is enough, and it is the same call the sweeper already makes.
- **Acceptance.** With the appserver refusing `sendEvents` for 3 hours, an incoming Discord message arrives in Roomy once the appserver returns, and `countFailedSends().terminal` is 0. Asserted against the repository layer with a clock the test advances; the 502 body the bridge received is the fixture.
- **Suggested priority:** **P1** — permanent loss of user content, on the deployment serving now, for a failure mode that recurs with every outage of an hour. The count is zero in the last 24 h, which is the only reason this is not the top item.
- **Not already tracked because.** Nothing in the queue names `failed_sends`, `send-retry`, or the bridge's retry budget. `TASK-22` is about embeds in bridged messages; CF7 is about thread *creates* being dropped on the backfill path, which `#406` fixes and which this PR's build does not carry. This is the message path, which `sendEventOrQueue` has been routing through the queue since before the deployed build — the queue works and the budget is too short.
