## Proposals (ranked)

### 1. A refused HappyView fetch is indistinguishable from an empty one, and staging has been refused on every batch for three days

- **Evidence.** Staging, build `58c13d01`, boot 2026-11-17T02:22:22.943Z:
  `scope=happyview profile pipeline enabled (endpoint host: staging.hv.roomy.space)`
  at `:22.864Z`, then `HappyView returned 401 for 2 DIDs` at `:28.6–28.7Z` (5.7 s after boot). Over
  seven days staging has **139** of these warnings, **112 in the last 48 h**
  (90 on 11-19, 22 on 11-20 so far) at 4–7 per hour; production has **0** in the
  same window. `da8cf682` does not contain `#582`'s commit `5a7617db`, so the
  environment that carries the client-key fix is the only one being refused, and
  the environment without it is not.
- **Code.** `packages/appserver/src/materialization/roomyProfile.ts:143-148`:
  `if (!resp.ok)` → one `log.warn` → `continue`, and the caller then falls
  through to a per-DID Bluesky fetch. A globally refused client and a network
  that simply has no record for a DID produce the same silent, uncounted
  outcome. `packages/appserver/src/happyview.ts:71-86` is the header helper
  `#582` introduced; `:57-63` refuses to enable the pipeline without a key, so a
  configured deployment is always sending one.
- **Why now.** HappyView is documented as the first source for every profile
  fetch (`AGENTS.md`, "HappyView"). In staging it has been dead — silently —
  since the day it was deployed, so the QA environment cannot validate the
  pipeline that production is expected to gain, and each profile there costs a
  PDS round-trip per DID instead of a batch.
- **Scope sketch.** Count rejections (a `roomy_happyview_requests_total{status}`
  counter or an equivalent), rate-limit the warn to one per endpoint per
  interval with the status in it, and make "refused" a distinct outcome in
  `getProfilesRoomyFirst`/`ensureProfilesRoomyFirst` so a refused pipeline is
  distinguishable from an empty index. Keep the Bluesky fallback exactly as it
  behaves now. Do not put a key in the repo.
- **Acceptance.** A test that a 401 chunk increments the rejection counter and
  still falls back; the counter is visible in `/metrics`; staging's batch fetch
  returns 200 once its client key is provisioned on `staging.hv.roomy.space`
  (the admin-API step is Meri's, same surface as the OAuth scope allowlist).
- **Suggested priority:** P2.
- **Not already tracked because:** `TASK-450`/`#582` fixed "the batched fetch
  never sends the client key" and shipped. This is the other end of the same
  pipe — the key is sent and refused, on the only build that sends it — and no
  open entry or carried-forward item covers it. CF17 is restated above because
  it is the evidence, not the defect.
