## Proposals (ranked)

### 1. The published client cannot be identified, and the session-death guard merged on 2026-11-05 is not in it

- Evidence: the live bundle at `https://roomy.space` (all 184 precached assets,
  enumerated from `/service-worker.js`) contains `roomy:autoReload` and
  `roomy:sessionExpiryHandOff` and **neither** `roomy:sessionStreak` nor
  `session.consecutive_failures` — the two strings added by
  `packages/app-lite/src/lib/session-health.ts` (`streakKey`, and
  `trackMeasurement` at `auth.svelte.ts:257`), merged as `1a642bb1` on
  2026-11-05. Client telemetry, 24 h: **732** responses were 401 from
  `hv.roomy.space` out of 2,142 requests to it (34 %), across **30 sessions**;
  the worst ran **242 consecutive rejections** from 01:55:44Z to 03:14:43Z
  (79 min, ~800 ms each, ~20 s apart) and the second worst 91. Zero
  `session.consecutive_failures` measurements exist in the same window, which
  is the guard's own telemetry seam.
- Why now: this is the top of CF12's failure class and the guard that bounds it
  is merged, reviewed and idle. A user with a dead session sat on a
  cache-rendered app for over an hour instead of being handed to login. The
  deploy path makes this structural: `.github/workflows/netlify.yml` runs only
  on `workflow_dispatch` and `netlify.toml` `[build] ignore = "true"` stops
  every automatic build, so no merge reaches the site without a human, and
  nothing checks the result.
- Scope sketch: generate a build id at build time (`scripts/build-prod.sh`
  already generates metadata; add a `/build-id.json` beside it carrying the
  commit), and add a job that fetches the live origin's build id and the built
  one and fails when they differ — the same check for the Tauri bundle. No
  change to auth behaviour.
- Acceptance: `curl https://roomy.space/build-id.json` returns the commit the
  site was built from; a CI run deploying an older ref reports the mismatch;
  after the next deploy the guard's `session.consecutive_failures` measurement
  appears in telemetry and stops a repeat of the 242-run.
- Suggested priority: P2.
- Not already tracked because TASK-447 (`#579`) puts a build id **on telemetry
  records the client emits**; this asserts **what the origin serves**, before
  anyone loads it, and covers the deploy step that currently has no check.
  TASK-462/CF28 is the same gap for the appserver.

### 2. Host storage stalls for ~35 s about once every 25 hours, taking every database statement with it

- Evidence: 7 days of production `db-slow`, clustered by 60 s windows:
  2026-11-03T14:12:22 (12 statements ≥500 ms, 55.0 s, max 11,565 ms), 11-04T16:12:17
  (12 / 60.0 s / 10,968), 11-05T17:12:13 (15 / 62.9 s / 8,423), 11-06T18:12:13
  (7 / 38.6 s / 20,431), 11-07T19:12:33 (12 / 48.8 s / 10,596), 11-08T20:12:20
  (7 / 32.2 s / 10,204), 11-09T21:12:13 (17 / 64.1 s / 9,888). The hour
  advances by exactly one each day — a 25 h period — and no other cluster in
  the 7 days has ≥4 statements. In the 11-09 window 17 of 24 rows show
  `selfMs ≈ totalMs` (100 % of wall time inside SQLite) across the `readstate`,
  `events`, `global`, `space-1`, `space-3` and `space-7` workers — separate
  databases, separate threads, one 35 s hole — while `bridge_token_grants`
  (7,543 ms total / 896 ms self) and one `read_positions` (2,986 / 909) show
  only queue wait.
- Why now: the hourly maintenance purge (`appserver.ts:755`, fires at :12 past
  every hour relative to boot) is the only thing in the process on a clock, and
  a stall in its minute has been read as "the purges are slow" (CF26) for two
  records running. Six workers blocked at once on different files is not a
  query plan; it is the storage underneath them, and the process cannot say so.
- Scope sketch: measure the stall instead of the query — `perf_hooks.monitorEventLoopDelay`
  as a histogram, plus a `roomy_db_stall_seconds_total{worker}` counter that
  increments when a statement's `selfMs` exceeds a threshold and other workers
  are also slow, surfaced in `/metrics` and `/health`. No query changes, no
  index changes, no behaviour change.
- Acceptance: forcing a 5 s synchronous block in a test shows one event-loop
  histogram spike and one stall counter increment on every worker; on
  production the next occurrence is visible as a single named stall rather than
  fifteen coincident `db-slow` lines.
- Suggested priority: P2.
- Not already tracked because CF22/TASK-461 (`#598`) adds a statement-time
  metric — that would price the *queries*; nothing measures the interval in
  which no query can run, which is what this window is.

service worker precaches; a lazily-loaded chunk outside that list could hold
code the grep missed (the guard's own strings are in the auth path, which the
precache does cover — `roomy:sessionExpiryHandOff` is found there). It

proposal). The 242-run is one tab's Faro session; the client sends no request
path, so I cannot name the endpoint that was rejecting it.

Proposal 2's period is derived from seven clusters in a 7-day window — 25 h
apart, one each day — and I could not name the job that causes it: the only
in-process hourly timer is the maintenance purge, which would fire hourly, not
daily. The stall is real and its self-vs-total split is unambiguous, but "the
storage underneath" is an inference from six workers blocking at once, not a
measurement of the storage.

Counts from `db-slow` are a floor: the threshold is 50 ms, so a stall of
sub-50 ms statements is invisible. Log-volume counts are instant-query
`count_over_time` over 24 h; an earlier run of this tick's queries used a range
query with a 24 h window at 5-minute steps, which multiplies every count by
288 — the inflated totals were discarded, but any number in this file that
looks 288× too large was read that way.
