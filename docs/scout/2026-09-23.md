### 1. The embed sweeper runs its backlog batch back-to-back with no wait, and its counters say so: 15,170 `enrichedNull` in the first 42 minutes of the deploy, `enrichedOk` still 0

- **Evidence.** `GET https://api.roomy.space/health/embed`, sampled 19× across 07:44–08:00Z and then 18× more across 08:08–08:17Z, on build `824daab9` (uptime 2,055 s at 08:08:46Z → process start ≈ **07:34:31Z**):
  `{"enrichedOk":0,"enrichedNull":885→15170,"pending":5085,"inFlight":0–8,"transientBackoff":2163→4358,"backlogStuck":false,"dbErrorCount":0}`.
  `enrichedNull` climbs **continuously** — 15,170 in ~42 min ≈ **360/min** since process start, and **305/min** over the last clean 471 s window (12,772 → 15,170, ten 45 s samples, no plateau between any two). On the previous build, sampled the same way over the same clock hour, it moved in bursts with flat stretches (`…17433,17433,17433,17433…` for 30 min at a time). `roomy_embed_in_flight` is non-zero on 8 of 8 successive 2-minute scrapes, where before the deploy it read 0 on 20 of 20. `enrichedOk` has not incremented once in 37 samples while `enrichedNull` added 14,285.
  Mechanism, read from this ref: `sweepCycle` returns `pending.length >= SWEEP_BATCH` (`sweeper.ts:682`, `SWEEP_BATCH = 25` at `:55`) and `runSweeperLoop` does `if (full) continue;` (`sweeper.ts:692–693`) — **a full batch skips `waitForWake(IDLE_POLL_MS)` entirely**. A cycle that selects 25 rows and fails all 25 transiently now runs the next cycle immediately. The only thing bounding it is that the 25 selected URLs enter `transientRetry` and are then excluded by `findPendingLinks`'s `where url not in (…4358 placeholders…)` (`enricher.ts:170–181`), so each URL can be re-selected exactly once per backoff window rather than in a tight spin (`enricher.ts:169`).
  The slope is corroborated by `transientBackoff`, which cycles 4,358 → 4,072 → 4,358 inside single minutes: parked URLs leave the backoff set and are re-parked almost immediately, which is only possible if selection keeps running. `enrichedOk` does not appear in `enrichedNull`'s place — it was already 0 before the deploy and has not incremented once in 37 samples.
- **Why now.** `pending` has been 5,085–5,087 without interruption for **31.5 h** (`roomy_embed_pending`, 15-min steps, 09-22 00:48Z → now), so the drain makes no net progress at all; what changed today is that the sweeper spends *more* of the box's time and outbound fetches producing the same result. Each unit of that work is a real outbound HTTP request to a third-party site.
- **Scope sketch.** The `if (full) continue;` is a deliberate latency optimisation for fresh links, so the fix is not to delete it — it is to bound it: yield to `waitForWake` (or a short fixed sleep) between consecutive full batches when the previous batch produced no `ok` outcome, and surface a sweep-cycle counter so the rate is observable. Separately, `statsEnrichedNull` conflates **two different outcomes** (`sweeper.ts:522` definitive no-data, `:529` transient retry) and is the only one of the pair with a metric — there is no `roomy_embed_enriched_ok` gauge at all, which is why "the backlog churns 5×/s and resolves nothing" is invisible except by sampling `/health/embed` twice.
- **Acceptance.** A sweep-cycle counter is exported and shows the rate; `enrichedNull` stops climbing when the backlog is fully parked; and either `ok` increments or a distinct metric separates definitive-no-data from transient-retry so the 0.05% success rate is readable from Grafana rather than by hand.
- **Suggested priority:** **P2** — no user-visible break, but it is sustained outbound traffic and CPU whose entire output is a counter.
- **Not already tracked because.** TASK-186/#248 changed only the *diagnostic* on the stall path (`classifyPendingLinks`, `classifyStallCause`, `lastStallCause`/`lastCycle`, and a new `roomy_embed_selectable_rows` gauge — I read the diff; the behaviour-changing hunks are the diagnostic queries and the removal of the `!backlogStuck` guard, not the selection).
