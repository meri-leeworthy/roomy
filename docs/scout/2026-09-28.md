### 7. A client whose clock is behind sends a message that lands in the middle of the history, on every client

- **Evidence.** Server ordering is by `entities.sort_idx`, a ULID of the message's own timestamp — `packages/appserver/src/materialization/sortIdx.ts`: `const timestamp = overrideExt ? Number(overrideExt.timestamp) : decodeTime(event.id); const sortIdx = ulid(timestamp)`, and the doc comment states the rule: *"Set `entities.sort_idx` for a freshly-created message based on its canonical timestamp… otherwise we use the message's own ULID timestamp."* `selectMessages` orders by it (`queries/links.ts:141` `order by sort_key desc`; `roomy.roomy.room.getMessages` pages on it, per the `#292` fix). The ULID is minted client-side — `packages/app-lite/src/lib/mutations/pending-sends.svelte.ts:73` `String(newUlid())`, `mutations/message.ts:167/215` — so the sort key of a message is the sender's device clock at compose time.
  Reported by a user, with the maintainer agreeing the mechanism is real: **Kai Jellinghaus, Roomy Space `#bugs`, 2026-09-25T15:52:54Z: *"Does roomy have some rules on reordering messages for reply chains or something? Sometimes a new/unread message is somehow not at the bottom. Also saw messages sticking to the bottom for no clear reason?"*** — **Zicklag, 15:54:16Z: *"Right now we trust the client's system time, instead of ordering on the server (we need to fix that), so it's probably just discrepancies between the time on different people's system."*** The parenthetical is the maintainer naming this as a known defect with no task.
- **Why now.** It is a cross-user correctness bug with a maintainer-confirmed cause and a user report, it is durable (the wrong `sort_idx` is written once and never repaired), and it is invisible in every dashboard — the message simply appears in the wrong place on everyone else's screen.
- **Scope sketch.** Stamp the canonical time server-side at materialisation (the appserver already owns the event's ingestion order) and key `sort_idx` on that, keeping the `timestampOverride` extension for bridged messages so Discord backfill still sorts by Discord time — `applyBundle.ts:212` shows that path is deliberate. A clamp against the client's claim would be a second-best fix; a monotonic server stamp is the one that matches the comment's own stated intent.
- **Acceptance.** A message sent with a device clock N hours behind appears at the bottom of the room for every other client, and `sort_idx` for a newly materialised message is derived from a server-side time; a test that a `createMessage` whose ULID decodes to an old timestamp still sorts newest.
- **Suggested priority:** **P2** — durable cross-user message misordering, confirmed by the maintainer, unreported in the queue.
- **Not already tracked because.** TASK-218 fixed the *paging key vs the sort key* (they disagreed, so scroll-back broke). This is the sort key itself being untrusted, which TASK-218's fix correctly left alone.
