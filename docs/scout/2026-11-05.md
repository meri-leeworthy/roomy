## Proposals (ranked)

### 1. Bound the appserver's RSS before it reaches the level its last three replacements happened at

- **Evidence.** The live `/metrics` of production reads
  `roomy_process_rss_bytes 958394368` at 2026-11-05T07:10Z, on a process booted
  2026-11-03T14:12:10Z. The hourly series is monotonic: **843 MB at
  2026-11-03T19:08Z → 957 MB at 2026-11-05T07:08Z**, i.e. **+114 MB in 36 h
  (3.2 MB/h)**, with no plateau at any hour. The process it replaced read
  **973 MB at 2026-11-01T07Z → 1,103 MB at 2026-11-03T02Z** (2.9 MB/h) and was
  replaced the same day. TASK-462's own note records **three prior replacements
  at ~1 GiB**, so the running process is on the trajectory that preceded every
  replacement on record. `[INFERENCE]` — the correlation is the task note's plus
  the two slopes above; the platform's limit is not measured here.
- **Where the memory is, as far as the metrics go.** `/health/pool` reports all
  **8** space workers at `openSpaceDbs: 100` / `maxSpaceDbs: 100` with
  `cacheKib: 512`. The pool does evict (LRU at the cap,
  `packages/appserver/src/db/worker.ts:495-500`), but with every worker pinned at
  100 the resident set is **800 open SQLite handles**, each entitled to 512 KiB
  of page cache — a ceiling of **~400 MB** (`worker.ts:552-554` states the
  `maxSpaceDbs × spaceDbCacheKib` ceiling explicitly), before per-handle Bun and
  SQLite overhead. Nothing reports what the pool actually holds against that
  ceiling.
- **Why now.** At 3.2 MB/h from 958 MB the running process crosses 1.10 GB in
  **~44 h, around 2026-11-07T03Z**. Whether the platform kills it there is
  exactly TASK-462's blocked question; the mitigation does not need that answer,
  and there is no alert between now and then that names memory (CF2, TASK-464).
- **Scope sketch.** Measure, then bound. (a) Take the pool's share first: run
  staging with `maxSpaceDbs` lowered and with idle space DBs closed after an
  idle window, and compare the RSS slope; (b) if the pool is not the growth,
  bisect at boot on staging by disabling one subsystem per restart (search
  backfill, embed sweeper, push evaluator) and compare 6-hour slopes; (c) keep a
  stated headroom number in the crate README. No new metric: `roomy_process_rss_bytes`,
  `roomy_db_open_space_dbs` and `roomy_cache_*` already exist.
- **Acceptance.** A 48-hour staging run whose RSS either plateaus or grows at a
  stated rate with the pool's measured contribution separated from the rest; and
  production reaching no replacement level for seven days.
- **Suggested priority:** **P1**.
- **Not already tracked because.** TASK-462 is the *cause* of the 2026-11-03
  outage, is blocked on Railway access, and is Meri's. This is the mitigation,
  which a worker can execute without it. TASK-464 (alerting) would tell us when
  it happens; nothing in the queue would stop it happening.

### 2. A failed push subscription is logged and forgotten, so the user it happened to never learns notifications are off

- **Evidence.** 13 `[push] subscription failed at subscribe/register:
  AbortError: Registration failed - push service error` records in seven days,
  across **11 sessions and 4 users** (Brave/Linux 6, Chrome/Android 3,
  Brave/Android 2, iOS 1, Chrome/Linux 1). Every one of them had **already
  granted notification permission** — the login path only subscribes when
  `Notification.permission === "granted"`
  (`packages/app-lite/src/lib/push.svelte.ts:258`), so these are users who asked
  for notifications. The failure path returns a typed outcome
  (`push.svelte.ts:330` logs it and returns `{ status: "failed", message }`),
  but the login-time entry point is `subscribeIfAlreadyPermitted`
  (`push.svelte.ts:237`, called from `auth.svelte.ts:299` and `:344`), which
  returns `void` and reduces every non-`ok` outcome to a `console.warn` at
  `:265`; only the settings page surfaces it, through `pushOutcomeMessage`
  (`push.svelte.ts:82`). Nothing emits a telemetry event for the outcome, so the
  population is only visible by grepping `console.error` records. The
  neighbouring product gap is already in `#bugs` (mo, 2026-09-15: the desktop
  shell "says that push notifications aren't supported"), which is a different
  cause and stays a product limitation.
- **Why now.** Every one of those sessions is a user with no notifications and
  no signal, and they cannot distinguish it from "nobody messaged me". The
  browser-side cause (`Registration failed - push service error`, typically a
  Chromium build with no FCM path) is outside this repo; the silence is not.
- **Scope sketch.** In the login path, map the outcome: `failed`/`timeout` →
  record one Faro measurement `push.subscribe_outcome` (status + browser) and
  show a dismissible in-app notice once per session linking to the settings
  page; `denied` is a user choice and stays silent; `ok`/`unsupported` unchanged.
  Retrying on the next login is already the behaviour and stays.
- **Acceptance.** A unit test that the login path surfaces `failed` exactly once
  per session and stays silent for `ok`/`denied`/`unsupported`; in production, a
  `push.subscribe_outcome` series carrying the status, so the next occurrence is
  countable without grepping console records.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No entry in the queue mentions push; the
  only related knowledge is the `#bugs` report about the desktop shell, which is
  a support gap rather than a failed subscription.

## Limits of the evidence

Proposal 1 establishes a slope and a correlation, not a mechanism: I have no
shell on the production host, so whether the growth is SQLite page cache, bun's
allocator, or a leak in one subsystem is separated only by the scope sketch. The
"~1 GiB" replacement threshold is the queue note's, not my own measurement of
the platform's limit, and Railway's memory limit and restart policy are exactly
what TASK-462 is blocked on.

Mimir's *instant* query returned 433 MB for `roomy_process_rss_bytes` at the same
minute the live `/metrics` read 958 MB and the hourly range series read 957 MB.
I trusted `/metrics` and the range series and did not use the instant value;
the discrepancy is not explained.

The deployed-client check is a bundle crawl, not a build id: I followed the
entry points across 164 chunks from `roomy.space` and found no
`session.consecutive_failures`. I confirmed the crawl reaches the auth module it
would have to touch (it contains the two neighbouring auth strings), and the
value is a string literal argument to `trackMeasurement`, so its absence means
the module is not in the bundle `[INFERENCE]` — but a build with a different
entry graph could in principle hide it, which is why CF13/TASK-447 matters.

Proposal 2's population is counted from `console.error` records, because nothing
emits a telemetry event for the outcome. Four users in seven days is the floor:
sessions that never reached the subscribe path are not counted, and the browser
text does not distinguish "FCM unreachable" from "permission blocked in a way
Chrome reports as a service error".
