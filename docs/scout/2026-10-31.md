### 2. One bridged guild's member count has been unreadable for 18 hours, and the capacity cache re-queries Discord on every check instead of backing off

- **Evidence.** `getMemberCount failed for guild 1560354048929038336` appears
  **1,934** times in 24 h and **zero** times in the six days before
  **2026-10-30T13:16:37Z**, the first occurrence; it is still occurring
  (`…T07:00:36Z`). Every failure is paired with
  `capacity: member count unavailable for guild … ; keeping previous decision`
  (**1,935** in 24 h) — together ~54 % of all bridge log lines. The guild is a
  live bridged space (`did:plc:a6rwfky627znbrlxvz7ispfa`, per
  `capacity: enabled sync for …`).
  The wrapped error is opaque: `{"message":"Failed to send request to discord.",
  "stack":"… at makeRequest (…/dist/index.js) … at getGuild …"}` —
  `@discordeno/bot`'s generic wrapper, with no HTTP status or Discord error code,
  so a permanent 404 (guild removed, bot kicked) is indistinguishable from a
  transient failure. Both the provider (`discord/member-count.ts:35-50`, catch →
  `log.warn` → `undefined`) and the other `getGuild` caller
  (`live-discord`, seen once this window at 2026-10-31T06:28:44Z) lose it the
  same way.
  The retry rate is the second half of the defect. The sweep is every 5 minutes
  (`index.ts:244` → `checkAllBridges`), which alone would be 12 failures/hour;
  observed is ~110/hour (5 per 5 min at 23:xxZ, ~2/min at 05:00–06:00Z). The
  cause is in `roomy/capacity.ts`: a fresh cached decision is returned at
  `:235`, but the failure branch returns the **stale** decision at `:245`
  without re-storing it, so `expiresAt` stays in the past and every gate
  consultation (`message-ingestion.ts:211,563,708`, `profile-sync.ts:54,130`,
  seven `backfill.ts` sites) performs a fresh Discord request that fails. The
  exact caller mix producing ~110/hour is not established.
- **Why now.** One bridged space's capacity decision is frozen at its last good
  value (or fail-open if it never had one) for as long as Discord keeps
  refusing, and during that time each of its ingestion path steps spends a
  Discord API round-trip and writes two warn lines. Nothing surfaces it beyond
  those warns, and nothing can say why Discord refuses.
- **Scope sketch.** Record the Discord status/code where the error is wrapped so
  the failure class is visible; on a permanent class (404 `Unknown Guild`,
  403 `Missing Access`) stop re-querying and mark the bridge config so the
  space's state is explicit instead of frozen; on the cache side, re-store the
  fallback decision (or a shorter backoff entry) so a failed lookup does not
  make every gate consultation a network call.
- **Acceptance.** A test that a member-count failure leaves the cached decision
  with a future expiry (a second `check` inside the TTL performs no second
  provider call), and a test that a permanent Discord refusal is logged once
  with its status and not retried per message. After the change, the
  `getMemberCount failed` rate for a failing guild is bounded by the sweep
  (12/h), not by traffic.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No task mentions the member-count provider or
  the capacity cache. `TASK-433`'s "carry the Discord status" scope is the
  webhook-create path (`live-webhook-manager.ts`), a different call site; the
  open capacity PR `#498` changes the appserver's measurement, not the bridge's
  retry behaviour.

### 3. Rotating a phone from landscape back to portrait loses the top bar

- **Evidence.** `#bugs` 2026-10-30T10:10:01Z (fei, maintainer): *"If I turn a
  mobile device sideways and then upright again, the layout shifts and I lose
  the top bar."* Newest message in the channel and the only report since
  2026-10-29; not a duplicate of any open task (`TASK-2` is the PWA chat
  background, `TASK-14` the profile popover).
  The shell sizes itself from a single viewport-derived rule:
  `packages/app-lite/src/lib/components/layout/MainLayout.svelte:255` is
  `height: calc(100dvh - env(safe-area-inset-top))`, with the comment above it
  (`:246-254`) recording that an overflowing panel is exactly what previously
  let "the navbar scroll off-screen" on iOS. The body carries the matching
  `padding-top: env(safe-area-inset-top)` (`app.css:102`) and `overflow: hidden`
  (`:100`), so the pair only stays consistent while the inset and `dvh` agree;
  a rotation is the one moment they can disagree, and the failure mode reported
  is precisely "the top bar is gone".
  Related, in the same mechanism: `app.html:151` wraps the app in
  `<div style="display: contents; padding-top: env(safe-area-inset-top);">` —
  `display: contents` removes the box, so that padding never applies.
- **Why now.** It is a maintainer-reported, deterministic, one-action
  reproduction on the platform that generates most of the remaining bug reports,
  and the same code path has produced this class of bug before.
- **Scope sketch.** Reproduce in a mobile-sized browser with an emulated
  orientation flip, then determine which of the three inputs is stale at the
  moment of rotation (the `dvh` value, the `env()` inset, or the body padding)
  and remove the dependence on a value that does not update on
  `orientationchange`/`resize` — e.g. drive the panel height from a CSS variable
  updated by a resize listener instead of `100dvh`, or use
  `100svh`/`100lvh` explicitly. Do not guess: the fix must be pinned by a
  reproduction. Delete the inert `display: contents` rule while in the file.
- **Acceptance.** With a portrait→landscape→portrait rotation in a mobile browser
  at 390×844, the navbar remains visible and the document does not scroll, at
  both orientations; a unit or e2e test covers the height computation if the
  chosen mechanism has one.
- **Suggested priority:** **P2**.
- **Not already tracked because.** No task, PR or scout record mentions
  orientation or rotation; the report arrived after the last `#bugs` read.
