## Proposals (ranked)

### 1. The staging collector publishes its series as `env="production"`, so every production metric is two processes alternating

- **Evidence:**
  - `roomy_process_boot_timestamp_seconds` has exactly one label set —
    `{env="production", instance="appserver.railway.internal:8080", job="prometheus.scrape.appserver"}`
    — and yet takes two values:
    `max_over_time(…[5m]) - min_over_time(…[5m])` reads **144,927.973 s**, the
    exact distance between two boots, in **158 of the last 168 hourly windows**.
  - `1793715130.654` = 2026-11-03T14:12:10.654Z, the boot of the process
    serving `https://api.roomy.space` (`/health`: `build_id f4413dcf`,
    `uptime 406,125 s` at 07:00:53Z).
  - `1793860058.627` = 2026-11-05T06:27:38.627Z, which is exactly what
    `https://api-staging.roomy.space/metrics` reports for
    `roomy_process_boot_timestamp_seconds`, with `build_id 6bcb375d` on
    `/health` and `env="staging"` on every one of its Loki lines. **The second
    process is staging.**
  - Every other series splits the same way over the same 5-minute windows:
    `roomy_process_rss_bytes` max **1.15 GB** / min **405 MB**;
    `roomy_cache_hits_total` max **16,560** / min **2** (the live production
    endpoint reads 16,556); `roomy_xrpc_requests_total{endpoint="/xrpc/space.roomy.space.getMetadata",status="200"}`
    **55,572** on the live endpoint against **7** in the scraped series;
    `roomy_db_open_space_dbs` sums to 800 on production and 1-5 on the second.
  - Cause: `deploy/alloy/config.alloy:143` labels the scrape from `ALLOY_ENV`,
    defaulting to `"production"`, and `deploy/alloy/README.md` says the staging
    collector must set it to `staging`. The observed staging series say it does
    not — an omission has the same shape as a correct production collector.
  - Consequences, measured now: `changes(roomy_process_boot_timestamp_seconds[1h])`
    = **119**, so the restart alert documented at `deploy/alloy/README.md:209`
    fires continuously on a process that has not restarted in five days; and
    `increase(roomy_cache_hits_total[1h])` = **979,024** against 16,556 hits
    since boot (**59×**), because a scrape that lands on the smaller process
    reads as a counter reset.
- **Why now:** every production metric this loop has quoted is a blend, and
  which half a query returns depends on which scrape the sample landed on. It
  also explains the ~405 MB RSS readings earlier records treated as production's
  (CF23 quotes the max, which is the serving process by luck).
- **Scope sketch:** set `ALLOY_ENV=staging` on the staging collector. Then make
  the failure impossible to repeat by omission: either require `ALLOY_ENV` (a
  blank/absent value drops the target rather than silently claiming
  `production`) or have the collector refuse to publish a scraped series whose
  target reports a different environment. Finally re-derive the two documented
  alerting rules and any cache-hit panel against a single-process series.
- **Acceptance:** `max_over_time(roomy_process_boot_timestamp_seconds[5m]) - min_over_time(…[5m])`
  = 0 on a quiet hour; `count(count by (instance) (roomy_process_boot_timestamp_seconds{env="production"}))`
  = 1; the production RSS series reads ~1.09 GB on every scrape instead of
  alternating with 405 MB; the boot timestamp from `api-staging.roomy.space/metrics`
  appears in no `env="production"` series; `changes(…[1h])` = 0 on a healthy hour
  and >0 within one scrape of a real restart.
- **Suggested priority:** P1
- **Not already tracked because:** TASK-461 measures statement time and TASK-458
  closes the endpoint; neither touches label identity, and no queue entry or PR
  does. It supersedes `#618`'s proposal 1 by supplying the identity and the cause
  that proposal could not establish.

### 2. A push that produces no delivery leaves no record anywhere

- **Evidence:** `/health/push` on the production origin at 07:05Z, unauthenticated,
  uptime 4.7 days: `dispatched 13392`, `deliveredOk 370`, `failed 14`, `gone 2`,
  `skipped 0`, `digestsFired 10`, `queueDepth 0`, `pendingRetries 0`.
  `statsDispatched++` counts evaluated message jobs
  (`packages/appserver/src/push/dispatcher.ts:285`); `deliveredOk` counts
  per-endpoint deliveries (`:413`). Everything between them is decided inside
  `evaluatePush`, and **every** reason it decides not to deliver is a
  `log.debug` line — `hides the author` (`push/evaluate.ts:251`), `level=silent`
  (`:257`), `no read access to room` (`:265`), `no push subscriptions
  registered` (`:272`), `level=quiet` (`:293`), `engaged, not participated`
  (`:302`), `engaged digest pending` (`:308`) — with no counter. `skipped` is
  only incremented for a transport that attempted nothing (`:422`), so it reads
  0 while 13,392 jobs produced 386 attempts.
- **Why now:** "why did I not get a notification" cannot be answered from any
  signal the service emits — the reasons exist and are thrown away at debug
  level. TASK-470's PR `#611` tells a user when their subscription *failed*; it
  cannot tell them their fan-out produced nothing.
- **Scope sketch:** a counter `roomy_push_evaluated_total{outcome, reason}`,
  incremented where each debug line is now, exposed per reason in `/health/push`
  and in `/metrics`; a debug line may stay, but must not be the only record. No
  change to what is delivered.
- **Acceptance:** after one message in a staging space with at least one
  subscriber, `/health/push` names the recipients skipped and why; the sum of
  the new counter's outcomes equals jobs dispatched plus deliveries; a space
  whose only subscriber is `silent` reads as `silent`, not as silence; a space
  where nobody holds a subscription reads as `no-subscriptions`.
- **Suggested priority:** P3
- **Not already tracked because:** TASK-470 is about a failed subscribe at
  login; nothing on the queue is about the delivery fan-out. No PR touches

### 4. The sign-in field accepts `@user@host` and fails with "Could not resolve handle"

- **Evidence:** `GET /xrpc/space.roomy.auth.getLoginScope` → 404
  `Could not resolve handle: @crr@fe.disroot.org` at 2026-11-07T12:06:04Z
  (production, `packages/appserver/src/handlers/space.roomy.auth.getLoginScope.ts:51`);
  the client half of the same attempt is in `roomy-app-lite`:
  `oauth sign-in failed OAuth sign-in failed at resolution: Failed to resolve
  handle: @crr@fe.disroot.org`. The handler passes the string straight to
  `idResolver.handle.resolve(handle)` with no normalization, so the Mastodon
  form (`@user@host`) can never resolve.
- **Why now:** one session in 24 h, so this is raised on severity rather than
  frequency — the failure is total for that user (sign-in cannot proceed) and the
  message does not name the form the app accepts. Recorded honestly: a scout
  should drop it if it does not recur, and it costs a few lines either way.
- **Scope sketch:** normalize at the handler — strip one leading `@`, and if the
  remainder contains another `@`, return a 400 naming the accepted form
  (`handle.domain`) instead of a resolution failure. Apply the same normalization
  to the client's identifier field so the request never carries the bad shape.
- **Acceptance:** `@alice.bsky.social` resolves to a DID; `@alice@bsky.social`
  returns a 400 whose message names `handle.domain`; the client renders that
  message verbatim.
- **Suggested priority:** P3
- **Not already tracked because:** no queue entry or PR touches handle
  normalization at sign-in.

  answer every time because those watermarks name rooms whose timeline no longer
  reaches them (`packages/appserver/src/db/readStateWatermarks.ts:66-80`,

  the same statement.
- **`/other` and `/other/xrpc` 404s** — 1,459 and 434 since the 2026-11-03 boot

- **`status="0"` on `sync.subscribe`** (3,626 since boot, all inside the 10 ms

- **`search.messages` p50 1 s / p99 10 s** — 21 requests since boot. Real

- **The 23 `capacity: … pairs are failing open` lines** — by design

## Honest limits

- Proposal 1's identity is established from public endpoints and exact value
  equality (boot timestamps, cache-hit counters, open-DB counts), not from the
  staging collector's configuration, which lives on Railway. What remains
  unverified is *why* `ALLOY_ENV` is unset there — a missing variable and a
  mis-set one are indistinguishable from here.
- The Faro side of the same defect is real in the config (`ALLOY_ENV` labels
  browser records too) but **no staging browser session appeared in 24 h**, so
  that half is a latent defect, not an observed one.
- Proposal 2 cannot say whether 13,392 jobs → 386 attempts is healthy (few
  subscribers) or broken (fan-out collapsing), which is precisely the point; the
  ratio is not evidence of a defect and is not presented as one.
- Proposal 3's percentiles come from 65-94 self-selected samples over 24 h, not
  a synthetic load, and the "boot work, not payload" split rests on a single
  measurement of the deployed assets.
- `db-slow` is a fixed 50 ms threshold, so every count in the log findings is a
  floor, not a population; and the `Mimir` series quoted anywhere above are the
  blended ones until proposal 1 lands — CF23 quotes the *max* of each window for
  that reason, which is the serving process only by luck of ordering.
