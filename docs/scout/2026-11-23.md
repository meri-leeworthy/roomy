## Proposals (ranked)

### 1. Put a deadline on the search sweeper's page query

- Evidence: production `db-slow`, 7 days, complete set of **190** statements at
  ≥ 1 s (the `≥ 1000 ms` count and the returned set agree). **6** of them are
  `SWEEP_SQL` — the sweeper's page query, `search/backfill.ts:41-52` — and those
  six account for **119 s** of blocked worker time: **28,763 ms**
  (2026-11-17T03:52:44.066Z, `space-7`,
  `did:plc:mzivbo4zvwilpxe7mskmeqkz`), 23,308 ms
  (2026-11-19T05:28:26.175Z, `space-2`), 18,618 ms
  (2026-11-21T07:28:26.482Z, `space-3`), 16,817 ms
  (2026-11-18T04:52:44.421Z, `space-2`), 16,383 ms
  (2026-11-22T08:28:26.547Z, `space-5`) and 15,102 ms
  (2026-11-20T06:28:26.306Z, `space-6`). In every one, `selfMs` equals
  `totalMs` — the worker was inside the statement, not queued — and the
  0-row branch that follows (`backfill.ts:261-283`) then logs
  `cursor: "", rows: 0` for that same space at the same millisecond, i.e. a
  query that returns nothing can occupy a worker for 28 s. In the last 24 h the
  statement ran **152** times (45.1 s total, p50 202 ms, p90 619 ms, 1 ≥ 1 s):
  it is routine, cheap when nothing is stuck, and unbounded when something is.
- Why now: `db-slow` fires at a fixed 50 ms and nothing above it is bounded —
  this is the same class as TASK-105's "there is still no per-job timeout". A
  28 s synchronous SQLite call on a space worker also stalls the reads that
  worker is serving, and the sweeper retries the same space a minute later.
- Scope sketch: give the page query a wall-clock deadline — the cycle already
  has `IDLE_POLL_MS` and a per-space re-index budget (`SPACE_REINDEX_BUDGET_MS`,
  for the synchronous XRPC path), so a third bound for the background cycle is
  the same shape. On expiry, log one warn naming space + elapsed and skip the
  space this cycle; the cursor is untouched, so the next pass retries. Do not
  change the rotation, the cursor semantics or the plan.
- Acceptance: 24 h after deploy, no `db-slow` record for `SWEEP_SQL` above
  `1,000 ms` in Loki, and a synthetic test that a slow page query is abandoned
  at the deadline with the space's cursor unchanged.
- Suggested priority: P2.
- Not already tracked because: CF36 is about how *often* the sweeper runs (don't
  open caught-up spaces); `#632`/`#630` are about the maintenance tick's
  statements; `#625` is stall instrumentation. Nothing names the sweeper's own
  query as unbounded, and the mechanism for the 15–28 s spikes is *not*
  established — four of the six land within a second of the maintenance tick's
  statement but two do not, so the proposal bounds the statement instead of
  claiming a cause.

  that would name the status is what `#590`/TASK-455 adds.
