## Proposals (ranked)

### 1. A device clock ahead of the server is a permanent session failure, and the client answers it with three reloads and a logout without ever naming the clock

- **Evidence.** `roomy-app-lite` telemetry, 7 d: **79** lines carrying `DPoP
  proof` — 58 `Error: DPoP proof iat is in the future` and 7 `DPoP proof expired`,
  the rest being the same error re-thrown by the profile fetch, the scope-grant
  record and the recovery handler. 73 of the 79 fall on 2026-10-25; the errors
  come from **7** browser sessions on three OSes (Windows 10, macOS 10.15,
  macOS 10.15.7). The recovery path then does exactly what it does for a
  refreshable token: **13** `[error-recovery] Recoverable ATProto error detected
  — reloading page`, **5** more for the `expired` variant, and **1** `… no
  auto-reloads remain — handing off to the login path`. Alongside them, **15**
  `Failed to record scope grant` and **15** `Failed to fetch profile` carry the
  identical error, i.e. every surface fails at once.
  The client has no clock-skew branch anywhere: `isRecoverableAtprotoError`
  (`packages/app-lite/src/lib/error-recovery.ts:66-117`) classifies on
  `status === 401 && !nsid` and on four message patterns, none of which name a
  clock; `DPoP proof iat is in the future` reaches the recoverable branch only
  because it is a bare 401. The reload it schedules re-runs `init()` → session
  restore (`packages/app-lite/src/lib/auth.svelte.ts:366-373`) against the same
  skewed clock, so all three reloads are known-futile before the first one
  starts. The hand-off (`error-recovery.ts:229-258`) then signs the user out.
- **Why now.** For the affected client this is total lockout with no explanation:
  the visible sequence is "the page reloaded three times, then I was signed out".
  The cause is a client-side fact the client can detect and describe, and the
  same classifier already has the vocabulary to do it (`error-recovery.ts` keeps
  a named list of unambiguous "session is dead" classes).
- **Scope sketch.** Add a non-recoverable classification for the DPoP clock
  failures, matched on the HappyView 401 body or on the message, and route it to
  a user-visible notice ("your device clock is ahead of ours by ~N") with a
  reload affordance, instead of `scheduleReload`. Do not spend the reload budget
  on it. If the failure is small skew rather than a wrong clock, a single retry
  with a server-derived timestamp is the alternative worth considering — but the
  notice is the minimum.
- **Acceptance.** A unit test on the classifier that fails pre-fix (a `DPoP proof
  iat is in the future` error is not "recoverable"); and a forced clock skew of
  +5 minutes against a built client produces the clock notice, **no** automatic
  reload, and **no** hand-off to the login path.
- **Suggested priority:** **P2**.
- **Not already tracked because.** `TASK-16` is the "Token was not issued to this
  client" message and `TASK-19` is a false "Not authenticated" right after login;
  neither mentions DPoP, clock skew, or the reload budget. Nothing in the 12 open
  tasks or the 17 open PRs names `error-recovery.ts`.

### 2. Session death is the client's largest failure class, every cause collapses into one unattributable string, and the recovery path spends three reloads and a logout on it

- **Evidence.** `roomy-app-lite`, 7 d: **620** lines matching `session expired,
  please re-authenticate`, from **36** distinct `session_id`s — 1, 8, 7, 6, 8, 1,
  4 and 1 sessions per day from 2026-10-19 to 2026-10-26. **19** of those sessions
  reached `[error-recovery] … no auto-reloads remain — handing off to the login
  path`, i.e. the user was signed out. Alongside them: **146** `[sync] Sync
  connect failed: session expired…` (14 in the last 24 h), and on the server
  **17** `getConnectionTicket` 401s and **10** `sync.subscribe` 401s over the
  same 7 d. One session shows the shape in 53 seconds: 8 sync failures, 8 profile
  fetches, 8 scope-grant records, 5 reloads, 1 hand-off
  (session `ZNRf3MaYuC`, 2026-10-25T16:41:00–16:41:53Z).
  The string itself is not in this repo — `git grep` over `origin/next` finds no
  such text, and no module constructs it — so the throw site is in the deployed
  HappyView session layer (stack frame `at call (…:17:…)`). Everything downstream
  of it is ours, and it is the part that turns a dead session into 3 reloads and
  a sign-out.
  The community has named the same class once: Muni Town `#todos`,
  2026-09-14T19:41Z, Zicklag — *"We've got to figure out why people are getting
  these errors: console.error: Failed to send message: Error: The session was
  deleted by another process … It might be why our session length is not what
  we've expected."* That hypothesis (a refresh-token rotation race between tabs
  or devices) has never been turned into work, and the current browser layer
  cannot rule it in or out: `packages/sdk/src/browser` contains neither
  `navigator.locks` nor a `BroadcastChannel`, so two tabs refresh independently.
- **Why now.** It is the single largest client failure class in the corpus (620
  lines against 271 ResizeObserver and 164 cache discards), it costs the user a
  re-login, and it is the one class where every occurrence is currently
  indistinguishable from every other cause: a clock skew, a rotation race, a
  refresh 401 and a server-side expiry all read as the same sentence. Without
  cause attribution, no fix can be aimed and no fix can be measured.
- **Scope sketch.** (a) Classify at the source: carry which failure it was
  (DPoP clock, DPoP expired, refresh 401, "deleted by another process", absent
  session) into the diagnostic and the Faro message, so the corpus becomes
  countable. (b) Do not spend the reload budget on a failure a reload cannot fix
  — one reload at most, then the notice and the sign-in affordance. (c) Test the
  rotation hypothesis with a two-tab case; if it reproduces, coordinate refresh
  with `navigator.locks` (or a `BroadcastChannel` hand-off) in the browser OAuth
  layer, both in `packages/sdk/src/browser/oauth.ts` and its HappyView branch.
- **Acceptance.** After the change, a 7 d window still shows the failures (that
  is fine) but each one carries a cause, and hand-offs to the login path fall
  below one a week; and a two-tab test where tab B's refresh does not invalidate
  tab A (fails pre-fix if the race is the cause).
- **Suggested priority:** **P2**.
- **Not already tracked because.** `TASK-19` is a *false* "Not authenticated"
  that fires before a session exists (`packages/app-lite/src/lib/arbiter.ts:17`
  throwing on a null agent) and `TASK-16` is one specific OAuth error message's
  wording. Neither covers a session that dies mid-use, and no open PR touches
  `error-recovery.ts` or the browser session layer.

  (`packages/app-lite/src/lib/mutations/push-preferences.ts:16-21`), so a 400

  event, no user report, no reproduction.

  string is deliberate: `packages/sdk/src/cache/persister.ts:91-101` states that
  `state` is carried across verbatim, without checking that it still means what
