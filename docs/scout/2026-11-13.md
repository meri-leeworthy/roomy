## Proposals (ranked)

### 1. Give the hourly maintenance purges an index, so one cold scan cannot block the read-state worker for 30 seconds

- Evidence: the sixth stall cluster ran **2026-11-13T00:12:38.999 →
  00:12:48.330Z**. Its longest statement is the maintenance tick's delete —
  `delete from user_thread_activity where last_active_at < ?`, **29,962 ms self
  / 29,963 ms total** — and the tick logged
  `[maintenance] purged 3 stale user_thread_activity rows` at **00:12:40.998Z**,
  **30.2 s after its nominal `:12:10.65` firing** (boot 1793715130.654 +
  hourly), against 6 s and 9 s on earlier occurrences. The rest of the window is
  queueing behind it: on the same `readstate` worker,
  `select did, granted_at from pro_role_grants` 29,450 ms total / 1,002 self,
  `insert into read_positions` 18,942 / 3,507,
  `select count(*) … from push_subscriptions` 17,452 / 895,
  `select f.key from feature_flags` 15,439 / 1,904 — **73.9 s of their 81.3 s
  spent waiting**. Across seven days the same delete costs **79, 83 and 63 ms**
  on ordinary hours and **2,071, 9,285, 29,962 ms** on stall hours; the
  thread-backfill purge (`delete from user_thread_backfill where completed_at
  < ?`) measured 3,005 ms and 4,225 ms on two stall days and 63 ms otherwise.
  Neither predicate can use an existing index: `user_thread_activity` carries
  `idx_user_thread_activity_user (user_did, last_active_at desc)`
  (`packages/appserver/src/db/readStateSchema.sql:93-94`) and
  `idx_user_thread_activity_user_space` (v7 migration,
  `readStateVersions.ts:102`), both leading with `user_did`;
  `user_thread_backfill` has only its `(user_did, space_did)` primary key
  (`readStateSchema.sql:122-126`). The six clusters are 25 h apart (11-07T19:12,
  11-08T20:12, 11-09T21:12, 11-10T22:12, 11-11T23:12, 11-13T00:12), so the
  trigger is outside the process — but the statement that pays for it is ours,
  and its cost is a scan of pages that may or may not be resident.
- Why now: six occurrences, the maximum growing 10.6 s → 29.2 s → 30.0 s, and
  the 2026-11-11 occurrence produced the process's only two 5xx since boot.
  Every read-state read queues behind the purge while it runs.
- Scope sketch: two additive indexes declared in
  `packages/appserver/src/db/readStateSchema.sql` — the file is exec'd on every
  open, which is the precedent already used for `idx_read_positions_room` at
  `:82` ("purely additive and idempotent, so it is safe to declare here for
  every version") — one on `user_thread_activity(last_active_at)` and one on
  `user_thread_backfill(completed_at)`. No change to either statement, to the
  timer, or to the read-path queries.
- Acceptance: a test asserting `explain query plan` for each purge does not
  contain `SCAN user_thread_activity` / `SCAN user_thread_backfill`; after
  deploy, the next `:12` occurrence should show the tick finishing in
  milliseconds and the `readstate` queue empty, or — if it does not — the
  remaining cost is proven to be I/O and belongs to the host, which is what
  `#630` and `#625` then report.
- Suggested priority: P2.
- Not already tracked because: `#630` (TASK-484) measures the tick and `#625`
  (TASK-481) measures stalls, but neither changes the scan; no PR adds either
  index.

### 2. Scope the backfill commands to the pair they name instead of walking every bridged channel

- Evidence: `runBackfill()` takes only `(discord, repo, roomy)` and always walks
  `repo.listAllBridgeConfigs()` (`packages/discord-bridge/src/services/backfill.ts:238-247`),
  plus `ensureRoomyRooms`, `syncInitialStructure`, `enumerateBackfillWork` and a
  per-space archived-thread sweep for all of them. The four slash-command call
  sites pass no filter (`slash-commands.ts:718`, `:933`, `:1003`, `:1391`).
  Observed live: one admin session at 06:20–06:28Z — connect, disconnect,
  reconnect, then `Reset cursors for 10 channels, starting full re-backfill` —
  produced **four** completed runs (`Phase-2 backfill complete: 2191 succeeded`,
  06:29:58Z; `2191`, 06:36:31Z; `2208`, 06:42:19Z; `2208`, 06:48:11Z) and four
  archived-thread sweeps (`Archived thread backfill complete` ×4, 06:36–06:53Z).
  That is **8,798 already-terminal (channel, space) pair walks**, **8,566
  `Channel … already complete; skipping` info lines** — 9,203 bridge lines in 26
  minutes against a 60–240/hour baseline — and, per sweep, 33 Discord
  `getPublicArchivedThreads … 403 Missing Access` errors, with a 1 s delay
  between parent channels (`backfill.ts:1548`).
- Why now: the cost scales with the fleet, not with the command's target, and
  the log flood is the only reason the bridge stream was unreadable for half an
  hour. TASK-142 already records noise reduction as a standing principle; this
  is the largest single instance since it was recorded.
- Scope sketch: give `runBackfill` an optional scope — a `spaceDid` and/or a set
  of `channelId`s — and pass it from the four slash-command sites; keep the
  unscoped call at boot (`index.ts:258`). `enumerateBackfillWork`,
  `ensureRoomyRooms`, `syncInitialStructure` and the archived-thread sweep all
  take the same filtered config list. The per-pair skip log drops to `debug`
  and each run logs one summary (`skipped N complete pairs`) instead of N lines.
- Acceptance: a test that a scoped run touches only the named pair's progress
  rows (and emits one skip summary); a live `/roomy-backfill` in one channel
  should log one `Phase-2 backfill complete: N succeeded` with N equal to the
  reset channels, not 2,191.
- Suggested priority: P3.
- Not already tracked because: TASK-143 is about agent-chatter write cost in the
  appserver, and no queue entry covers the bridge's backfill fan-out or its
  per-pair skip log.

## Considered and rejected

- **Raising the per-connection page cache as the stall fix** — `/health/pool`
  reports `cacheKib: 512` per worker, which is why a cold full scan is
  catastrophic, but the cache budget is exactly what `#617` (CF22) re-derives in

## Honest limits

The stall-to-tick correlation is now stronger than a coincidence but still not a
cause: six clusters 25 h apart cannot be produced by an hourly timer, so
something outside the process has that period, and the purge is the statement
that happens to be running when it lands. What today adds is that the purge's
own cost varies 375× between ordinary and stall hours for identical SQL against
identical data, which is a property of *scanning* rather than of the statement's
result — hence the index, which is cheap and bounded either way. If the next
occurrence still shows a 30 s tick, the index has ruled the scan out and the
remaining owner is the host.

The row count of `user_thread_activity` in production cannot be read from any
endpoint, so the scan's absolute size is unknown; the 375× spread is the
evidence, not a page count.

Proposal 2's 2,191-pair figure is one run's own summary line; the 8,798 total
assumes the four runs each walked the full set, which their four
`Phase-2 backfill complete` lines and the 8,566 skip lines (≈2,141 per run)
support but do not prove — a scoped run would have printed a smaller N and I saw
none.

Production figures come from the public `/metrics` endpoint because Mimir
carries a different process under the same labels (CF26). `db-slow` counts are a
floor at a fixed 50 ms threshold, and the 7-day cluster analysis used only
statements ≥ 500 ms, so a stall made entirely of 400 ms statements would not
appear. The published bundle is dated by marker strings, not by a build id —
nothing serves one (TASK-480 / `#626`). The community rooms are unchanged
except Muni Town #roomy, whose two new messages (a question about chat-as-MVP
and the "shelved?" question) are reactions to the freeze, not reports.
