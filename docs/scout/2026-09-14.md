### 1. Bridge Roomy→Discord forwards, which are silently dropped since forwards became createMessage attachments

- **Evidence**: app-lite has emitted forwards as `createMessage` + `space.roomy.attachment.forward.v0` since `294867b9` (#53) / `ab57dab6` (#75) — see `app-lite/src/lib/mutations/message.ts:204` (`forwardMessage`) and `mutations/thread.ts:60` (`createThread`). The bridge's `#extractAttachments` (`discord-bridge/src/services/roomy-event-router.ts:437-490`) handles only `attachment.reply.v0`, `.image.v0`, `.video.v0`, `.file.v0` and `continue`s past every other `$type`, so `forward.v0` is discarded; a forward with no commentary then hits `content === "" && files.length === 0` and is skipped at `:354-359`. `grep -rn "attachment.forward" packages/discord-bridge/src` → **0 hits**. The legacy `#handleForwardMessages` (`:810`) still exists but nothing emits `space.roomy.message.forwardMessages.v0` any more.
  Community: Zicklag 2026-09-11T17:58Z (#todos) "the forwards aren't bridged like they used to be"; Meri 2026-09-11T06:09Z (#todos) "looks like ur forwarded message didn't get bridged to discord Fei (note to self)".
- **Why now**: multi-select forwarding shipped and was announced on 2026-09-11 (#general/#roomy), so users are producing forwards today and every one of them that lands in a bridged room is dropped without a trace. Silent content loss in a shipped feature.
- **Scope sketch**: discord-bridge only. Resolve `attachment.forward.v0` targets to Discord message ids in `#extractAttachments` (the `#repo.getDiscordId(spaceDid, "message", …)` lookup already used for replies), and render them through the existing faux-forward path (`#forwardMessageBatch` / `#buildReplyPrefix`) rather than as a new renderer. Backfills will re-deliver the affected events, so no repair job is needed.
- **Acceptance**: forward a message in a room bridged to Discord; the forward appears in the Discord channel. Unit test: a `createMessage` carrying an empty body + `attachment.forward.v0` is no longer skipped and produces a faux-forward send.
- **Suggested priority**: P2.
- **Not already tracked because**: TASK-22 (link embeds), TASK-24 (thread system messages), TASK-25 (channel mentions as links) and TASK-30 (faux-reply snippets) are four other bridge gaps; none covers `attachment.forward.v0`.

### 2. `TokenRefreshError` is invisible to the auto-reload recovery, so a dead session wedges the app

- **Evidence**: `error-recovery.ts` exists to reload the app when an ATProto session dies (`"In the installed PWA there is no way to manually reload, so this is a breaking issue"`). Its `recoverableNames` check (`error-recovery.ts:39-56`) matches on `err.name`. `TokenRefreshError` never sets `this.name` (`node_modules/@atproto/oauth-client/dist/errors/token-refresh-error.js` — only `sub` is defined), so `err.name === "Error"` and the resolved name is `"Error"`: the class list can never match. The message fallbacks do not cover it either — `"The session was deleted by another process"` matches neither `/token.*(refresh|revok|invalid|expired)/i` nor `/session.*(expired|revoked|invalid)/i`. Verified by executing the matcher against a real constructed `TokenRefreshError`: `isRecoverable=false`.
  Log: `{service_name="roomy-app-lite"} |= "session was deleted"` → **17 events / 7 days**, including 8 `console.error: Failed to send message: Error: The session was deleted by another process` and the user-visible failure it names.
- **Why now**: this is the exact failure mode the module was written to prevent, and it is the third distinct member of the auth-failure family (TASK-16, TASK-19) — all three are "an auth failure strands the user". Low frequency, but when it fires the only recovery is a manual reload the PWA user may not have.
- **Scope sketch**: `app-lite/src/lib/error-recovery.ts`. Match on `constructor.name` (which *is* `"TokenRefreshError"`) in addition to `err.name`, or add the session-getter messages to the message fallback list. Add the test file app-lite currently lacks for this module.
- **Acceptance**: unit test — `isRecoverableAtprotoError(new TokenRefreshError("did:plc:x", "The session was deleted by another process")) === true`; and it must still return `false` for an appserver XRPC error carrying an `nsid` (the deliberate narrowness at `:60-72`).
- **Suggested priority**: P2.
- **Not already tracked because**: TASK-16 is a specific PDS "Token was not issued to this client" message with auto-reauth, TASK-19 is a post-login race; neither is about the recovery matcher failing to fire.

### 4. The invite modal fetches `getInvites` on mount for every space, turning a 403 into the largest error source in the appserver

- **Evidence**: `SpaceSidebar.svelte:792` renders `<InviteModal>` whenever `spaceId` is set — not when `openInviteModal` is true. `InviteModal.svelte:16` calls `createInvitesQuery(() => spaceId)` at component init, and `app-lite/src/lib/queries/invites.ts` sets no `enabled`, so the query fires on mount. `/space.roomy.space.getInvites` then 403s for every non-admin member of any space with `allow_member_invites` off (`handlers/space.roomy.space.getInvites.ts:40-51`). TanStack's default is `retry: 3` (`@tanstack/query-core/retryer.js:86`) and `app-lite/src/lib/client.ts` does not override it, so each mount costs up to 4 requests — matching the observed ~4-request bursts (`19:39:55.176 / :57.359 / 1.522 …`).
  Log: `GET /xrpc/space.roomy.space.getInvites failed: Member-created invites are disabled in this space` = **1,375 / 7 days** (top error signature by message); all `getInvites failed` = **1,489** against **307** successes over the same window. Steady every day (127–866/day).
- **Why now**: it is the single largest generator of appserver error noise, which is what makes real errors hard to spot, and it does work the user never asked for on every space load.
- **Scope sketch**: gate the query — `enabled: () => open` in `createInvitesQuery`/`InviteModal`. Optionally go further and skip it entirely when the space has `allowMemberInvites === false` and the caller is not admin, a condition `SpaceSidebar.svelte:144-149` already computes as `showInvitesTab`.
- **Acceptance**: load a space as a non-admin with member invites disabled → zero `getInvites` requests; open the invite modal → exactly one.
- **Suggested priority**: P3.
- **Not already tracked because**: this is an app-lite query-lifecycle bug, not the server-side invite policy TASK-10 is about.

Not one `level="error"` or `level="warn"` line was emitted in that window — the process died without recording why. Collateral: `discord-bridge` logged **334 `Connection error for <space>` in that hour**, every one `XRPC space.roomy.auth.getConnectionTicket failed (502): …origin_bad_gateway`, i.e. Cloudflare in front of a dead origin. Recovery is confirmed: the loop ends at 04:37:29Z on `build_id=d553d6ae…` ("(appserver) migration hotfix", authored 04:35:43Z, touching `db/userSpaceMembershipMigration.ts`) — so the incident is *already fixed*, and the proposal is about detection, not the bug.
- **Why now**: ~30 minutes of total appserver unavailability for every client, discoverable only by noticing 289 identical info lines after the fact. Nothing paged, and the crash left no evidence for a post-mortem.
- **Scope sketch**: emit a distinguishable line (or metric) on unhandled fatal errors that cause process exit, and add a crash-loop signal — e.g. a `roomy_process_starts_total` counter that a Grafana alert can watch for `increase(...[10m]) > 3`. The `/metrics` registry (`appserver/src/metrics.ts`) and Alloy scrape already exist, so this is a counter plus an alert rule.
- **Acceptance**: a deliberately crashing build produces a log line naming the fatal error and trips the restart-rate alert within one scrape interval.
- **Suggested priority**: P2.
- **Not already tracked because**: the queue has no observability item other than the CLI self-check tasks (TASK-85..TASK-103), which cover the *agent fleet*, not the appserver.

### 6. `room.getMetadata` is repeatedly called with an empty `roomId`

- **Evidence**: `GET /xrpc/space.roomy.room.getMetadata failed: Missing or empty required param: roomId` = **199 / 7 days**, present every day, bursts of up to 20/hour (2026-09-14 10:00Z = 20). Two call sites construct the query without an `enabled` guard: `routes/[space]/[room]/+page.svelte:86` and `routes/[space]/[room]/search/+page.svelte:29` both call `createRoomMetadataQuery(() => roomId)` — the helper supports `opts.enabled` (`queries/room-metadata.ts:9`) and `SpaceSidebar.svelte:67` passes it, but these two do not, and both read `roomId` from a non-null-asserted route param.
- **Why now**: same class as proposal 4 — a self-inflicted 4xx the appserver logs as an error on every occurrence, and the fix is one argument per call site.
- **Scope sketch**: pass `{ enabled: !!roomId }` at the two unguarded call sites (or make `enabled` default to `!!roomId()` inside `createRoomMetadataQuery`, which fixes it once for every future caller).
- **Acceptance**: navigating within a space issues no `getMetadata` request without a `roomId`.
- **Suggested priority**: P3.
- **Confidence caveat (could not confirm)**: I could not pin the exact trigger. The two unguarded callers are the only ones I found, but both route components should keep their param populated while mounted, so the empty value more likely comes from a transition or an unmount-race I did not reproduce. The fix above is correct regardless of which of those it is; treat the mechanism as unverified.
